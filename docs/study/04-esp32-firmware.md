## 1. ทำไมต้องเขียนเฟิร์มแวร์เอง

ทางเลือกสำเร็จรูปที่มีคือ **Tasmota** หรือ **ESPHome** ซึ่งทั้งคู่ดีมาก
แต่ไม่ตอบโจทย์สองข้อ

1. **การ provisioning ผ่าน BLE พร้อม token ครั้งเดียว** — ทั้งสองตัวใช้
   Wi-Fi AP mode (บอร์ดปล่อย Wi-Fi ให้เราต่อแล้วกรอกค่าผ่านหน้าเว็บ)
   ซึ่งบนมือถือต้องสลับ Wi-Fi ออกจากเน็ตหลักไปมา ยุ่งยากเมื่อต้องติดตั้ง
   หลายสิบตัว และไม่มีกลไกยืนยันว่าบอร์ดนี้คือบอร์ดที่เราจองตำแหน่งไว้
2. **ไดรเวอร์ IR ของ Saijo Denki** — แอร์ยี่ห้อนี้ในอาคารไม่มีใน
   IRremoteESP8266 ต้องจับสัญญาณเองแล้วเขียนตัวส่ง 72 บิตเอง

การเขียนเองยังทำให้ **ตรรกะ "แอร์ทำงานจริงไหม" อยู่ที่บอร์ด** ซึ่งสำคัญมาก
(อธิบายด้านล่าง)

## 2. ไลบรารีที่ใช้ และทำไม

| ไลบรารี | ใช้ทำอะไร | ทำไมตัวนี้ |
|---|---|---|
| `ArduinoJson` 6.x | แปลง JSON | จัดการหน่วยความจำเองแบบ static ไม่ทำให้ heap แตก |
| `PubSubClient` | MQTT | เล็ก เสถียร ใช้กันแพร่หลายบน ESP32 |
| `IRremoteESP8266` 2.9.0 | ส่ง IR 15 ยี่ห้อ | ครอบคลุมยี่ห้อมากที่สุดในโลก Arduino |
| `PZEM004Tv30` | อ่านมิเตอร์ไฟ | ของผู้ผลิตโมดูลโดยตรง |
| `ld2410` (Nick Reynolds) 0.2.2+ | อ่านเรดาร์ | **ต้อง 0.2.2 ขึ้นไป** เพราะรุ่นเก่าไม่มี API อ่านค่าราย gate |

## 3. `rmutt_esp32_air` — บอร์ดควบคุมแอร์

### ขาที่ใช้

| ขา | ต่อกับ | หมายเหตุ |
|---|---|---|
| `GPIO17` | ตัวส่ง IR (LED อินฟราเรด) | ต้องเห็นตาแอร์ |
| `GPIO0` | ปุ่ม BOOT | กดค้างเพื่อเข้าโหมดตั้งค่า BLE |
| UART2 (`GPIO16` RX / `GPIO18` TX) | PZEM-004T | TTL 9600 baud |
| `GPIO25` / `GPIO26` / `GPIO27` | LED สถานะ | เขียว/แดง/เหลือง |
| `GPIO21` / `GPIO22` | จอ OLED SDA / SCL | เพิ่มใน 2.5.0 (ดูหัวข้อ 3.1) |

### 3.1 จอ OLED 1.3" (อัปเดต 14 ต.ค. 2569)

ตั้งแต่ 2.5.0 (บอร์ด IR) และรุ่นสายแอร์ บอร์ดแอร์ต่อจอ **SH1106 128×64 แบบ I2C**
ที่ GPIO21 (SDA) / GPIO22 (SCL) ใช้ไลบรารี **U8g2** แสดงห้อง·เครื่อง นาฬิกา
สถานะ MQTT/Wi-Fi โหมด อุณหภูมิที่ตั้ง พัดลม กำลังไฟจาก PZEM และ `OUT OF CLASS`
เมื่อแอร์ทำงานนอกคาบ แอร์ปิดนานเกิน 10 นาทีจะพักจอกันจอเบิร์น
ไม่มีจอต่ออยู่ก็ทำงานได้ (Serial ขึ้น `OLED: not found`) ปรับค่าได้ใน `oled_display.h`
(`OLED_LAYOUT`, `OLED_ROTATE_180`, `OLED_CONTRAST`, `OLED_SAVER_AFTER_MS`)

**ทำไมมีไฟล์ `build_opt.h`** — แฟลชช่องแอปเกือบเต็ม (รุ่น 2.4.1 ใช้ 98.8%)
ไฟล์นี้ใส่ `-DU8X8_NO_HW_I2C -DU8X8_NO_HW_SPI` (จอใช้ I2C แบบซอฟต์แวร์)
และในบอร์ด IR ยังปิดโปรโตคอล IR ยี่ห้อที่แอปไม่มีให้เลือกด้วย `-DSEND_xxx=false`
รวมแล้วเฟิร์มแวร์ใส่จอได้และเล็กลงกว่าเดิม ห้ามลบไฟล์นี้
รายละเอียดใน `firmware/rmutt_esp32_air/README_OLED_TH.md`

### วงจรชีวิตของบอร์ด

```
บูต
 ├─ อ่าน NVS
 │   ├─ ยังไม่เคยตั้งค่า ─────> เปิด BLE รอแอปมาตั้งค่า
 │   └─ เคยตั้งค่าแล้ว
 │        ├─ ต่อ Wi-Fi
 │        ├─ ต่อ MQTTS (ตรวจใบรับรอง)
 │        ├─ ถ้ามี token ค้าง ─> ส่ง /provision รอ /provision-ack
 │        └─ เข้าลูปหลัก
 └─ ลูปหลัก
      ├─ ทุก 2 วินาที : อ่าน PZEM 6 ค่า
      ├─ ตัดสิน ac_running
      ├─ ส่ง /status แบบ retained
      ├─ ฟัง /command : ยิง IR แล้วส่ง /state กลับ
      └─ ฟัง /schedule-status : จำว่าตอนนี้มีคาบเรียนไหม
```

### NVS — ทำไมต้องมี

**NVS (Non-Volatile Storage)** คือพื้นที่เก็บค่าถาวรในชิป ESP32
ที่ไม่หายเมื่อไฟดับ

เก็บ Wi-Fi SSID/รหัส · MQTT host/port/user/pass · ห้อง · ลำดับแอร์ ·
โปรโตคอล IR · ตารางเปิดปิดรายวัน

**ถ้าไม่มี** ทุกครั้งที่ไฟดับต้องเดินไปทุกห้องเพื่อ provision ใหม่
ในอาคารสามชั้นนั่นคือหายนะ

สเก็ตช์ `reset/reset.ino` มีไว้ล้าง NVS เมื่อจะย้ายบอร์ดไปห้องอื่น

(อัปเดต 14 ต.ค. 2569) ตั้งแต่แอร์ 2.5.1 / สายแอร์ 2.5.2-slm8 / ตรวจคน 1.3.2
กดลบอุปกรณ์ในแอปแล้ว Backend ส่งคำสั่ง `unprovision` ให้บอร์ดล้าง NVS
และรีบูตเข้าโหมดตั้งค่าบลูทูธเอง (ดู `05-mqtt-ble.md`) `reset.ino` ยังจำเป็น
เมื่อบอร์ดออฟไลน์อยู่ตอนกดลบ

### การตัดสิน `ac_running` — จุดออกแบบที่สำคัญที่สุดของบอร์ดนี้

```
กำลังไฟ ≥ 30 W ติดกัน 3 ครั้ง  →  acRunning = true
กำลังไฟ ≤ 10 W ติดกัน 3 ครั้ง  →  acRunning = false
ระหว่างนั้น                     →  คงค่าเดิมไว้
```

**ทำไมต้องดูหลายครั้ง ไม่ตัดสินจากค่าเดียว**

คอมเพรสเซอร์แอร์ **ตัดเข้าตัดออกเป็นช่วง ๆ** เมื่ออุณหภูมิถึงที่ตั้งไว้
มันจะหยุดแล้วเหลือแค่พัดลมทำงาน กำลังไฟจะตกจาก 800 W เหลือ 40 W
ถ้าตัดสินจากค่าเดียว ระบบจะเห็นแอร์ "ปิด" ทุกครั้งที่คอมเพรสเซอร์พัก
แล้วนาฬิกานับถอยหลังจะรีเซ็ตตลอดเวลา ไม่มีวันครบ 5 นาที

**ทำไมเกณฑ์ขึ้นกับลงไม่เท่ากัน (30 กับ 10)**

นี่คือ **hysteresis** ถ้าใช้เกณฑ์เดียวเช่น 20 W แอร์ที่กินไฟแกว่งอยู่ราว 20 W
พอดีจะสลับสถานะไปมาทุกสองวินาที ทำให้ส่งข้อความรัวและสถานะกระพริบ
การเว้นช่องว่างระหว่างเกณฑ์ขึ้นกับลงทำให้ต้องเปลี่ยนอย่างชัดเจนถึงจะสลับ

**ทำไมตัดสินที่บอร์ด ไม่ส่งค่าดิบให้เซิร์ฟเวอร์ตัดสิน**

- บอร์ดเห็นค่าทุก 2 วินาที ส่วนเซิร์ฟเวอร์เห็นเฉพาะตอนที่ส่งมา
- ถ้าส่งทุกค่าที่อ่านได้ จะได้ข้อความ 30 ครั้ง/นาที/เครื่อง
  40 เครื่องคือ 1,200 ข้อความต่อนาที ซึ่งเปลืองโดยไม่ได้อะไร
- ตรรกะ hysteresis ต้องการ **ประวัติค่าติดกัน** ซึ่งบอร์ดมีอยู่แล้วในตัวแปร
  ถ้าย้ายไปเซิร์ฟเวอร์ต้องเก็บ state ต่ออุปกรณ์ในหน่วยความจำ ซึ่งหายเมื่อรีสตาร์ต

### ไดรเวอร์ IR ของ Saijo Denki

`SaijoDenkiAC.cpp/.h` เป็นโค้ดที่เขียนเองทั้งหมด เพราะยี่ห้อนี้ไม่มีใน
IRremoteESP8266

วิธีทำคือใช้ตัวรับ IR จับสัญญาณจากรีโมตจริงทีละปุ่ม แล้วถอดรหัสว่า
72 บิตนั้นบิตไหนคืออะไร

ช่วงคำสั่งที่ยืนยันแล้วว่าใช้ได้จริง — Power, Cool, 18–29 °C,
Fan Auto/Low/Medium/High, Swing แนวตั้ง Auto/Top/Middle/Bottom

**ข้อจำกัดของ IR ที่ต้องยอมรับ** — เป็นการสื่อสาร **ทางเดียว ไม่มีการตอบรับ**
บอร์ดไม่มีทางรู้ว่าแอร์ได้รับคำสั่งหรือไม่ วิธีเดียวที่ยืนยันได้คือ
**ดูว่ากำลังไฟเปลี่ยนไหม** ซึ่งเป็นเหตุผลที่ระบบปิดอัตโนมัติต้องยิงซ้ำและ
ตรวจผลจาก PZEM

### PZEM-004T v3.0

โมดูลวัดไฟที่ต่อกับสายเมนของแอร์ คุยผ่าน UART 9600 baud โปรโตคอล Modbus-RTU

ให้ 6 ค่า — แรงดัน (V) · กระแส (A) · กำลังไฟจริง (W) · พลังงานสะสม (kWh) ·
ความถี่ (Hz) · ตัวประกอบกำลัง (PF)

**คอลัมน์อื่นทั้งหมดในรายงานคำนวณต่อจาก 6 ค่านี้** ไม่มีค่าไหนที่เซ็นเซอร์
ไม่ได้ให้มาจริง

> **ข้อควรระวังด้านความปลอดภัย** — PZEM ต่อกับไฟบ้าน 220 V
> ส่วน CT (คอยล์วัดกระแส) คล้องรอบสายไฟโดยไม่ต้องตัดสาย
> การติดตั้งต้องทำโดยคนที่มีความรู้เรื่องไฟฟ้า และต้องตัดเบรกเกอร์ก่อนเสมอ

**`pzemAvailable`** เป็น boolean แยกต่างหาก เพราะถ้าโมดูลไม่ตอบ
ค่าที่อ่านได้จะเป็น `NaN` ซึ่งถ้าส่งไปเป็น 0 เซิร์ฟเวอร์จะคิดว่าแอร์ปิดอยู่
ทั้งที่จริงคือวัดไม่ได้

## 3.2 `rmutt_esp32_air_wired` — บอร์ดสายแอร์ Daikin SLM8 (อัปเดต 14 ต.ค. 2569)

เฟิร์มแวร์ที่แตกจากรุ่น IR 2.4.1 ใช้กับแอร์ Daikin ที่ **ถอดรีโมตติดผนังออก**
แล้วให้ ESP32 คุยกับแอร์ทางสายแอร์โดยตรง BLE, MQTT topic, PZEM, LED, OTA
และข้อมูลย้อนหลังเหมือนรุ่น IR ทุกอย่าง แอปและ Backend จึงใช้ได้โดยไม่ต้อง migrate
ฐานข้อมูล (คอลัมน์ `protocol` เก็บค่า `DAIKIN_WIRED`)

| ขา | ต่อกับ | หมายเหตุ |
|---|---|---|
| `GPIO33` | สายสั่งงาน (panel → แอร์) ผ่านไดโอด 1N4148 | `BUS_TX_PIN` (ใช้ 2N2222 แทนได้ ตั้ง `BUS_TX_INVERT = true`) |
| `GPIO35` | สายสถานะ (แอร์ → panel) ผ่านตัวแบ่งแรงดัน 100k/200k | `BUS_RX_PIN` |
| `GPIO34` | สายสั่งงาน ผ่าน 100k/200k | `BUS_ECHO_PIN` ตรวจเฟรมของตัวเอง ไม่บังคับ (-1 = ไม่ใช้) |
| `GPIO4` | DHT11 (Keyes KY-015) | อุณหภูมิห้อง อ่านทุก 5 วินาที |
| `GPIO21` / `GPIO22` | จอ OLED | เหมือนรุ่น IR |
| `GPIO16` / `GPIO18`, `GPIO25/26/27` | PZEM, LED | เหมือนรุ่น IR |

**ทำไมต้องใช้ FreeRTOS task แยก** — สายแอร์ต้องได้เฟรมทุก 1 วินาทีตลอดเวลา
(แอร์คิดว่ารีโมตติดผนังหายถ้าเงียบ) แต่ `loop()` หลักมีช่วงค้างนาน เช่น ต่อ Wi-Fi,
ต่อ MQTT/TLS, OTA `wired_bus.h` จึงสร้าง task `slm8bus` ด้วย
`xTaskCreatePinnedToCore(..., 4096, ..., 3, nullptr, 1)` = stack 4 KB, priority 3
(สูงกว่า `loop()` ที่เป็น 1) บน core 1 และป้องกันข้อมูลที่ใช้ร่วมกันด้วย mutex
ตอนบูตจะส่งค่าที่จำไว้ใน NVS ตั้งแต่เฟรมแรก แอร์จึงไม่ดับเองเมื่อบอร์ดรีบูต

**ทำไมมี DHT11** — รีโมตติดผนังเดิมมีเซนเซอร์อุณหภูมิห้องที่แอร์ใช้ตัดคอมเพรสเซอร์
บอร์ดจึงอ่าน DHT11 แล้วส่งค่าให้แอร์แทน (อ่านเฉพาะช่วงสายว่างหลังส่งเฟรม
เพราะ DHT11 ปิด interrupt ชั่วครู่) ชดเชยค่าคลาดได้ด้วย `ROOM_TEMP_OFFSET_C`

**ฟังก์ชันที่แอร์รับได้ทางสาย** — เปิด/ปิด · 16–30 °C · Cool/Dry/Fan ·
พัดลม Low/Medium/High/Auto · ส่าย เปิด/ปิด · Sleep (ไม่ได้ในโหมด Dry)
คำสั่งนอกเหนือจากนี้ Backend ปฏิเสธ และถ้าหลุดมาถึงบอร์ด เฟิร์มแวร์ปรับให้ตรง
กับที่แอร์ทำได้แล้วรายงานค่าจริงใน `state`

**ต่างจากรุ่น IR ตรงที่สื่อสารสองทาง** — `status` มีช่องเพิ่ม
`controlMode: "wired"`, `busOk`, `compressorRunning`, `unitRoomTemperature`,
`roomTemperature` และ identity บลูทูธส่ง `"controlType":"wired","brand":"Daikin"`
ให้แอปล็อกยี่ห้อเป็น **Daikin · สายแอร์**

ไลบรารีเพิ่ม: **U8g2**, **DHT sensor library** (Adafruit) ไม่ต้องใช้ IRremoteESP8266
รายละเอียดการต่อสายและการทดสอบหลังแฟลชอยู่ใน
`firmware/rmutt_esp32_air_wired/README_WIRED_TH.md`

## 4. `rmutt_esp32_occupancy` — บอร์ดตรวจคน

### ขาที่ใช้

| ขา | ต่อกับ |
|---|---|
| `GPIO32` | LD2410 `TX` (บอร์ดรับ) |
| `GPIO33` | LD2410 `RX` (บอร์ดส่ง) |
| `GPIO0` | ปุ่ม BOOT |

```cpp
constexpr uint8_t  RADAR_RX_PIN = 32;
constexpr uint8_t  RADAR_TX_PIN = 33;
constexpr uint32_t RADAR_BAUD   = 256000;
```

### HLK-LD2410 คืออะไร และทำไมไม่ใช้ PIR

**PIR (Passive Infrared)** คือเซ็นเซอร์ตรวจความเคลื่อนไหวราคาถูกที่ใช้กับ
ไฟทางเดินทั่วไป ปัญหาคือมัน **ตรวจเฉพาะการเคลื่อนไหว** คนที่นั่งนิ่ง ๆ
อ่านหนังสือหรือใช้คอมพิวเตอร์จะถูกมองว่าไม่มีคนภายในไม่กี่นาที

ในห้องเรียนหรือห้องทำงาน นี่คือกรณีปกติ ไม่ใช่ข้อยกเว้น **ถ้าใช้ PIR
ระบบจะปิดแอร์ใส่คนที่นั่งอยู่**

**LD2410 เป็นเรดาร์คลื่นมิลลิเมตร 24 GHz** ที่จับได้ทั้ง

- **Moving target** — คนเดิน
- **Stationary target** — คนนั่งนิ่ง จับจากการขยับของหน้าอกตอนหายใจ

ความสามารถอย่างหลังคือเหตุผลเดียวที่เลือกโมดูลนี้

### กติกาตัดสิน

```
เปิด Engineering mode
อ่าน static energy ของเกต 0 ถึง 8
เกตใดเกตหนึ่ง > 25  →  occupied = true
ทุกเกต ≤ 25          →  occupied = false
```

**"เกต" คืออะไร** — LD2410 แบ่งระยะออกเป็นช่วง ๆ เรียกว่าเกต
เกตละประมาณ 0.75 เมตร เกต 0 คือใกล้สุด เกต 8 คือราว 6 เมตร
แต่ละเกตรายงานความแรงของสัญญาณสะท้อนเป็นตัวเลข 0–100

**ทำไมต้องเปิด Engineering mode** — โหมดปกติของ LD2410 รายงานแค่
"มี/ไม่มีเป้าหมาย" ตามเกณฑ์จากโรงงาน ซึ่งเราปรับไม่ได้และไม่รู้ว่ามันคิดยังไง
Engineering mode ให้ค่าดิบรายเกต ทำให้ตั้งเกณฑ์เองได้ตามขนาดห้อง

**ทำไมใช้แค่ static ไม่ใช้ moving** — เพราะถ้ามีคนเดินอยู่ ก็ต้องมีคน
นั่งอยู่ในห้องด้วยอยู่แล้ว static ครอบคลุมทั้งสองกรณี ส่วน moving อย่างเดียว
จะพลาดคนนั่งนิ่ง การใช้ทั้งคู่ไม่ได้เพิ่มความแม่นแต่เพิ่มความซับซ้อน

**ทำไมเกณฑ์ 25** — ได้จากการทดลองในห้องจริง ค่าต่ำกว่านี้จะตรวจเจอสัญญาณ
สะท้อนจากผนังและพัดลม ค่าสูงกว่านี้จะพลาดคนที่นั่งไกล
เก็บเป็นคอลัมน์ `static_threshold` ในฐานข้อมูลเพื่อปรับรายห้องได้

### `radarAvailable` แยกจาก `occupied` — บทเรียนราคาแพง

```json
{
  "online": true,
  "radarAvailable": true,
  "occupied": true,
  "staticThreshold": 25
}
```

สามค่านี้ **ห้ามรวมกัน** เพราะ

| สถานการณ์ | online | radarAvailable | occupied | ระบบควรทำอะไร |
|---|---|---|---|---|
| ปกติ มีคน | true | true | true | ไม่ปิด |
| ปกติ ไม่มีคน | true | true | false | **เริ่มนับถอยหลัง** |
| สาย UART หลุด | true | **false** | false | **ห้ามปิดเด็ดขาด** |
| บอร์ดไฟดับ | **false** | — | — | **ห้ามปิดเด็ดขาด** |

แถวที่สามคือสิ่งที่เกิดขึ้นจริงกับห้อง 16103 — บอร์ดต่อเน็ตได้ปกติ
แต่สาย UART ต่อผิดขา อ่านเรดาร์ไม่ได้ ถ้า `occupied` เป็นค่าเดียวที่ส่งมา
ระบบจะเห็น `false` แล้วสั่งปิดแอร์ใส่คนที่นั่งอยู่

### การหาสาเหตุเมื่อเรดาร์เงียบ

เฟิร์มแวร์ 1.1.2 ขึ้นไปพิมพ์บล็อก `[diag]` ทุก 10 วินาที

```text
[diag] wifi=yes ip=192.168.1.109 rssi=-52 | mqtt=yes state=0 | room=16103
[diag] radar init=0 engineeringEnabled=0 isConnected=0 available=0 occupied=0
[diag] UART1 rx bytes in the last 10s: 0
```

**`UART1 rx bytes: 0` บอกอะไร** — ได้ **ศูนย์ไบต์** ไม่ใช่ไบต์ขยะ
ความต่างนี้สำคัญมาก

- ได้ไบต์ขยะ = มีสัญญาณเข้ามาแต่ถอดรหัสไม่ได้ → **baud ผิด**
- ได้ศูนย์ไบต์ = ไม่มีสัญญาณเข้ามาเลย → **สายผิด ขาเสีย หรือไม่มีไฟเลี้ยง**

เมื่อรู้ว่าเป็นอย่างหลัง จึงสร้างเครื่องมือสองตัว

**`ld2410_probe.ino`** — ทดสอบทางไฟฟ้าที่ GPIO32/33 ด้วย `INPUT_PULLDOWN`
แล้วไล่ 6 ชุด (สลับขา × 3 baud)

**`ld2410_pinscan.ino`** — สแกน 18 ขาทีละขา หาว่าสายไปถึงขาไหนจริง

```cpp
const uint8_t PINS[] = {2,4,5,12,13,14,16,17,18,19,21,22,23,25,26,27,32,33};
```

ตัดออกโดยตั้งใจ — `GPIO 6–11` (ต่อชิปแฟลช แตะแล้วบอร์ดค้าง) ·
`GPIO 1, 3` (Serial ที่คุยกับคอม) · `GPIO 0` (ปุ่ม BOOT) ·
`GPIO 34–39` (อ่านอย่างเดียว ไม่มี pull ภายใน สแกนแล้วได้แต่สัญญาณรบกวน)

**วิธีแยกว่าขาไหนมีข้อมูล**

1. เปิด pull-up ภายในแล้วอ่าน
2. เปิด pull-down ภายในแล้วอ่าน
3. นับจำนวนครั้งที่สถานะพลิกใน 250 ms

| ผล | แปลว่า |
|---|---|
| ค่าเปลี่ยนตาม pull ที่เปิด | ไม่มีอะไรต่ออยู่ ขาปกติดี |
| พลิก 20–8000 ครั้ง | **มีข้อมูล UART วิ่งอยู่** |
| ค้าง HIGH | มีสายต่อแต่แพดนั้นไม่ส่ง → จิ้มผิดแพด |
| ค้าง LOW | ขาถูกดึงลง GND อย่าใช้ |
| พลิกเกิน 8000 ครั้ง | เร็วเกินกว่าจะเป็นข้อมูล น่าจะเป็นคริสตัล |

**ที่มาของเลข 8000** — LD2410 ส่งเฟรมละ ~30 ไบต์ ทุก 100 ms
ใน 250 ms จึงได้ 2–3 เฟรม คิดเป็นบิตที่พลิกจริงหลักร้อย
ส่วนคริสตัล 32.768 kHz ที่บางบอร์ดติดมาที่ GPIO32/33 จะพลิก
65,536 ครั้งต่อวินาที = ราว 16,000 ครั้งใน 250 ms
**ตัวเลขห่างกันสิบเท่า จึงแยกด้วยช่วงได้ชัดเจน**

ผลที่ได้จริงคือ **GPIO32 ที่ 256000 baud รับข้อมูลได้ถูกต้อง** (184 ไบต์
ใน 0.8 วินาที = 8 เฟรม × 23 ไบต์ ซึ่งตรงกับเฟรมโหมดปกติพอดี)
ค่าตรงกับที่สเก็ตช์หลักตั้งไว้อยู่แล้ว แปลว่า **โค้ดไม่เคยผิด สายอยู่ผิดแพด**

> LD2410C มี 5 แพด และแพดที่สกรีนว่า `TX` **ไม่ใช่แพดที่ส่งจริงเสมอไป**
> ขึ้นกับรุ่นย่อยและผู้ผลิตบอร์ดขยาย

### `radarAvailable` คิดจากเวลา ไม่ใช่จากธง

เฟิร์มแวร์ 1.1.3 แก้บั๊กที่กินเวลานาน

```cpp
if (freshFrame) { lastRadarDataAt = millis(); lastRadarDetected = ...; }
radarAvailable = radarInitialised && radarEngineeringEnabled &&
                 lastRadarDataAt != 0 &&
                 millis() - lastRadarDataAt < RADAR_DATA_TIMEOUT_MS;  // 3 วิ
```

**ปัญหาเดิม** — `ld2410::engineeringRetrieved()` คืน `true` **ครั้งเดียวต่อ
หนึ่งเฟรม** แล้วล้างธงทิ้ง การเอามันมาใช้เป็นเงื่อนไข "เซ็นเซอร์พร้อมใช้งาน"
ตรง ๆ ทำให้สถานะกระพริบหลายครั้งต่อนาที และทุกครั้งที่กระพริบจะส่ง MQTT
แบบ retained ออกไป แอปจึงสลับไปมาระหว่างค่าจริงกับ `เซ็นเซอร์ไม่พร้อมใช้งาน`

ที่แย่กว่านั้นคือ **บล็อก `[diag]` ก็เรียกฟังก์ชันเดียวกัน** จึงไปแย่งธงจาก
ตัวที่ทำงานจริง ทำให้ยิ่งกระพริบหนักขึ้น — เครื่องมือวินิจฉัยกลายเป็นตัวปัญหาเอง

**วิธีแก้** — จำ **เวลาของเฟรมล่าสุด** แล้วถือว่าพร้อมใช้งานถ้าเฟรมล่าสุด
เก่าไม่เกิน 3 วินาที เรดาร์ส่งราว 10 เฟรมต่อวินาที การเงียบ 3 วินาที
จึงเป็นความผิดปกติจริง ไม่ใช่แค่พลาดไปหนึ่งเฟรม

## 5. MQTTS และใบรับรอง

`update-root-ca.ps1` ดาวน์โหลดใบรับรอง **ISRG Root X1** (root ของ
Let's Encrypt) แล้วสร้างไฟล์ `letsencrypt_ca.h` ให้ `rmutt_esp32_air` และ `rmutt_esp32_occupancy`
(`rmutt_esp32_air_wired` มีไฟล์นี้ติดมาในโฟลเดอร์แล้ว แต่สคริปต์ยังไม่ได้เขียนให้ ถ้าอัปเดตใบรับรองให้คัดลอกไปเอง)
(ใบรับรองของ Tailscale Funnel `*.ts.net` ก็ออกโดย Let's Encrypt บอร์ดจึงต่อพอร์ต 8443 ได้ด้วย root เดียวกัน)

**ต้องรันก่อนคอมไพล์ทุกครั้ง** ถ้าไม่มีไฟล์นี้จะคอมไพล์ไม่ผ่าน

**ทำไมต้องฝังใบรับรองในเฟิร์มแวร์** — ESP32 ไม่มีที่เก็บ root CA
เหมือนเบราว์เซอร์หรือระบบปฏิบัติการ ถ้าไม่ฝังไว้ก็ตรวจไม่ได้ว่ากำลังคุย
กับเซิร์ฟเวอร์จริงหรือคนกลาง

**ทางเลือกที่ไม่ควรทำ** — `setInsecure()` ซึ่งข้ามการตรวจใบรับรองไปเลย
ทำให้ต่อได้ง่ายแต่ใครก็ปลอมเป็น Broker แล้วสั่งเปิดปิดแอร์ทั้งอาคารได้

**ข้อควรระวัง** — ใบรับรอง root มีวันหมดอายุ ISRG Root X1 หมดอายุปี 2035
ก่อนถึงตอนนั้นต้องอัปเดตเฟิร์มแวร์ทุกบอร์ด

## 7. Wi-Fi retry ระหว่างเปิด BLE

เฟิร์มแวร์รุ่นแรกมีปัญหา — ถ้ากรอก Wi-Fi ผิดตอน provisioning
บอร์ดจะพยายามต่อแล้วล้มเหลว แต่ BLE ถูกปิดไปแล้ว **จึงแก้ไม่ได้เลย**
ต้องต่อสาย USB แล้วล้าง NVS อย่างเดียว ซึ่งบนเพดานทำไม่ได้

รุ่นปัจจุบันจึง **เปิด BLE ค้างไว้ระหว่างพยายามต่อ Wi-Fi**
ถ้าต่อไม่ได้ภายในเวลาที่กำหนด ยังกลับมาแก้ค่าผ่านแอปได้

นี่เป็นตัวอย่างของบทเรียนที่ได้จากการติดตั้งจริงเท่านั้น
ตอนทดสอบบนโต๊ะจะไม่มีวันเจอ เพราะสาย USB เสียบอยู่แล้ว
