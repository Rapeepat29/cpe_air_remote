## 2. `run_all.ps1` — สคริปต์เดียวจบตอนพัฒนา

ทำ 7 ขั้นเรียงกัน

1. ตรวจว่ามี Node, Flutter, Docker ครบไหม
2. `setup_mqtt.ps1` — หา LAN IP → สุ่มรหัสผ่าน → สร้าง ACL → เขียนลง `.env`
3. `docker compose up` ของ Broker
4. `npm install` ของ backend
5. รัน migration ทุกตัวเรียงกัน
6. `doctor.js --fix`
7. `npm start`

**ทำไมต้องสุ่มรหัส MQTT ให้** — ถ้าให้คนตั้งเอง ส่วนใหญ่จะตั้ง `1234`
หรือปล่อยว่าง การสุ่มให้ทำให้ค่าเริ่มต้นปลอดภัยโดยไม่ต้องพึ่งวินัยของคน

**ทำไมต้องหา LAN IP อัตโนมัติ** — ESP32 ต้องรู้ที่อยู่ Broker
ซึ่งเปลี่ยนทุกครั้งที่ย้ายเครือข่าย (บ้าน → มหาวิทยาลัย → ร้านกาแฟ)
ถ้าให้คนจดเอง จะลืมอัปเดตแล้วมานั่งงงว่าทำไมบอร์ดต่อไม่ได้

### ข้อควรรู้เรื่อง PowerShell 5.1

Windows 10/11 มากับ PowerShell 5.1 ซึ่งมีข้อจำกัดที่กัดเจ็บ

| ปัญหา | วิธีแก้ |
|---|---|
| อ่านไฟล์ UTF-8 ที่ไม่มี BOM เป็นภาษาไทยไม่ออก | ต้องบันทึกไฟล์ `.ps1` แบบ **UTF-8 with BOM** |
| `$` และ `` ` `` ในสตริงคู่ถูกตีความ | ใช้สตริงเดี่ยว `'...'` เมื่อมีอักขระพวกนี้ |
| ไฟล์ `.sh` ที่แก้บน Windows ติด CRLF | `sed -i 's/\r$//'` ก่อนรันบน Linux |

ข้อสุดท้ายเป็นปัญหาที่หาสาเหตุยากมาก — bash จะฟ้อง
`bad interpreter: /bin/bash^M: no such file or directory`
ซึ่งดูเหมือนไฟล์หายทั้งที่อยู่ตรงนั้น

## 3. `deploy/` — โครงสร้างบน VPS

```
/opt/rmutt/
├── docker-compose.yml
├── .env
├── backend/          ซอร์สที่อัปโหลดขึ้นไป
├── backend.Dockerfile
├── Caddyfile
├── mosquitto/
└── update-remote.sh
```

### สี่คอนเทนเนอร์

| ชื่อ | ภาพ | หน้าที่ |
|---|---|---|
| `db` | mariadb | ฐานข้อมูล |
| `mqtt` | eclipse-mosquitto | Broker |
| `backend` | node | API |
| `caddy` | caddy | reverse proxy + HTTPS |

**ทำไมต้อง Caddy ไม่ใช่ nginx**

Caddy **ขอและต่ออายุใบรับรอง Let's Encrypt ให้เองอัตโนมัติ**
โดยตั้งค่าแค่ชื่อโดเมน

nginx ต้องติดตั้ง certbot แยก ตั้ง cron ต่ออายุ และเขียนคอนฟิก TLS เอง
ซึ่งมีรายละเอียดเยอะและพลาดง่าย

สำหรับโปรเจกต์ที่ไม่มีคนดูแลเต็มเวลา **การที่ใบรับรองต่ออายุเองได้
สำคัญกว่าความยืดหยุ่นที่ nginx ให้**

ใบรับรองของ Let's Encrypt อายุ 90 วัน ถ้าลืมต่อ ระบบจะพังทั้งหมด
ทั้งแอปและ ESP32 พร้อมกัน

### ทำไม Backend คุย Broker ผ่านชื่อ service

```
MQTT_URL=mqtt://mqtt:1883                                 ← Backend ใช้
MQTT_DEVICE_URL=mqtts://rmutt-energy.duckdns.org:8883      ← ส่งให้ ESP32
```

ใน Docker network คอนเทนเนอร์เรียกกันด้วยชื่อ service ได้เลย
ไม่ต้องออกอินเทอร์เน็ตแล้ววนกลับเข้ามา ซึ่ง

- เร็วกว่า
- ไม่กิน bandwidth
- **ไม่ต้องเปิดพอร์ต 1883 ออกสู่ภายนอก**

ส่วน ESP32 อยู่ในอาคารซึ่งเป็นคนละเครือข่าย ต้องเข้ามาทางโดเมนจริง
และต้องเข้ารหัสเพราะวิ่งผ่านอินเทอร์เน็ต

## 4. `update-server.ps1` — อัปเดตด้วยคำสั่งเดียว

```powershell
.\deploy\update-server.ps1
```

| ขั้น | ทำอะไร |
|---|---|
| 1 | `scp` อัปโหลด `src`, `scripts`, `database`, `package.json` |
| 2 | `ssh` รัน `update-remote.sh` บนเซิร์ฟเวอร์ |

**ทำไมอัปโหลดแค่บางโฟลเดอร์** — `node_modules` มีหลายหมื่นไฟล์
อัปโหลดทุกครั้งจะช้ามาก และอาจมีไฟล์ที่คอมไพล์สำหรับ Windows
ซึ่งใช้บน Linux ไม่ได้ `npm install` บนเซิร์ฟเวอร์แทนจะได้ของที่ถูกต้อง

**ทำไมส่งสคริปต์ไปพร้อมกัน** — เพื่อให้ถามรหัสผ่าน **แค่รอบเดียว**
ถ้าแยกเป็นสองคำสั่ง `ssh` จะถามสองครั้ง ซึ่งน่ารำคาญพอที่คนจะเลี่ยงไม่ใช้สคริปต์

### `update-remote.sh` — 5 ขั้นบนเซิร์ฟเวอร์

```bash
1. docker compose up -d --build backend
2. รอให้ backend พร้อม (ลองทุก 2 วินาที สูงสุด 40 ครั้ง)
3. รัน migration ทุกตัว + doctor --fix
4. restart backend
5. ตรวจว่าใช้งานได้จริง
```

### ขั้นที่ 2 ทำไมต้องรอ

```bash
for _ in $(seq 1 40); do
  if docker compose exec -T backend node -e 'process.exit(0)' >/dev/null 2>&1; then
    ready=1; break
  fi
  sleep 2
done
```

`docker compose up -d` คืนค่าทันทีที่ **สั่งสร้าง** คอนเทนเนอร์
ไม่ใช่ตอนที่มันพร้อมใช้งาน ถ้ารีบรัน migration ต่อเลยจะเจอ
`container not running` แล้วสคริปต์ล้มทั้งที่ไม่มีอะไรผิด

การรอสูงสุด 80 วินาทีเผื่อเครื่องช้าและ image ใหญ่

### ขั้นที่ 5 ตรวจอะไรบ้าง

```bash
health=$(curl -s --max-time 20 "https://$DOMAIN/api/health")
case "$health" in
  *'"status":"ok"'*)      echo 'API ตอบปกติ' ;;
  *) fail "API ยังไม่ตอบ" ;;
esac
case "$health" in
  *'"connected":true'*)   echo 'MQTT เชื่อมต่ออยู่' ;;
  *) echo 'เตือน: MQTT ยังไม่เชื่อมต่อ' ;;
esac

for path in /api/alerts /api/energy/summary /api/energy/live /api/settings; do
  code=$(curl -s -o /dev/null -w '%{http_code}' "https://$DOMAIN$path")
  [ "$code" = "401" ] && echo "OK   $path" || echo "ผิด  $path -> $code"
done
```

**ทำไมคาดหวัง 401 ไม่ใช่ 200**

- `401 Unauthorized` = **เส้นทางมีอยู่จริง** แค่ยังไม่ได้ล็อกอิน → โค้ดใหม่ขึ้นแล้ว
- `404 Not Found` = เส้นทางไม่มี → **โค้ดใหม่ยังไม่ขึ้น**

เป็นวิธีตรวจว่า deploy สำเร็จจริงโดยไม่ต้องมี token
ถ้าไม่มีการตรวจนี้ คนจะคิดว่าอัปเดตแล้วทั้งที่ยังไม่ขึ้น แล้วไปงงที่แอป
(ซึ่งเกิดขึ้นจริง — แอปขึ้น `ไม่พบ API ที่เรียกใช้งาน` เพราะลืมอัปเดต VPS)

**MQTT เป็นแค่คำเตือน ไม่ใช่ล้มเหลว** เพราะ Broker อาจเพิ่ง restart
และยังไม่ต่อกลับมา ซึ่งจะหายเองในไม่กี่วินาที

### ขั้นสุดท้าย ตรวจว่าตัวคุมจังหวะทำงาน

```bash
if docker compose logs --tail 200 backend | grep -q 'Auto-off service started'; then
  echo 'ตัวคุมจังหวะปิดแอร์อัตโนมัติทำงานแล้ว'
fi
```

เพราะ API ตอบได้ไม่ได้แปลว่างานเบื้องหลังเริ่มแล้ว มันอาจล้มตอน startup
โดยที่ Express ยังรับคำขอได้ปกติ

## 5. ความปลอดภัย

### รหัสผ่าน · bcrypt cost 12

```js
password.length >= 8 && Buffer.byteLength(password, 'utf8') <= 72
```

**ทำไม cost 12** — ใช้เวลาราว 0.2–0.3 วินาทีต่อครั้ง คนไม่รู้สึก
แต่ทำให้การไล่เดารหัสช้าลงเป็นล้านเท่าเทียบกับ MD5 หรือ SHA-1

**ทำไม 72 ไบต์** — bcrypt ตัดที่ 72 ไบต์ ตัวที่ 73 เป็นต้นไปถูกทิ้งเงียบ ๆ
ถ้าไม่ดัก ผู้ใช้ที่ตั้งรหัสยาวจะคิดว่าปลอดภัยมากทั้งที่ไม่ใช่

สังเกตว่าเช็ค **ไบต์** ไม่ใช่ **ตัวอักษร** — ภาษาไทยหนึ่งตัวกิน 3 ไบต์
รหัสผ่านไทย 24 ตัวก็ชน 72 ไบต์แล้ว

### OTP · HMAC ไม่ใช่ hash เปล่า

```js
export function hashSecret(value, pepper = config.otpPepper) {
  return crypto.createHmac('sha256', pepper).update(value).digest('hex');
}
```

OTP มี 6 หลัก = 1,000,000 ความเป็นไปได้
ถ้าใช้ SHA-256 เปล่า ๆ คนที่ขโมยฐานข้อมูลไปสร้างตารางเทียบครบทุกค่า
ได้ในไม่กี่วินาที

HMAC ผสม **ความลับที่อยู่ใน `.env` ไม่ได้อยู่ในฐานข้อมูล** เข้าไปด้วย
คนที่ได้แค่ฐานข้อมูลจึงเทียบกลับไม่ได้

**`OTP_PEPPER` ต้องต่างจาก `JWT_SECRET`** — ถ้าใช้ค่าเดียวกัน
การรั่วของอย่างหนึ่งจะทำให้อีกอย่างพังตามทันที

### การเทียบ hash · `timingSafeEqual`

```js
return left.length === right.length && crypto.timingSafeEqual(left, right);
```

`===` หยุดทันทีที่เจอตัวต่างกัน ทำให้เวลาที่ใช้บอกใบ้ว่าเดาถูกไปกี่ตัว
`timingSafeEqual` เทียบครบทุกไบต์เสมอ

การโจมตีแบบนี้ทำได้ยากผ่านอินเทอร์เน็ต แต่ **ต้นทุนของการทำถูกแทบเป็นศูนย์**
จึงไม่มีเหตุผลที่จะไม่ทำ

### JWT · `token_version`

JWT ยกเลิกไม่ได้เมื่อออกไปแล้ว คอลัมน์ `token_version` แก้ปัญหานี้

ใส่ค่านี้ลงไปใน token ตอนออก แล้วทุกครั้งที่ตรวจให้เทียบกับฐานข้อมูล
เมื่อเปลี่ยน role / เปลี่ยนรหัสผ่าน / ปิดบัญชี ก็แค่ `+1`
**session เดิมทุกเครื่องตายทันที** โดยไม่ต้องเก็บรายการ token ที่ยกเลิกแล้ว

### กติกากันพลาดของการจัดการผู้ใช้

1. **แก้หรือลบบัญชีตัวเองไม่ได้** — กันไม่ให้ถอดสิทธิ์ตัวเองจนเข้าไม่ได้
2. **ต้องเหลือ admin ที่ `is_active` อย่างน้อย 1 บัญชีเสมอ**

ข้อ 2 ตรวจใน transaction ด้วย `FOR UPDATE`

```sql
SELECT COUNT(*) FROM users
 WHERE role = 'admin' AND is_active = TRUE AND username <> ?
 FOR UPDATE
```

**ทำไมต้อง `FOR UPDATE`** — ถ้าแอดมินสองคนกดถอดสิทธิ์กันเองพร้อมกัน
ทั้งคู่จะเห็นว่า "ยังเหลืออีกคน" แล้วทั้งคู่ก็ถอดสำเร็จ
ผลคือ **ไม่เหลือแอดมินเลย และไม่มีใครเข้าไปแก้ได้อีก**

`FOR UPDATE` ล็อกแถวไว้ ทำให้คนที่สองต้องรอ แล้วจะเห็นสถานะหลังจากคนแรกทำเสร็จ

### `publicUser()` — ด่านเดียวที่ข้อมูลออกไป

ทุกเส้นทางที่คืนข้อมูลผู้ใช้ต้องผ่านฟังก์ชันนี้ ซึ่งตัด `id`,
`password_hash`, `token_version` ทิ้ง

**ทำไมตัด `id`** — ตัวเลขที่ไล่ขึ้นเรื่อย ๆ บอกใบ้ว่าระบบมีผู้ใช้กี่คน
และเดา id ของคนอื่นได้

มีเทสต์ยืนยันว่า `'id' in result === false` ซึ่งจะจับได้ทันทีถ้ามีคน
เผลอเพิ่มกลับเข้าไป

### `assertServerConfig()` — ปฏิเสธค่าที่ไม่ปลอดภัย

```js
function unsafeSecret(value) {
  return value.length < 32 || /replace|change|example/i.test(value);
}
```

เซิร์ฟเวอร์จะไม่ยอมเปิดถ้า secret สั้นเกินไปหรือยังเป็นค่าตัวอย่าง

ความผิดพลาดแบบนี้ **ไม่แสดงอาการ** ระบบยังทำงานได้ทุกอย่าง
แค่ใครก็ปลอม token ได้ การดักตั้งแต่ตอนเปิดคือวิธีเดียวที่จะรู้

### MQTTS และ ACL

- **MQTTS** กันการดักฟังและการปลอมคำสั่ง
- **ACL** จำกัดว่าผู้ใช้ไหนเข้าถึงหัวข้อไหนได้

```
topic readwrite rmutt/ac/#
topic readwrite rmutt/occupancy/#
```

**ถ้าขาดบรรทัดใดบรรทัดหนึ่ง Broker จะปฏิเสธเงียบ ๆ**
ไม่มี error ไคลเอนต์คิดว่าสำเร็จ แต่ข้อความหายไปเฉย ๆ

นี่คือข้อผิดพลาดที่กินเวลาหาสาเหตุมากที่สุดในโปรเจกต์

### ใบรับรองใน ESP32

`update-root-ca.ps1` ฝัง ISRG Root X1 ลงในเฟิร์มแวร์
**ต้องรันก่อนคอมไพล์ทุกครั้ง**

ทางเลือกที่ไม่ควรทำคือ `setInsecure()` ซึ่งข้ามการตรวจใบรับรอง
ทำให้ต่อง่ายแต่ใครก็ปลอมเป็น Broker แล้วสั่งเปิดปิดแอร์ทั้งอาคารได้

**ข้อควรระวังระยะยาว** — ISRG Root X1 หมดอายุปี 2035
ก่อนถึงตอนนั้นต้องอัปเดตเฟิร์มแวร์ทุกบอร์ด ซึ่งควรจดไว้ในเอกสารส่งมอบ

## 6. สิ่งที่ยังไม่ปลอดภัยพอ และควรแก้

เขียนไว้ตรง ๆ เพื่อให้คนที่มาดูแลต่อรู้

| เรื่อง | ความเสี่ยง | ควรทำ |
|---|---|---|
| รหัสผ่าน MQTT เคยหลุดเป็น plaintext ในการสนทนา | ใครที่เห็นสามารถสั่งงานอุปกรณ์ได้ | เปลี่ยนรหัสแล้ว re-provision ทุกบอร์ด |
| ยังไม่ได้แฟลชเฟิร์มแวร์ TLS ลงบอร์ดจริง | บอร์ดยังคุย MQTT ไม่เข้ารหัส | แฟลช 1.2.0 / 2.2.0 แล้ว re-provision |
| ไม่มีการจัดการ 401 อัตโนมัติในแอป | token หมดอายุแล้วแอปค้าง ผู้ใช้ต้องปิดเปิดเอง | ดัก 401 แล้วพาไปหน้าล็อกอิน |
| ไม่มี rate limit ที่ MQTT | บอร์ดที่พังอาจส่งรัวจนฐานข้อมูลล้น | จำกัดจำนวนข้อความต่อวินาทีต่ออุปกรณ์ |
| ไม่มีตาราง command log | ตรวจสอบย้อนหลังไม่ได้ว่าใครสั่งเปิดปิดเมื่อไร | เพิ่มตารางบันทึกคำสั่งที่คนสั่งเอง |

`express-rate-limit` ใช้อยู่แล้วที่ฝั่ง HTTP โดยเฉพาะเส้นทางล็อกอินและ OTP
แต่ฝั่ง MQTT ยังไม่มี
