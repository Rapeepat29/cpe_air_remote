## เหตุการณ์ 1 · ติดตั้งบอร์ดแอร์ใหม่ (Provisioning)

**Provisioning** = กระบวนการทำให้บอร์ดใหม่ "รู้จัก" ระบบ: รู้ Wi-Fi, รู้ Broker, รู้ว่าเป็นแอร์ห้องไหน
และให้ระบบ "ยืนยัน" ว่าบอร์ดนี้เป็นของจริง

### ภาพรวม

```text
 แอดมิน+แอปมือถือ          Backend                 ฐานข้อมูล          Mosquitto          ESP32 ใหม่
      │                       │                       │                   │                   │
 (1)  │── สแกน BLE ────────────────────────────────────────────────────────────────────────────▶│ RMUTT-AC-XXXX
 (2)  │◀─ อ่าน Identity: deviceId, firmware, configured=false ───────────────────────────────────│
 (3)  │── อ่าน Nearby Wi-Fi ──────────────────────────────────────────────────────────────────▶│ สแกน Wi-Fi
      │◀─ [["RMUTT-WiFi",-42,true], ...] ──────────────────────────────────────────────────────│
 (4)  │ แอดมินเลือก Wi-Fi, ใส่รหัส, เลือกห้อง/หมายเลขแอร์/ยี่ห้อ                                     │
 (5)  │── POST /air-conditioners/reservations ─▶│                   │                   │
      │                       │── INSERT status='reserved', token_hash ─▶│               │
      │◀─ 201 {reservation:{mqttHost, mqttPort, mqttUsername, mqttPassword, mqttTopic,     │
      │         provisioningToken, expiresInSeconds:900, ...}} ─│                     │
 (6)  │── เขียน Config ทาง BLE (หั่นเป็นชิ้น): Wi-Fi + MQTT + ห้อง + ยี่ห้อ + token ─────────────▶│
      │                                                                                  (7) ทดสอบ Wi-Fi
      │◀─ notify ACK {ok:true} ────────────────────────────────────────────────────────────────│ บันทึก NVS, รีสตาร์ท
      │                       │                       │                   │           (8)  │ ต่อ Wi-Fi + MQTT
      │                       │                       │                   │◀── publish .../provision {token} (retain)
 (9)  │                       │◀──────────────────────────────────────────│               │
      │                       │ hash(token) ตรงกับที่เก็บไว้? และยังไม่หมดอายุ?              │
      │                       │── UPDATE status='active' ─▶│              │               │
(10)  │                       │── publish .../provision-ack {token} (retain) ─▶│──────────▶│ ลบ token จาก NVS
      │                       │── ล้าง token_hash, ล้าง retained .../provision ─▶│          │
(11)  │ แอปเห็นแอร์ขึ้นสถานะออนไลน์ (ดึงทุก 10 วินาที)                                            │
```

### ทำไมต้องมี token ครั้งเดียว
ถ้าไม่มี ใครก็ได้ที่รู้ topic สามารถ publish "ฉันคือ ESP32-XXXX" แล้วยึดช่องแอร์ได้
token สุ่ม 24 ไบต์ ใช้ได้ **15 นาที** Backend เก็บแค่ **hash** ของ token (เหมือนรหัสผ่าน)
และบอร์ดต้องพิสูจน์ด้วยการส่ง token ผ่าน MQTT = พิสูจน์ว่า **บอร์ดตัวนั้นต่อ Broker ได้จริง**

### ทำไมต้องจองก่อน (reservation)
- ตรวจก่อนเขียน BLE ว่าห้องมีอยู่, หมายเลขแอร์ยังว่าง, บอร์ดนี้ไม่ได้ลงทะเบียนห้องอื่น
  ถ้าชน ได้ **409** ตั้งแต่ก่อนแตะบอร์ด
- ค่า MQTT (host, user, pass) **มาจาก Backend** ไม่ต้องให้แอดมินพิมพ์ → ไม่มีวันพิมพ์ผิด

### โค้ดที่เกี่ยวข้อง
| ขั้น | ไฟล์ |
|---|---|
| 1–3, 6 | `lib/services/ble_provisioning_service.dart`, `lib/screens/ble_provisioning_screen.dart` |
| 5 | `backend/src/routes/air-conditioners.js` → `POST /reservations` |
| 6–8 | `firmware/.../rmutt_esp32_air.ino` → `ConfigCallbacks::onWrite`, `processPendingConfig`, `saveConfig`, `publishProvisioningToken` |
| 9–10 | `backend/src/services/mqtt.js` → `activateProvisioning()` |

### โหมด dynsec (เซิร์ฟเวอร์จริง)
ขั้นที่ 5 Backend ยังสร้าง **บัญชี MQTT เฉพาะบอร์ดนี้** (username = Device ID,
รหัสคำนวณจาก `MQTT_DEVICE_SECRET`) และ host เป็น `mqtts://<โดเมน>:8883`

### ตั้งค่าบอร์ดเดิมใหม่ (เปลี่ยน Wi-Fi / ย้าย Broker)
- บอร์ดออนไลน์อยู่: แอป → เมนูของแอร์ → **ตั้งค่าบอร์ด** → Backend ส่ง MQTT `command` ให้บอร์ดเปิด BLE 5 นาที
- บอร์ดออฟไลน์: กด **BOOT ค้าง + กด EN** ที่บอร์ด แล้วเลือก **ตั้งค่าใหม่ผ่านบลูทูธ** ในแอป
- ระบบบังคับว่า **Device ID เดิม + ห้อง/หมายเลขเดิม** เท่านั้น

บอร์ดตรวจคนทำเหมือนกันทุกขั้น แต่ใช้ `POST /api/occupancy-sensors/reservations`,
Device ID `OCC32-...`, BLE `RMUTT-OCC-...`, topic `rmutt/occupancy/...` และห้องหนึ่งมีได้ตัวเดียว

## เหตุการณ์ 2 · กดเปิดแอร์จากแอป

```text
[แอป] air_control_card.dart  กดปุ่ม Power
   ▼  AirConditionerController → AirConditionerService
[HTTP] POST /api/air-conditioners/ESP32-AABBCCDDEEFF/command
       Authorization: Bearer <JWT>
       {"power":true,"temperature":24,"mode":"cool","fanSpeed":"auto",...}
   ▼
[Backend] routes/air-conditioners.js
   authenticate ✔ → SELECT provision_status, protocol → ต้องเป็น 'active' (ไม่งั้น 409)
   validateAirState(body, protocol)  ← ตรวจค่า เช่นอุณหภูมิอยู่ในช่วง, ยี่ห้อ Saijo รองรับเฉพาะบางฟังก์ชัน
   publishAirCommand() → services/mqtt.js
   ◀── 202 {accepted:true, commandId}          (ถ้า MQTT ไม่ต่อ → 503)
   ▼
[MQTT] rmutt/ac/ESP32-AABBCCDDEEFF/command  QoS1
       {"version":1,"commandId":"<uuid>","sentAt":"...","state":{...}}
   ▼
[ESP32] mqttCallback() เก็บข้อความ → loop() → processMqttCommand()
        อัปเดต airState → saveAirState() (จำไว้ใน NVS)
        sendCurrentIrState() → irAc.sendAc()   💡 ยิง IR
        publishState(commandId) → rmutt/ac/.../state
   ▼
[Backend] handleIncomingMessage → type 'state' → UPDATE air_conditioners SET state_json=...
   ▼
[แอป] รอบดึงข้อมูลถัดไป (≤10 วินาที) แสดงสถานะใหม่
        ~ไม่กี่วินาทีต่อมา PZEM เห็นกำลังไฟ >50W 3 ครั้ง → acRunning = true → การ์ดขึ้น "กำลังทำงาน"
```

**จุดที่ต้องเข้าใจ**: 202 แปลว่า "ส่งคำสั่งแล้ว" ไม่ใช่ "แอร์เปิดแล้ว"
ความจริงว่าแอร์เปิดหรือไม่ มาจาก **PZEM วัดกำลังไฟ** ไม่ใช่จากการที่เราสั่ง
(IR ไม่มีการตอบกลับ ถ้ามีอะไรบังตัวรับ แอร์จะไม่รู้เรื่อง)

## เหตุการณ์ 3 · บันทึกค่าไฟรายชั่วโมง

```text
ESP32 ทุก 2 วินาที อ่าน PZEM
ESP32 ทุก 10 วินาที publish rmutt/ac/<id>/status (retain)
  {"online":true,"pzemAvailable":true,"acRunning":true,"outsideSchedule":false,
   "voltage":229.8,"current":2.145,"powerWatts":465.2,"energyKwh":12.345,
   "frequencyHz":50.0,"powerFactor":0.94, "historyPending":0}
   ▼
Backend handleAirStatus()   (ทำทีละข้อความต่อบอร์ด — runSerialForDevice กันลำดับสลับ)
   1. อ่านแถวเดิม (energy_kwh ครั้งก่อน, last_seen_at ครั้งก่อน)
   2. ถ้าบอร์ดไม่มีข้อมูลย้อนหลังค้าง → recordEnergySample()
        ผลต่าง kWh = ปัจจุบัน − ครั้งก่อน
           • ถ้าติดลบ (มิเตอร์รีเซ็ต/บูตใหม่) → 0
           • ถ้า > 50 kWh (ค่าเพี้ยน) → 0
        เวลาที่ผ่านไป (เกิน 300 วินาที = ขาดช่วง ไม่นับ)
        หาถังชั่วโมงตามเวลาไทย เช่น 2026-09-30 14:00:00
        INSERT ... ON DUPLICATE KEY UPDATE  energy_hourly
           consumption_kwh += ผลต่าง
           voltage_sum += V, voltage_min = LEAST(...), voltage_max = GREATEST(...)
           runtime_seconds += (ถ้าแอร์ทำงาน)
           sample_count += 1
   3. UPDATE air_conditioners SET voltage, power_watts, energy_kwh, ac_running, ... (ค่าล่าสุด)
   4. แจ้ง auto-off service ว่ามีข้อมูลใหม่ของบอร์ดนี้
   ▼
แอป/เว็บ  GET /api/energy/summary?period=week  → SUM(consumption_kwh) GROUP BY วัน → กราฟ
          GET /api/energy/export?...            → ไฟล์ .xlsx
```

ไฟล์: `services/energy-recorder.js`, `utils/energy-history.js` (`energyDelta`, `elapsedSeconds`,
`buildSampleDelta`, `bangkokHourStart`), `routes/energy.js`

**ข้อมูลช่วงเน็ตหลุด**: บอร์ดส่ง `historyPending > 0` ระหว่างที่ยังส่งข้อมูลเก่าไม่หมด
Backend จะ **ไม่บันทึกค่าสด** ช่วงนั้น (กันนับซ้ำ) แต่บันทึกจาก `.../history` แทน แล้วตอบ `history-ack`

## เหตุการณ์ 4 · ปิดแอร์อัตโนมัติเมื่อห้องว่าง

### เงื่อนไขครบ 5 ข้อจึงเริ่มนับ
1. สวิตช์รวม `system_settings.auto_off_enabled = true` **และ** สวิตช์ของแอร์เครื่องนั้น `auto_off_enabled = 1`
2. ห้องมีเซ็นเซอร์ที่ **ออนไลน์** และ **เรดาร์ใช้ได้** (ไม่มีเซ็นเซอร์ = ไม่รู้ว่ามีคน → **ไม่ปิดเด็ดขาด**)
3. PZEM อ่านค่าได้ (ไม่งั้นตรวจไม่ได้ว่าปิดสำเร็จไหม)
4. เซ็นเซอร์บอก **ไม่มีคน**
5. แอร์ **กำลังกินไฟ** (acRunning)

### เครื่องสถานะ (State machine) ของ `decideAutoOff()`

```text
                    ┌──────────┐
         ┌─────────▶│  idle    │◀──────────────── cancel (มีคนเข้ามา / เซ็นเซอร์ดับ /
         │          └────┬─────┘                   ปิดฟีเจอร์ / แอร์หยุดเองก่อนเราสั่ง)
         │               │ start: ห้องว่าง + แอร์ทำงาน
         │               │   deadline = ตอนนี้ + 300s (นอกคาบ) หรือ +900s (ในคาบเรียน)
         │               ▼
         │          ┌──────────┐
         │          │ counting │── wait (ยังไม่ถึง deadline) ──┐
         │          └────┬─────┘◀──────────────────────────────┘
         │               │ fire: ถึง deadline → ส่ง power:false ผ่าน MQTT (attempt 1)
         │               ▼
         │          ┌────────────┐
         │          │ commanding │── wait (ยังไม่ครบ 20s จากครั้งก่อน)
         │          └──┬──────┬──┘── fire (ครบ 20s แอร์ยังกินไฟ → attempt 2..5)
         │             │      │
         │  succeeded  │      │ giveUp: ยิงครบ 5 ครั้ง แอร์ยังทำงาน
         │ (ไฟตกลง)    │      ▼
         │             │  แจ้งเตือน auto_off_failed (status=open ต้องมีคนไปดู)
         │             ▼
         └── แจ้งเตือน auto_off_succeeded (status=resolved) แล้วล้างนาฬิกา
```

| ค่าคงที่ (`utils/auto-off.js`) | ค่า |
|---|---|
| `AUTO_OFF_IDLE_SECONDS` | 300 (5 นาที นอกคาบเรียน) |
| `AUTO_OFF_IN_CLASS_SECONDS` | 900 (15 นาที ระหว่างคาบ — เผื่อพักเบรก) |
| `AUTO_OFF_RETRY_SECONDS` | 20 |
| `AUTO_OFF_MAX_ATTEMPTS` | 5 |

### ใครเรียก `decideAutoOff()`
`services/auto-off.js` เรียก
- ทุก 10 วินาที (`setInterval`) — เผื่ออุปกรณ์เงียบไป
- ทันทีที่บอร์ดแอร์ส่ง status ใหม่
- ทันทีที่เซ็นเซอร์ในห้องส่ง status ใหม่

แล้วบันทึกผลลงคอลัมน์ `auto_off_started_at`, `auto_off_deadline_at`, `auto_off_attempts`,
`auto_off_last_attempt_at`, `auto_off_in_class` ของ `air_conditioners`
แอปอ่านคอลัมน์เหล่านี้ไปแสดง **นาฬิกานับถอยหลัง** (`lib/widgets/auto_off_countdown.dart`)

### ทำไมตรรกะอยู่ที่ Backend ไม่อยู่ในบอร์ด
เซ็นเซอร์ (OCC32) กับบอร์ดแอร์ (ESP32) เป็นคนละตัว **คุยกันเองไม่ได้**
Backend เป็นที่เดียวที่เห็นทั้งสองฝั่ง + ตารางเรียน + สวิตช์รวม

### ทำไม `decideAutoOff` เป็นฟังก์ชันบริสุทธิ์
รับข้อมูล → คืน "การตัดสินใจ" ไม่แตะฐานข้อมูล ไม่ส่ง MQTT
→ `test/auto-off.test.js` ทดสอบทุกกรณีได้โดยไม่ต้องมีแอร์จริง (ลองอ่านไฟล์นี้ เข้าใจกติกาเร็วที่สุด)

## เหตุการณ์ 5 · ตารางเรียน + ไฟแดงบนบอร์ด + แจ้งเตือนนอกเวลา

```text
แอดมินนำเข้าตารางเรียน (Excel/CSV) ในแอป/เว็บ
   → POST /api/schedules/import/preview   (อ่านไฟล์ แสดงตัวอย่าง ยังไม่บันทึก)
   → POST /api/schedules/import/commit    (บันทึกลง class_schedules)

เมื่อบอร์ดแอร์ส่ง status:
   Backend เช็กว่า "ตอนนี้ (เวลาไทย) ห้องนี้มีคาบเรียนไหม"  utils/class-schedule.js
   → publish rmutt/ac/<id>/schedule-status (retain)
        {"classScheduleConfigured":true,"withinClassSchedule":false,...}
   → บอร์ดใช้ค่านี้: แอร์ทำงาน + นอกคาบ → LED แดงติด (คู่กับเขียว)
     ถ้าไม่ได้ข้อมูลนี้ 2 นาที บอร์ดใช้ช่วงเวลาเปิด-ปิดประจำวันที่ตั้งตอน provisioning แทน

auto-off service เพิ่มเติม:
   แอร์ทำงาน + มีคน + ไม่มีคาบเรียน → แจ้งเตือน outside_schedule_occupied (status=open)
   เมื่อเงื่อนไขหมดไป → ปิดการแจ้งเตือนนั้นเอง (resolved)
```

ตัวอย่างไฟล์ตารางเรียน: `examples/rmutt_class_schedules_1-2569.csv`

## เหตุการณ์ 6 · ผู้ใช้ล็อกอิน → token หมดอายุ → เปลี่ยนสิทธิ์

```text
09:00  สมชาย ล็อกอิน → JWT {sub:"somchai", role:"staff", ver:3, exp:17:00}
09:05  แอปเก็บ token ใน Secure Storage, แนบทุกคำขอ
10:00  แอดมินเปลี่ยนสมชายเป็น admin → UPDATE users SET role='admin', token_version=4
10:00  คำขอถัดไปของสมชาย: authenticate เห็น ver 3 ≠ 4 → 401 "กรุณาเข้าสู่ระบบใหม่"
       แอป/เว็บ ล้าง token → เด้งหน้าล็อกอิน
10:01  สมชายล็อกอินใหม่ → ได้ token role:"admin", ver:4 → เห็นเมนูแอดมิน
17:00  (ถ้าไม่มีอะไรเกิดขึ้น) token หมดอายุ → 401 → ล็อกอินใหม่
```

กติกาที่ Backend บังคับ (แอปข้ามไม่ได้)
- แก้สิทธิ์/ระงับ/ลบ **บัญชีตัวเอง** ไม่ได้
- ต้องเหลือ admin ที่ active **อย่างน้อย 1 คน** เสมอ (ตรวจใน transaction + `SELECT ... FOR UPDATE`)

## สรุป: ใครรู้อะไร

| ข้อมูล | อยู่ที่ไหน | ใครเป็นเจ้าของความจริง |
|---|---|---|
| รหัสผ่านผู้ใช้ | `users.password_hash` | Backend |
| Wi-Fi ของบอร์ด | NVS ของบอร์ด | บอร์ด (Backend ไม่รู้รหัส Wi-Fi) |
| ที่อยู่ Broker ของบอร์ด | NVS ของบอร์ด (ได้จาก Backend ตอน provisioning) | Backend กำหนด |
| สถานะรีโมต (อุณหภูมิ ฯลฯ) | NVS ของบอร์ด + `state_json` | บอร์ด |
| แอร์ทำงานจริงไหม | PZEM → `ac_running` | บอร์ด (วัดจริง) |
| มีคนไหม | LD2410 → `is_occupied` | บอร์ดตรวจคน |
| ค่าไฟย้อนหลัง | `energy_hourly` | Backend |
| จะปิดแอร์ไหม | `decideAutoOff()` | Backend |
| คาบเรียน | `class_schedules` | Backend |
