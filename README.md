# RMUTT Save Energy

แอป Flutter และเว็บแอปสำหรับควบคุมเครื่องปรับอากาศในอาคาร 16 พร้อมระบบเข้าสู่ระบบ
Backend API, MariaDB, การเปลี่ยนรหัสผ่านด้วย OTP 6 หลักทางอีเมล และหน้า
จัดการสิทธิ์ผู้ใช้สำหรับ Admin

แอปมือถือกับเว็บแอปใช้ฐานข้อมูลและ API ชุดเดียวกัน ต่างกันที่หน้าที่:
มือถือใช้ตั้งค่าบอร์ดผ่าน Bluetooth และพกไปหน้างานได้ ส่วนเว็บใช้ดูข้อมูล
ละเอียดบนจอกว้างและจัดการข้อมูลจำนวนมาก เปิดที่ <https://rmutt-energy.duckdns.org/>

> **ใช้งานจริงบนเซิร์ฟเวอร์ของมหาวิทยาลัย:** ดูขั้นตอนที่ `deploy/DEPLOY.md`
> และสเปกเครื่องที่ต้องขอที่ `deploy/SERVER_REQUIREMENTS.md`

## ฟังก์ชันในโปรเจกต์

### ระบบบัญชี

- หน้าเข้าสู่ระบบโทนสีเขียว `RMUTT Save Energy`
- ใช้ Username และ Password
- เก็บ Access Token ใน Secure Storage ของอุปกรณ์
- มีตัวเลือก “จดจำรหัสผ่าน” เพื่อกรอก Username และ Password ให้อัตโนมัติ
  ในการเข้าสู่ระบบครั้งถัดไป โดยเก็บไว้ใน Secure Storage และควรเปิดใช้เฉพาะ
  เครื่องส่วนตัว
- เมื่อตั้งรหัสผ่านใหม่ผ่าน OTP ระบบจะลบรหัสผ่านเดิมที่เคยจดจำไว้โดยอัตโนมัติ
- ลืมรหัสผ่านด้วยลำดับ:
  1. กรอก Username หรือ Email
  2. รับ OTP 6 หลักจากอีเมลในฐานข้อมูล
  3. กรอก OTP ภายใน 10 นาที
  4. ตั้งรหัสผ่านใหม่
- ปุ่มติดต่อแอดมินดึงชื่อและเบอร์จากผู้ใช้ที่มี `role = 'admin'`
- หน้าโปรไฟล์แสดงข้อมูลผู้ใช้จริงและมีปุ่มออกจากระบบ

### จัดการสิทธิ์ผู้ใช้ (เฉพาะ Admin)

- เปิดหน้า `จัดการสิทธิ์ผู้ใช้` จากแท็บ Profile หัวข้อ `การจัดการระบบ`
  เมนูนี้แสดงเฉพาะบัญชีที่มี `role = 'admin'`
- ดูรายชื่อผู้ใช้ทั้งหมดพร้อมสิทธิ์ สถานะบัญชี และเวลาเข้าสู่ระบบล่าสุด
- สลับสิทธิ์ระหว่าง `Administrator` และ `Staff` ได้จากในแอป ไม่ต้องแก้ค่า
  ในตาราง `users` ด้วย SQL อีกต่อไป
- ระงับบัญชี (`is_active = 0`) หรือเปิดใช้งานใหม่ได้ โดยข้อมูลเดิมยังอยู่ครบ
  บัญชีที่ถูกระงับจะเข้าสู่ระบบไม่ได้
- เพิ่มบัญชีใหม่พร้อมตั้งรหัสผ่านเริ่มต้น (bcrypt cost 12) และเลือกสิทธิ์
- ลบบัญชีถาวรได้ พร้อมกล่องยืนยันที่แนะนำให้ใช้การระงับบัญชีแทนถ้าอยากเก็บ
  ประวัติไว้
- ทุกครั้งที่เปลี่ยนสิทธิ์หรือระงับบัญชี Backend จะบวก `token_version`
  ทำให้ Token เดิมของผู้ใช้คนนั้นใช้ไม่ได้ทันทีและต้องเข้าสู่ระบบใหม่
- กติกาที่ Backend บังคับเสมอ แอปข้ามไม่ได้:
  - แก้สิทธิ์ ระงับ หรือลบบัญชีของตัวเองไม่ได้
  - ต้องเหลือ Admin ที่ `is_active = 1` อย่างน้อยหนึ่งบัญชีเสมอ โดยตรวจ
    ภายใน Transaction ด้วย `SELECT ... FOR UPDATE` กันกรณีกดพร้อมกันสองเครื่อง

| Method | Path | ใช้ทำอะไร |
|---|---|---|
| `GET` | `/api/users` | รายชื่อผู้ใช้ทั้งหมด + สิทธิ์ + สถานะ |
| `POST` | `/api/users` | สร้างบัญชีใหม่ |
| `PATCH` | `/api/users/:username` | เปลี่ยน `role` และ/หรือ `isActive` |
| `DELETE` | `/api/users/:username` | ลบบัญชีถาวร |

ทุกเส้นทางต้องแนบ Bearer Token ของบัญชี Admin และไม่มี API ใดคืนค่า
`password_hash` ออกไป

### ระบบควบคุมแอร์ผ่าน ESP32

- มีห้องมาตรฐาน `16101` ถึง `16307` และ Admin จัดการห้องเพิ่มเติมได้
- รองรับห้องพิเศษที่เป็นตัวอักษร เช่น `CL503`
- เพิ่มแอร์ได้สูงสุด 6 เครื่องต่อห้อง
- Admin ค้นหาและคอนฟิก ESP32 ผ่าน Bluetooth จากแอป
- กดสแกนในช่อง Wi-Fi เพื่อดู SSID ที่ ESP32 ตรวจพบ ณ ตำแหน่งติดตั้ง
- ตรวจ Device ID และตำแหน่งห้อง/หมายเลขแอร์ซ้ำกับ MariaDB ก่อนเขียนค่า
- บันทึก Wi-Fi, MQTT, โปรโตคอล IR และเวลาเปิด–ปิดใน NVS ของ ESP32
- ตั้งค่า ESP32 ตัวเดิมใหม่ผ่าน Bluetooth ได้ โดยไม่สร้างอุปกรณ์ซ้ำ
- หลังคอนฟิก แอปส่งคำสั่งผ่าน Backend และ MQTT ไปยัง ESP32
- เปิด/ปิด ปรับอุณหภูมิ 16–30 °C (Saijo Denki ใช้ช่วงที่จับได้ 18–29 °C)
- Mode, Fan, Swing, Eco, Turbo, Sleep, Quiet, Display, Clean และ Timer
- ESP32 ส่งสถานะที่ใช้งานจริงและสถานะ Online กลับผ่าน MQTT
- หน้าห้องดึงค่าใหม่ทันทีที่เปิดห้อง จากนั้นรีเฟรชเองทุก 10 วินาที และปุ่ม
  รีเฟรชมุมขวาบนบังคับดึงข้อมูลชุดใหม่เสมอ แม้รอบอัตโนมัติกำลังทำงานอยู่
  (จะรอรอบนั้นจบแล้วดึงซ้ำให้) ค่าที่อัปเดตจะขึ้นทันทีโดยไม่ต้องออกจากห้อง
- Firmware ใช้ `IRremoteESP8266` ผ่าน Common A/C interface (`IRac`) และมี
  ไดรเวอร์ `SAIJO_DENKI` ที่รวมอยู่ในโฟลเดอร์สเก็ตช์
- เลือกโปรโตคอลของ Daikin, Mitsubishi, Panasonic, Gree, Midea, LG, Samsung,
  Toshiba, Hitachi, Fujitsu, Kelvinator, Sharp, Electra, Haier และ Saijo Denki
  ได้ในแอป
- หน้าควบคุมแอร์แสดงค่าที่วัดจาก PZEM และสถานะทำงานจริง ส่วนสรุป Dashboard
  และสถิติย้อนหลังบางส่วนยังเป็นข้อมูลตัวอย่างจนกว่าจะเพิ่มระบบเก็บประวัติ

### เงื่อนไขที่บอร์ดเปิดบลูทูธให้ตั้งค่าใหม่

ใช้เหมือนกันทั้ง ESP32 ของแอร์ และ ESP32 + LD2410 มีทั้งหมด 5 ทาง:

| เงื่อนไข | เกิดขึ้นเมื่อ |
|---|---|
| ยังไม่เคยตั้งค่า | บูตครั้งแรกหรือหลังล้าง NVS |
| กดปุ่ม BOOT ค้างขณะกด RESET | ต้องการตั้งค่าใหม่ด้วยมือ |
| ต่อ Wi-Fi ที่บันทึกไว้ไม่ได้ตอนบูต | รอครบ `WIFI_TIMEOUT_MS` = 20 วินาที |
| Wi-Fi หลุดระหว่างใช้งานแล้วต่อกลับไม่ได้ | ตรวจทุกรอบของ `loop()` |
| แอปสั่ง `enter_setup` ผ่าน MQTT | เปิด BLE ให้ 5 นาที (`ONLINE_SETUP_WINDOW_MS`) |

สามข้อกลาง ๆ เข้าโหมด BLE recovery คือหยุดงานปกติทั้งหมดแล้วรอรับค่าใหม่
เมื่อบันทึกสำเร็จบอร์ดจะรีสตาร์ตเองภายใน 1.5 วินาที

**เฉพาะกรณีที่เปิด BLE เพราะ Wi-Fi** (Firmware แอร์ 2.1.0 / เซ็นเซอร์ 1.1.0)
บอร์ดจะแอบลองต่อ Wi-Fi เดิมซ้ำทุก 30 วินาที (`WIFI_RECOVERY_RETRY_MS`)
ระหว่างที่ BLE ยังเปิดอยู่ ถ้าเครือข่ายกลับมาเอง เช่นเราเตอร์รีบูตเสร็จ
บอร์ดจะออกจากโหมดตั้งค่า ปิดการกระจายสัญญาณบลูทูธ ต่อ MQTT แล้วทำงานต่อทันที
โดยไม่ต้องเดินไปกดปุ่มที่ตัวบอร์ด

- การลองแต่ละครั้งรอไม่เกิน 8 วินาที (`WIFI_RECOVERY_ATTEMPT_MS`) แทนที่จะเป็น
  20 วินาทีแบบตอนบูต บอร์ดจึงไม่ค้างนาน
- ไม่ลองต่อขณะที่มีมือถือหรือคอมเชื่อม BLE อยู่ และถ้ามีคนต่อเข้ามาระหว่างลอง
  บอร์ดจะไม่ปิด BLE ทิ้งกลางคัน แต่รอไปลองใหม่รอบหน้า
- บอร์ดที่เปิด BLE เพราะกดปุ่ม BOOT หรือยังไม่เคยตั้งค่า จะไม่ลองต่อ Wi-Fi เอง
  แต่รอให้ตั้งค่าจากแอปตามปกติ

ส่วน MQTT ใช้กติกาต่างออกไป คือ **ไม่เปิดบลูทูธ** แต่จะลองต่อ Broker ใหม่ทุก
3 วินาทีไปเรื่อย ๆ เพราะ Broker ควรอยู่ในเครือข่ายเดียวกันและกลับมาเองได้
ถ้า IP ของเครื่องที่รัน Broker เปลี่ยน ให้รัน `run_all.ps1` เพื่ออัปเดต
`backend/.env` แล้วตั้งค่าบอร์ดผ่านบลูทูธใหม่หนึ่งรอบ (กด BOOT ค้าง + RESET)

### ระบบตรวจคนภายในห้อง

- ใช้ ESP32 + HLK-LD2410 แยกหนึ่งชุดต่อห้อง ไม่ใช้บอร์ดเดียวกับตัวควบคุมแอร์
- โมดูล LD2410C มี 5 ขา (`VCC`, `GND`, `TX`, `RX`, `OUT`) ระบบใช้แค่ 4 ขาแรก
  ส่วนขา `OUT` ซึ่งเป็นผลตรวจจับที่โมดูลตัดสินเองตามค่าโรงงาน ไม่ได้ใช้และ
  ปล่อยลอยไว้ได้ เพราะระบบตัดสินจากค่าพลังงานรายเกตที่อ่านผ่าน UART แทน
- Admin เพิ่ม ตั้งค่าใหม่ หรือนำเซ็นเซอร์ออกจากหน้าห้องผ่าน Bluetooth ได้
- Firmware ใช้เฉพาะค่า Static/Stationary target ใน Engineering mode เกต 0–8
- ถ้ามีเกตใดเกตหนึ่ง `> 25` ห้องจะเป็น “มีคน”; ทุกเกต `<= 25` คือ “ไม่มีคน”
- ไม่ใช้และไม่ส่งค่า Moving target, ระยะ หรือค่าอื่นของ LD2410 ไปยังแอป
- แอปแยก “ไม่มีคน” ออกจาก “เซ็นเซอร์ออฟไลน์/LD2410 ใช้งานไม่ได้”
- สถานะ “เรดาร์พร้อมใช้งาน” ตัดสินจากเวลาที่ได้รับเฟรมล่าสุด (ภายใน 3 วินาที)
  ไม่ใช่จากธงของไลบรารีที่คืนค่า true ครั้งเดียวต่อเฟรม จึงไม่กระพริบไปมา
  ระหว่าง “มีคน” กับ “เซ็นเซอร์ไม่พร้อมใช้งาน” อีก (Firmware 1.1.3)
- ถ้าเริ่มต้น LD2410 ไม่สำเร็จตอนบูต (ขึ้น `LD2410 not detected` ใน Serial)
  Firmware 1.1.1 จะลองเริ่มต้นใหม่ทุก 10 วินาที แก้สายแล้วใช้งานต่อได้เลย
  ไม่ต้องรีบูตบอร์ด และ `connectMqtt()` พิมพ์ปลายทางกับรหัสข้อผิดพลาดออกมา
  ทุกครั้ง จึงดูได้จาก Serial ว่าบอร์ดถูกตั้งให้ไปหา Broker ที่ IP ใด
- Firmware 1.1.2 พิมพ์บล็อก `[diag]` ทุก 10 วินาที รวมค่าที่มักเป็นต้นเหตุ
  ปัญหาไว้ในที่เดียว: สถานะ Wi-Fi/IP/RSSI, สถานะ MQTT พร้อมรหัส state และ
  IP ปลายทางที่จำไว้ใน NVS, ห้องกับ topic ที่ตั้งไว้, เงื่อนไขของ
  `radarAvailable` แยกทีละตัว, จำนวนไบต์ดิบที่เข้ามาทางขา RX ของเรดาร์
  (0 = สายผิดหรือไม่มีไฟ, มากกว่า 0 แต่อ่านไม่ออก = baud ไม่ใช่ 256000)
  ค่าพลังงานรายเกต 0–8 พร้อมผลตัดสิน และ JSON ที่ส่งขึ้น MQTT จริง
  รายละเอียดวิธีอ่านอยู่ใน `firmware/README.md`
- เซ็นเซอร์ถูกจำไว้ในตาราง `occupancy_sensors` แบบเดียวกับที่แอร์ถูกจำไว้ใน
  `air_conditioners` คือหนึ่งแถวต่อหนึ่งอุปกรณ์ พร้อม `provision_status`,
  `mqtt_topic`, `is_online`, `radar_available`, `is_occupied` และ
  `last_seen_at` ข้อมูลอยู่ถาวรจนกว่าจะกดนำออกจากแอป
- อุปกรณ์ที่เพิ่งเพิ่มจะเป็น `reserved` จนกว่า ESP32 จะยืนยันตัวเองผ่าน MQTT
  แล้วเปลี่ยนเป็น `active` ระหว่างนั้นการ์ดในหน้าห้องจะขึ้นว่า
  “เซ็นเซอร์ตรวจจับคนยังไม่พร้อมใช้งาน” แทนที่จะหายไปจากหน้าจอ
- ตรวจรายการเซ็นเซอร์ทั้งหมดได้จาก `GET /api/occupancy-sensors`
  (ต้องแนบ Bearer Token, ใช้ได้ทั้ง Admin และ Staff)

| Method | Path | ใช้ทำอะไร |
|---|---|---|
| `GET` | `/api/occupancy-sensors` | รายการเซ็นเซอร์ทั้งหมด + สถานะ |
| `POST` | `/api/occupancy-sensors/reservations` | จองสิทธิ์ก่อนคอนฟิกผ่าน Bluetooth |
| `POST` | `/api/occupancy-sensors/:deviceId/setup-mode` | สั่งบอร์ดเข้า Setup Mode |
| `DELETE` | `/api/occupancy-sensors/:deviceId` | นำเซ็นเซอร์ออกจากห้อง |

การกด “นำออก” ในแอปจะลบแถวออกจากตารางจริง (hard delete) แล้วล้างข้อความ
retain บน Broker ทุก topic ของอุปกรณ์นั้น (`command`, `status`, `provision`,
`provision-ack`) เพื่อไม่ให้ข้อความเก่าย้อนกลับมาเมื่อเพิ่มอุปกรณ์รหัสเดิมอีกครั้ง
เครื่องปรับอากาศใช้กติกาเดียวกัน แต่ล้าง `state` และ `schedule-status` เพิ่มด้วย

ทั้งสอง API ตอบกลับเป็น JSON เพื่อให้ตรวจสอบได้ว่าลบไปกี่แถวจริง ๆ และการกดลบซ้ำ
ถือว่าสำเร็จ (ไม่ตอบ 404) เพื่อไม่ให้แอปค้างกับอุปกรณ์ที่หายไปจากฐานข้อมูลแล้ว:

```json
{ "removed": true, "deviceId": "OCC32-…", "deletedRows": 1,
  "retainedTopicsCleared": 4 }
```

หน้าต่าง Backend จะพิมพ์บรรทัดสรุปทุกครั้งที่มีการลบ ใช้ยืนยันได้ทันทีว่าคำสั่ง
มาถึง Backend จริงและลบไปกี่แถว:

```text
[occupancy] ลบ OCC32-AABBCCDDEEFF โดย admin: deletedRows=1 retainedTopicsCleared=4
```

ถ้า `deletedRows=1` แต่ยังเห็นข้อมูลในโปรแกรมจัดการฐานข้อมูล ให้กด Refresh
ผลลัพธ์ (DBeaver = F5) เพราะตารางที่เปิดค้างไว้จะแสดงผลชุดเดิมจนกว่าจะสั่งอ่านใหม่

### ตารางเรียนแต่ละห้อง

- ปุ่มปฏิทินมุมขวาบนของหน้า `Room Schedule` สำหรับ Admin
- เลือกชั้น ห้อง และวันในสัปดาห์ได้
- เพิ่มชื่อวิชา กลุ่มเรียน ชื่ออาจารย์ เวลาเริ่ม และเวลาเลิก
- แก้ไขหรือลบรายการเดิมได้
- ป้องกันการเพิ่มช่วงเวลาที่ซ้อนกันภายในห้องและวันเดียวกัน
- บันทึกตารางใน MariaDB ผ่าน Backend API เพื่อให้ทุกบัญชีเห็นข้อมูลตรงกัน
- Staff ดูตารางได้ แต่มีเฉพาะ Admin ที่เพิ่ม แก้ไข หรือลบได้
- Admin ล้างตารางเรียนทุกห้องพร้อมกันได้ โดยระบบจะแสดงจำนวนรายการและขอ
  ยืนยันก่อนลบ ห้อง แอร์ ผู้ใช้ และการตั้งค่าอื่นจะไม่ถูกลบ
- Admin เพิ่ม แก้รายละเอียด และลบห้องว่างจากหน้า `Control` ได้

### Application Settings

- เลือกภาษาได้ระหว่าง `ภาษาไทย` และ `English`
- ค่าเริ่มต้นเป็นภาษาไทย และเปลี่ยนข้อความทั้งแอปทันที
- จดจำภาษาที่เลือกด้วย Secure Storage หลังปิดและเปิดแอปใหม่
- เปิดหน้า `Application Settings` จากแท็บ Profile
- เปิดและปิด Dark Mode ได้ทันทีทั้งแอป
- จดจำค่า Dark Mode ด้วย Secure Storage หลังปิดและเปิดแอปใหม่
- ภาษาและ Dark Mode บันทึกแยกจากกัน
- ข้อความในแอปผ่านตารางคำแปลทั้งหมด 501 คำ ครอบคลุมทั้งหน้าจอ ปุ่ม กล่องยืนยัน
  และ SnackBar แจ้งเตือน เมื่อเลือกภาษาไทยจะไม่มีข้อความอังกฤษหลงเหลือ ยกเว้น
  ชื่อยี่ห้อแอร์ ชื่อหน่วย (kWh, dBm) และตัวเลือกภาษา `English` ที่คงไว้ตามเดิม
- ข้อความที่มีตัวแปรปนอยู่ เช่น `ห้อง 16101` หรือ `3 เครื่อง` แยกคำที่ต้องแปล
  ออกจากตัวแปรด้วย `context.tr()` จึงแปลได้ครบโดยตัวเลขยังถูกต้อง
- ยังไม่รวมการตั้งค่า Notifications ในเวอร์ชันนี้

### อัตราค่าไฟฟ้า

- เปิดหน้า `Electricity Rate` จากแท็บ Profile
- กำหนดอัตราค่าไฟได้ตั้งแต่ `0.01` ถึง `100.00` บาทต่อ kWh
- ค่าเริ่มต้นคือ `4.50 บาท/kWh` ซึ่งตรงกับตัวเลข Mock เดิม
- แสดงตัวอย่างการคำนวณก่อนบันทึกด้วยสูตร
  `ค่าไฟ = พลังงาน (kWh) × อัตราค่าไฟฟ้า`
- บันทึกอัตราที่เลือกด้วย Secure Storage หลังปิดและเปิดแอปใหม่
- ตัวเลขค่าไฟในหน้า Home และ Analytics เปลี่ยนตามอัตราที่บันทึกทันที
- ตั้งแต่ v3.13.0 อัตราค่าไฟถูกเก็บไว้ที่เซิร์ฟเวอร์ด้วย (`system_settings`
  คีย์ `electricity_rate`) และแก้ได้จากหน้า `อัตราค่าไฟ` บนเว็บแอป
  เฉพาะแอดมิน เพื่อให้ตัวเลขค่าใช้จ่ายที่ทุกคนเห็นตรงกัน
  เส้นทาง `GET /api/settings` และ `PATCH /api/settings/rate`

### ปิดแอร์อัตโนมัติเมื่อห้องว่าง

เซ็นเซอร์ตรวจคน (OCC32) กับบอร์ดแอร์ (ESP32) เป็นคนละตัวและคุยกันเองไม่ได้
Backend จึงเป็นคนคุมจังหวะทั้งหมด เพราะเป็นที่เดียวที่เห็นทั้งสองฝั่ง

**ลำดับการทำงาน**

1. แอร์กินไฟอยู่ + ห้องว่าง → เริ่มนับถอยหลัง
   - นอกคาบเรียน **5 นาที**
   - ระหว่างมีคาบเรียนในตาราง **15 นาที** เผื่อพักเบรกแล้วกลับเข้ามา
2. ครบเวลาแล้วห้องยังว่าง → ส่งคำสั่งผ่าน MQTT ให้บอร์ดยิง IR ปิดแอร์
3. อ่านค่าจาก PZEM ต่อ ถ้ายังกินไฟอยู่จะยิงซ้ำ **ทุก 20 วินาที สูงสุด 5 ครั้ง**
4. กำลังไฟตกลงจนเฟิร์มแวร์ถือว่าแอร์หยุด → หยุดยิงและแจ้งเตือนว่าปิดสำเร็จ
5. **มีคนเข้ามาเมื่อไหร่ก็ยกเลิกทันที** ไม่ว่าจะอยู่ขั้นไหน

**กติกากันพลาด**

- ห้องที่ยังไม่มีเซ็นเซอร์ตรวจคน หรือเซ็นเซอร์ออฟไลน์/เรดาร์ไม่ตอบ
  **จะไม่ถูกปิดอัตโนมัติเลย** เพราะระบบไม่รู้ว่ามีคนอยู่หรือไม่
- ถ้า PZEM อ่านค่าไม่ได้ ก็ไม่ปิดเช่นกัน เพราะตรวจไม่ได้ว่าแอร์หยุดจริงหรือยัง
- ยิงครบ 5 ครั้งแล้วแอร์ยังทำงาน ระบบจะเลิกยิงแล้วแจ้งเตือนให้คนไปดูแทน
- ปิดฟีเจอร์นี้รายเครื่องได้ด้วย `PATCH /api/air-conditioners/:deviceId`
  พร้อม `{"autoOffEnabled": false}` เผื่อห้องที่ต้องเปิดแอร์ค้างไว้

**นาฬิกาที่เห็นในแอป** — เวลาที่เหลือขึ้นทั้งในการ์ดรายการห้อง (แบบย่อ)
และในหน้าควบคุมห้อง (แบบเต็มพร้อมคำอธิบาย) Backend ส่งมาแค่ `เวลาที่จะสั่งปิด`
แอปเดินนาฬิกาเองทุกวินาที จึงเห็นตัวเลขลดลงต่อเนื่องโดยไม่ต้องยิงคำขอถี่ ๆ

### การแจ้งเตือนของระบบ

ตอนนี้มี 2 กติกาตามที่ตกลงกันไว้

1. **ไม่มีคาบเรียนในตาราง + แอร์ทำงานอยู่ + มีคนอยู่ในห้อง**
   ขึ้นเป็นใบสีส้มสถานะ `รอดำเนินการ` กดปุ่ม `รับทราบแล้ว` เพื่อปิดใบได้
   ถ้าเงื่อนไขหมดไปเอง (ปิดแอร์ หรือคนออกจากห้อง) ระบบจะปิดใบให้เอง
2. **ระบบปิดแอร์อัตโนมัติสำเร็จ** ขึ้นเป็นใบสีเขียวไว้เป็นบันทึกเหตุการณ์

มีใบที่สามเพิ่มมาเองคือ `สั่งปิดแอร์ไม่สำเร็จ` เมื่อยิงครบ 5 ครั้งแล้วไม่ได้ผล

การแจ้งเตือนเก็บในตาราง `system_alerts` เป็น **รหัสชนิด ไม่ใช่ข้อความสำเร็จรูป**
แอปจึงแปลเป็นไทย/อังกฤษเองได้ และแก้ถ้อยคำภายหลังโดยไม่ต้องแตะข้อมูลเก่า

### หน้าหลักและหน้าสถิติใช้ข้อมูลจริงแล้ว

- ตัวเลข kWh ค่าไฟ กราฟ และรายการแยกตามห้อง ดึงจาก `GET /api/energy/summary`
  ซึ่งอ่านจากตาราง `energy_hourly` ไม่ใช่ตัวเลขตัวอย่างที่ฝังไว้ในโค้ดอีกต่อไป
- มี **Dropdown เลือกช่วงเวลา** ทั้งสองหน้า: `วันนี้` / `7 วันล่าสุด` /
  `30 วันล่าสุด` / `กำหนดช่วงเอง` (เปิดปฏิทินเลือกวันเริ่ม–วันจบในหน้าจอเดียว)
- เลือก `วันนี้` กราฟจะเป็นรายชั่วโมง 24 จุด ช่วงยาวกว่านั้นเป็นรายวัน
- ป้ายเพิ่มขึ้น/ลดลงเทียบกับช่วงก่อนหน้าที่ยาวเท่ากันโดยอัตโนมัติ
  ถ้าช่วงก่อนหน้ายังไม่มีข้อมูลจะขึ้นว่า `ยังไม่มีข้อมูลช่วงก่อนหน้าให้เทียบ`
- หน้าสถิติกรองตามชั้นได้ รวมทั้งตัวเลือก `ทุกชั้น`

### ตั้งค่าบัญชีผู้ใช้

เปิดจากแท็บ Profile หัวข้อ `บัญชีและการตั้งค่า` เมนู `ตั้งค่าบัญชีผู้ใช้`

- แก้ชื่อ นามสกุล อีเมล และเบอร์โทรของตัวเองได้ (`PATCH /api/auth/me`)
- เปลี่ยนรหัสผ่านโดยยืนยันด้วยรหัสเดิม (`POST /api/auth/me/password`)
  ต่างจากการรีเซ็ตผ่าน OTP ตรงที่ไม่ต้องรออีเมล
- เปลี่ยนรหัสผ่านสำเร็จจะบวก `token_version` ทำให้ทุกเครื่องที่ค้างอยู่
  ต้องเข้าสู่ระบบใหม่ รวมถึงเครื่องที่กดเปลี่ยนเอง แอปจึงพากลับหน้าเข้าสู่ระบบ
- **Username กับสิทธิ์ (admin/staff) แก้ที่นี่ไม่ได้โดยตั้งใจ**
  ต้องให้ผู้ดูแลระบบแก้จากหน้า `จัดการสิทธิ์ผู้ใช้` เท่านั้น

### ฐานข้อมูลค่าไฟและส่งออก Excel

เปิดจากแท็บ Profile หัวข้อ `การจัดการระบบ` เมนู `ฐานข้อมูล` หน้าจอแบ่งเป็นสองแท็บ

**แท็บ `ค่าไฟสด`**

- แสดงค่าที่ PZEM-004T v3.0 ส่งเข้ามาแบบต่อเนื่อง โมดูลนี้ให้ค่าพื้นฐาน 6 ค่า
  คือ แรงดัน (V) กระแส (A) กำลังไฟจริง (W) พลังงานสะสม (kWh) ความถี่ (Hz)
  และตัวประกอบกำลัง (PF)
- เลือกรอบอัปเดตได้ระหว่าง 2, 5, 10, 30 และ 60 วินาที ค่าเริ่มต้นคือ 5 วินาที
  ซึ่งเห็นการเปลี่ยนแปลงเกือบทันทีโดยไม่ยิงคำขอถี่เกินจำเป็น
- ปุ่ม `หยุดชั่วคราว` ปิดรอบอัตโนมัติไว้ก่อนได้ เช่น ตอนกำลังอ่านค่าอยู่
- การ์ดด้านบนสรุปกำลังไฟรวมของเครื่องที่ทำงานอยู่ พร้อมค่าไฟต่อชั่วโมงโดยประมาณ
  ตามอัตราที่ตั้งไว้ในหน้า `อัตราค่าไฟฟ้า`

**แท็บ `ส่งออกเป็น Excel`**

1. เลือกช่วงวัน จะเอาวันเดียวหรือตั้งแต่วันไหนถึงวันไหนก็ได้ (สูงสุด 366 วัน)
2. เลือกระดับรายละเอียด
   - `ทั้งอาคาร` หนึ่งแถวต่อหนึ่งชั่วโมง รวมแอร์ทุกเครื่อง ตรงกับไฟล์ตัวอย่าง
     ที่มีคอลัมน์ `data`, `time`, `พลังงานที่ใช้/kWh`
   - `แยกตามห้อง` และ `แยกตามเครื่องแอร์` คือ **โหมดรายละเอียดสูง**
     เลือกเฉพาะห้องหรือเฉพาะเครื่องที่ต้องการได้ และปลดล็อกคอลัมน์เพิ่ม
     เช่น ค่าต่ำสุด ค่าสูงสุด เวลาที่แอร์ทำงาน และจำนวนครั้งที่บันทึก
   - ถ้าไม่ติ๊กห้องหรือเครื่องไหนเลย ระบบจะเอาทั้งหมดในระดับนั้น
3. ติ๊กค่าที่ต้องการ และเปิดสวิตช์ `เพิ่มคอลัมน์ค่าไฟโดยประมาณ` ได้ถ้าอยากได้
   ยอดเงินคำนวณจากอัตราค่าไฟที่ตั้งไว้
4. กด `ดูตัวอย่าง` เพื่อเห็นตารางบนหน้าจอก่อน (แสดง 50 แถวแรก) แล้วกด
   `ดาวน์โหลด Excel`
   - บน Windows จะเปิดกล่อง `บันทึกเป็น` ให้เลือกโฟลเดอร์เอง
   - บน Android จะเปิดเมนูแชร์ เลือกเก็บลง Files ส่งไลน์ หรือส่งอีเมลก็ได้

**วิธีที่ข้อมูลถูกเก็บ**

- ทุกครั้งที่ ESP32 ส่งข้อความ `status` เข้ามา Backend จะอ่านค่าเดิมใน
  `air_conditioners` ก่อน แล้วบวกส่วนต่างเข้าไปในแถวของชั่วโมงนั้นในตาราง
  `energy_hourly` (หนึ่งแถวคือหนึ่งเครื่องต่อหนึ่งชั่วโมงตามเวลาไทย)
- เก็บเป็นผลรวมกับตัวนับ ไม่ได้เก็บทุกตัวอย่างดิบ ฐานข้อมูลจึงไม่บวมแม้ส่งถี่
  ค่าเฉลี่ยคำนวณตอนดึงรายงาน (`ผลรวม ÷ จำนวนครั้ง`)
- พลังงานที่ใช้ในชั่วโมงนั้นคิดจากผลต่างของเลขมิเตอร์สะสม ถ้าค่าลดลงแปลว่า
  บอร์ดรีเซ็ตหรือเพิ่งบูตใหม่ ระบบจะนับรอบนั้นเป็น 0 ไม่เดาย้อนหลัง
- ถ้าอุปกรณ์เงียบเกิน 5 นาที ช่วงที่หายไปจะไม่ถูกนับเป็นเวลาทำงาน
- ประวัติยังอยู่แม้จะนำอุปกรณ์ออกจากระบบไปแล้ว เครื่องที่ถูกนำออกจะขึ้นป้าย
  `นำออกแล้ว` ในรายการให้เลือก

**API ที่เกี่ยวข้อง** (ต้องแนบ Bearer token ทุกเส้น)

| Endpoint | หน้าที่ |
| --- | --- |
| `GET /api/energy/live` | ค่าล่าสุดของแอร์ทุกเครื่อง |
| `GET /api/energy/metrics` | รายชื่อค่าที่เลือกใส่รายงานได้ |
| `GET /api/energy/sources` | ห้องและเครื่องที่มีข้อมูลให้เลือก |
| `GET /api/energy/history` | ข้อมูลรายชั่วโมงเป็น JSON ใช้กับหน้าตัวอย่าง |
| `GET /api/energy/export` | ไฟล์ `.xlsx` ตามเงื่อนไขเดียวกับ `history` |
| `GET /api/energy/summary` | ตัวเลขของหน้าหลัก/หน้าสถิติ ตามช่วงที่เลือก |
| `GET /api/alerts` | การแจ้งเตือนล่าสุด ใบที่ยังเปิดอยู่มาก่อน |
| `POST /api/alerts/:id/acknowledge` | กด `รับทราบแล้ว` |

พารามิเตอร์ที่ใช้ร่วมกันคือ `from`, `to` (รูปแบบ `YYYY-MM-DD`),
`scope` (`building` / `room` / `device`), `rooms`, `devices`, `metrics`
(คั่นด้วยจุลภาค) และ `rate` สำหรับคอลัมน์ค่าไฟโดยประมาณ

ไฟล์ `.xlsx` สร้างที่ Backend ด้วย `src/utils/xlsx-writer.js` ซึ่งเขียนแพ็กเกจ
Office Open XML เองโดยใช้ `fflate` ที่โปรเจกต์มีอยู่แล้ว จึงไม่ต้องเพิ่ม
dependency ใหม่ และรองรับหัวตารางภาษาไทยเพราะทุกไฟล์ข้างในเป็น UTF-8

## โครงสร้างระบบ

```text
Flutter App                      เว็บแอป (web/)
    ├── BLE: คอนฟิก ESP32           เสิร์ฟเป็นไฟล์ static โดย Caddy
    │   ครั้งแรก/ตั้งค่าใหม่          ที่ https://<โดเมน>/
    │                                    │
    │ HTTPS/HTTP (JSON)                  │ HTTPS (JSON) โดเมนเดียวกัน จึงไม่ติด CORS
    ▼                                    ▼
Node.js Backend API
    ├── MariaDB: users + OTP + schedules + air_conditioners
    │            + occupancy_sensors + energy_hourly + system_alerts
    ├── SMTP: ส่งอีเมล OTP
    └── MQTT Broker
            │ Wi-Fi/MQTT
            ▼
        ESP32 แอร์ ── IR/PZEM ── เครื่องปรับอากาศ
        ESP32 ห้อง ── UART ── HLK-LD2410
```

แอป Flutter ไม่ควรเชื่อม MariaDB โดยตรง เพราะจะทำให้รหัสฐานข้อมูลถูกดึงออกจาก
ไฟล์ APK ได้ Backend จึงเป็นผู้ตรวจรหัสผ่านและเรียกฐานข้อมูลแทน

## เริ่มใช้งานเร็วสุดด้วย `run_all.ps1`

ถ้าเคยตั้งค่า MQTT และฐานข้อมูลไว้แล้ว ให้เปิด Docker Desktop แล้วรันจาก
โฟลเดอร์หลัก `cpe_air_remote`:

```powershell
Set-ExecutionPolicy -Scope Process Bypass
.\run_all.ps1
```

สคริปต์ทำ 7 ขั้นให้อัตโนมัติ:

1. ตรวจว่า Docker Desktop ทำงานอยู่
2. เปิด MariaDB container แล้วรอจนพอร์ต `DB_PORT` ตอบ
3. รัน `db:migrate:pzem`, `db:migrate:occupancy`, `db:migrate:energy`,
   `db:migrate:autooff` และ `scripts/doctor.js --fix` เพื่อเติมตารางกับ
   คอลัมน์ที่ขาดให้ตรงกับ `database/schema.sql`
4. หา LAN IPv4 ปัจจุบัน แล้วเขียน `MQTT_URL`, `MQTT_USERNAME`, `MQTT_PASSWORD`
   ลง `backend/.env` ให้ตรงกับ `mqtt/.env`
5. เปิด Mosquitto และรอจนสถานะเป็น `healthy`
6. ปิด Backend ตัวเก่าที่ค้างพอร์ต 3000 แล้วเปิดใหม่ในหน้าต่างของตัวเอง
7. ตรวจ `/api/health` ว่า `mqtt.connected` เป็น `true` แล้วเปิดแอป Flutter

ตัวเลือกเพิ่มเติม:

```powershell
.\run_all.ps1 -SkipFlutter                 # เฉพาะ MariaDB + MQTT + Backend
.\run_all.ps1 -BrokerHost 192.168.1.153    # กำหนด LAN IP เอง
.\run_all.ps1 -InitDb                      # สร้างตารางครั้งแรก
```

ถ้า LAN IP เปลี่ยนไปจากตอนที่คอนฟิก ESP32 ไว้ ต้องตั้งค่าบอร์ดผ่าน Bluetooth
ใหม่หนึ่งรอบ เพราะค่า MQTT ถูกเขียนลง NVS ของ ESP32 ตั้งแต่ตอน Provisioning

## 0. ตั้งค่า Mosquitto MQTT Broker

เวอร์ชันนี้มี Broker อยู่ในโฟลเดอร์ `mqtt/` แล้ว โดยใช้ Eclipse Mosquitto 2
ผ่าน Docker Compose และปิด Anonymous access

เปิด Docker Desktop แล้วรัน:

```powershell
Set-ExecutionPolicy -Scope Process Bypass
cd mqtt
.\setup_mqtt.ps1
```

สคริปต์จะหา LAN IPv4, สร้างรหัสผ่านแบบสุ่ม, สร้าง ACL สำหรับ
`rmutt/ac/#` และ `rmutt/occupancy/#`, เปิด Broker, ทดสอบ Publish/Subscribe และอัปเดตค่า MQTT ใน
`backend/.env` ให้อัตโนมัติ หาก IP ที่เลือกไม่ตรงกับ `ipconfig` ให้ระบุเอง:

```powershell
.\setup_mqtt.ps1 -BrokerHost 192.168.1.10
```

คำสั่งใช้งานภายหลัง:

```powershell
.\start_mqtt.ps1
.\test_mqtt.ps1
.\stop_mqtt.ps1
```

แอปไม่แสดงช่อง MQTT อีกต่อไป Backend จะใช้ค่าจาก `backend/.env` และส่งให้
ESP32 อัตโนมัติ จึงควรตรวจว่า `MQTT_URL` ใช้ LAN IP ของคอม ไม่ใช่
`127.0.0.1`

### ACL ต้องมีทั้งสอง prefix

ไฟล์ `mqtt/config/acl` ต้องมีอย่างน้อยสี่บรรทัดนี้:

```text
user rmutt_air
topic readwrite rmutt/ac/#
topic readwrite rmutt/occupancy/#
topic read $SYS/#
```

ถ้าไฟล์นี้ถูกสร้างไว้ตั้งแต่ก่อนเวอร์ชัน 2.1.0 จะไม่มีบรรทัด `rmutt/occupancy/#`
ผลคือ Broker **ปฏิเสธแบบเงียบ ๆ** ทั้งการ publish ของ ESP32 เซ็นเซอร์และการ
subscribe ของ Backend ทั้งสองฝั่งยังเชื่อมต่อและยืนยันรหัสผ่านผ่านตามปกติ
Serial ของบอร์ดขึ้น `MQTT connected` ด้วย แต่ไม่มีข้อมูลไปถึงฐานข้อมูลเลย และ
แอปจะค้างที่ “เซ็นเซอร์ไม่พร้อมใช้งาน” ตลอด

ดูหลักฐานได้ที่ `mqtt/log/mosquitto.log` จะมีบรรทัด `not authorised`
ตั้งแต่เวอร์ชันปัจจุบัน `run_all.ps1` ตรวจและซ่อมไฟล์ ACL ให้อัตโนมัติ พร้อม
รีสตาร์ต Broker เมื่อมีการแก้ไข

## 1. ตั้งค่า Backend และ MariaDB

ต้องมี Node.js 20 ขึ้นไปและ MariaDB ที่เปิดใช้งานอยู่

เปิด PowerShell ในโฟลเดอร์ `backend`:

```powershell
npm install
Copy-Item .env.example .env
```

เปิด `.env` แล้วแก้ค่าฐานข้อมูล, `JWT_SECRET`, `OTP_PEPPER`, SMTP และข้อมูล
แอดมิน ห้ามนำไฟล์ `.env` ขึ้น GitHub

สร้าง Secret แบบสุ่ม 2 ครั้ง แล้วนำผลลัพธ์คนละค่าไปใส่ `JWT_SECRET` และ
`OTP_PEPPER`:

```powershell
node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
```

สร้างตารางใหม่โดยไม่ลบตาราง `floor`, `hub`, `room` และ `user` เดิม:

```powershell
npm run db:init
```

ตาราง `users` ใช้ `username` เป็น Primary Key โดยตรงและไม่มีคอลัมน์ `id`
ส่วนตาราง OTP เชื่อมบัญชีด้วย `username`

หากเคยรันโปรเจกต์เวอร์ชันเดิมที่ตาราง `users` ยังมี `id` ให้สำรองฐานข้อมูล
แล้วรันคำสั่งนี้หนึ่งครั้งก่อนเปิด Backend:

```powershell
npm run db:migrate:username
```

สคริปต์จะย้ายการอ้างอิง OTP จาก `user_id` ไปเป็น `username` แล้วจึงนำ
คอลัมน์ `id` ออกจาก `users` โดยไม่เปลี่ยน Username, Password หรือข้อมูลบัญชี

ถ้าเป็นฐานข้อมูลเดิม ให้เพิ่มตารางเรียนและข้อมูลตัวอย่างโดยรันหนึ่งครั้ง:

```powershell
npm run db:migrate:schedules
```

คำสั่งนี้ไม่ลบตารางหรือข้อมูลผู้ใช้เดิม และจะสร้างตาราง `class_schedules`
สำหรับตารางเรียนของแต่ละห้อง

เพิ่มตาราง ESP32/เครื่องปรับอากาศโดยรันหนึ่งครั้ง:

```powershell
npm run db:migrate:air
```

คำสั่งนี้สร้างตาราง `air_conditioners` และไม่ลบข้อมูลผู้ใช้หรือตารางเรียนเดิม

ถ้าใช้ฐานข้อมูลจากเวอร์ชันก่อนหน้า ให้เพิ่มคอลัมน์ PZEM ตารางเซ็นเซอร์ตรวจคน
และตารางประวัติค่าไฟ โดยรันคำสั่งต่อไปนี้หนึ่งครั้ง:

```powershell
npm run db:migrate:pzem
npm run db:migrate:occupancy
npm run db:migrate:energy
npm run db:migrate:autooff
```

`db:migrate:occupancy` สร้างตาราง `occupancy_sensors` แบบหนึ่งเซ็นเซอร์ต่อ
หนึ่งห้อง ส่วน `db:migrate:energy` สร้างตาราง `energy_hourly` สำหรับเก็บค่าไฟ
รายชั่วโมง ส่วน `db:migrate:autooff` เพิ่มคอลัมน์นาฬิกาปิดอัตโนมัติใน
`air_conditioners` และสร้างตาราง `system_alerts` ทุกคำสั่งไม่ลบข้อมูลห้อง
แอร์ ตารางเรียน หรือผู้ใช้เดิม

### ตรวจโครงสร้างฐานข้อมูลด้วย `db:doctor`

ถ้าไม่แน่ใจว่าฐานข้อมูลตกคอลัมน์ไหนไปบ้าง ให้ตรวจก่อนเปิด Backend:

```powershell
npm run db:doctor
```

สคริปต์อ่าน `database/schema.sql` แล้วเทียบกับตารางจริงทุกตารางทีละคอลัมน์
พร้อมรายงานสถานะ Provisioning ของอุปกรณ์ทั้งสองชนิด คือ `air_conditioners`
(ESP32 + PZEM) และ `occupancy_sensors` (ESP32 + LD2410) ว่าแต่ละตัวเป็น
`reserved` หรือ `active` แล้ว ถ้าต้องการให้ซ่อมอัตโนมัติ:

```powershell
node scripts/doctor.js --fix
```

โหมด `--fix` จะ **สร้างตารางที่หายไปทั้งตาราง** ตามคำสั่ง `CREATE TABLE` ใน
`schema.sql` และเติมคอลัมน์ที่ขาดในตารางที่มีอยู่แล้ว โดยไม่ลบข้อมูลเดิมและ
ไม่แตะคอลัมน์ที่มีอยู่ จะข้ามเฉพาะคอลัมน์ที่เป็น `NOT NULL` แบบไม่มี `DEFAULT`
แล้วแจ้งให้เติมเอง ตารางที่เพิ่งสร้างจะยังว่าง ถ้าต้องการข้อมูลห้องตัวอย่างให้
รัน `npm run db:init` ต่อ (ใช้ `INSERT IGNORE` จึงไม่ทับข้อมูลเดิม)

`db:doctor` ยังสรุปประวัติค่าไฟให้ด้วยว่ามีกี่ช่วงเวลา จากกี่อุปกรณ์ ข้อมูล
เริ่มตั้งแต่เมื่อไหร่ และรวมพลังงานได้เท่าไร ถ้ายังไม่มีตาราง `energy_hourly`
จะบอกให้รัน `npm run db:migrate:energy`

อาการที่แก้ด้วยคำสั่งนี้ได้ เช่น เพิ่มเซ็นเซอร์ LD2410 ในแอปแล้วระบบไม่จำค่า
เพราะฐานข้อมูลยังไม่มีตาราง `occupancy_sensors` (ฐานข้อมูลที่สร้างไว้ก่อน
เวอร์ชัน 2.1.0 และยังไม่ได้รัน `npm run db:migrate:occupancy`)

อาการที่พบบ่อยของฐานข้อมูลรุ่นเก่าคือหน้าห้องขึ้น
`เกิดข้อผิดพลาดภายในเซิร์ฟเวอร์` และไม่เห็นแอร์ ทั้งที่มีแถวอยู่ใน MariaDB
สาเหตุคือตาราง `air_conditioners` ยังไม่มีคอลัมน์ชุด PZEM (`energy_kwh`,
`frequency_hz`, `power_factor`, `pzem_available`, `ac_running`,
`outside_schedule`) ทำให้คำสั่ง `SELECT` ของ `GET /api/air-conditioners`
ล้มทั้งชุด แก้ด้วย `npm run db:migrate:pzem` หรือ `node scripts/doctor.js --fix`
แล้วเปิด Backend ใหม่

`mqtt/setup_mqtt.ps1` จะเพิ่มค่าต่อไปนี้ใน `.env` ให้ Backend โดยอัตโนมัติ:

```env
MQTT_REQUIRED=true
MQTT_URL=mqtt://192.168.1.10:1883
MQTT_USERNAME=rmutt_air
MQTT_PASSWORD=รหัสผ่านที่สคริปต์สร้าง
MQTT_TOPIC_PREFIX=rmutt/ac
MQTT_OCCUPANCY_TOPIC_PREFIX=rmutt/occupancy
```

## ความปลอดภัยที่ใส่ไว้

- รหัสผ่านเก็บด้วย bcrypt cost 12 ไม่เก็บ Password แบบอ่านได้
- OTP และ Reset Token เก็บเป็น HMAC-SHA256 hash
- OTP หมดอายุใน 10 นาที ใช้ได้ครั้งเดียว และกรอกผิดได้ไม่เกิน 5 ครั้ง
- จำกัดความถี่ Login และ Forgot Password
- เมื่อเปลี่ยนรหัสผ่าน Token เดิมทั้งหมดถูกยกเลิก
- เมื่อ Admin เปลี่ยนสิทธิ์หรือระงับบัญชีของผู้ใช้คนใด Token เดิมของคนนั้น
  ถูกยกเลิกทันทีด้วย `token_version` จึงไม่มีช่วงที่ยังใช้สิทธิ์เก่าค้างอยู่
- API จัดการผู้ใช้ทุกเส้นทางผ่าน `authenticate` + `requireAdmin` และตรวจซ้ำ
  ฝั่ง Server ว่าห้ามแก้บัญชีตัวเองและต้องเหลือ Admin อย่างน้อยหนึ่งบัญชี
- ข้อความขอ OTP ไม่เปิดเผยว่า Username หรือ Email มีอยู่จริงหรือไม่
- Secret และรหัสฐานข้อมูลอยู่เฉพาะ Backend `.env`

## 4. อัปโหลด Firmware ESP32

ไฟล์ Firmware อยู่ที่:

```text
firmware/rmutt_esp32_air/rmutt_esp32_air.ino
```

ติดตั้ง Arduino libraries:

- PubSubClient
- IRremoteESP8266 2.9.0
- PZEM004Tv30 (Jakub Mandula)

ค่าเริ่มต้นใช้ `GPIO17` เป็นขาส่ง IR และ `GPIO0` เป็นปุ่มเข้า Setup Mode
รายละเอียดการต่อและลำดับคอนฟิกอยู่ใน `firmware/README.md` ส่วนสัญญา BLE/MQTT
ฉบับเต็มอยู่ใน `docs/BLE_MQTT_PROTOCOL.md`

หนึ่ง ESP32 ควบคุมหนึ่งแอร์ และต้องเลือกโปรโตคอลยี่ห้อ/รุ่นให้ตรงกับรีโมตจริง
ฟังก์ชันบางรายการ เช่น Eco, Clean หรือ Swing อาจไม่มีในแอร์บางรุ่น

Firmware ตรวจคนอยู่ที่:

```text
firmware/rmutt_esp32_occupancy/rmutt_esp32_occupancy.ino
```

ติดตั้งไลบรารี `ld2410` by Nick Reynolds เวอร์ชัน 0.2.2 ขึ้นไป แล้วอัปโหลด
ลง ESP32 อีกบอร์ดหนึ่ง การต่อ UART แบบแรงดันต่ำและกติกา `Static > 25`
อยู่ใน `firmware/README.md` และคู่มือ `README_LD2410_OCCUPANCY_V210_TH.txt`

### เครื่องมือตรวจ LD2410 เมื่อไม่ได้รับข้อมูลเลย

ถ้า `[diag]` ขึ้นว่า `UART1 rx bytes in the last 10s: 0` แปลว่าเรดาร์ไม่ได้ส่ง
อะไรออกมาเลย ไม่ใช่ส่งมาแล้วอ่านผิด baud จึงต้องไล่หาว่า "ขาเสีย" หรือ
"จิ้มผิดแพด" ใช้สเก็ตช์ตรวจ 2 ตัวนี้ ไล่ตามลำดับ

```text
firmware/ld2410_probe/ld2410_probe.ino      ตรวจ GPIO32/33 และไล่ baud ทั้งสองทิศ
firmware/ld2410_pinscan/ld2410_pinscan.ino  สแกนทีละขา หาว่าสายไปถึงขาไหนจริง
```

วิธีใช้ `ld2410_pinscan` โดยย่อ

1. ต่อ `VCC` กับ `GND` ไว้ตามปกติ **`GND` ต้องถึงกันเสมอ** ไม่งั้นสแกนไม่เจอ
2. เอาสายจากแพด `TX` ของโมดูลเส้นเดียว จิ้มขา ESP32 ทีละขา
3. เปิด Serial Monitor ที่ 115200 สเก็ตช์จะสแกนซ้ำทุก 2 วินาที ขยับสายดูสด ๆ ได้
4. ขาที่ขึ้น `<<< UART` คือขาที่ใช้ได้ สเก็ตช์จะไล่ baud ให้ต่อ แล้วพิมพ์ค่า
   `RADAR_RX_PIN` กับ `RADAR_BAUD` ที่เอาไปวางใน `rmutt_esp32_occupancy.ino` ได้เลย

ผลที่อ่านได้มี 5 แบบ คือ `ว่าง` (ไม่มีอะไรต่อ ขาปกติ), `<<< UART` (เจอข้อมูลจริง),
`ต่ออยู่ HIGH ค้าง` (มีสายต่อแต่แพดนั้นไม่ส่ง ให้ย้ายแพด), `ต่ออยู่ LOW ค้าง`
(ขาถูกดึงลง GND อย่าใช้) และ `แกว่งเร็ว` (พลิกเป็นหมื่นครั้งต่อ 250ms เร็วเกินกว่า
จะเป็นข้อมูล มักเป็นคริสตัล 32.768kHz ที่ติดมากับ `GPIO32`/`GPIO33` ให้เลี่ยงไปขาอื่น)

ข้อควรระวัง: ห้ามคาสายไว้ที่ `GPIO12` ตอนกดรีเซ็ต ถ้า `GPIO12` ถูกดันเป็น HIGH
ตอนบูต ESP32 จะตั้งไฟแฟลชผิดแล้วบูตไม่ขึ้น

การอัปโหลดสเก็ตช์ตรวจทั้งสองตัวไม่ลบ NVS ห้องกับค่า MQTT ยังอยู่ครบ
แฟลชสเก็ตช์หลักกลับไปก็ใช้งานต่อได้ทันที รายละเอียดเต็มอยู่ใน `firmware/README.md`

## กราฟบอกค่าไฟรายจุด และหน่วยที่สลับอัตโนมัติ (v3.9.0)

เดิมกราฟหน้าสถิติวาดแค่เส้นกับจุด ไม่มีตัวเลขกำกับเลย และทุกหน้าจอตรึงหน่วยไว้
ที่ `kWh` ทศนิยมตำแหน่งเดียว พอลองวัดโหลดเล็ก ๆ อย่างที่ชาร์จมือถือ (21 W)
ค่าจริง `0.005 kWh` จะถูกปัดเหลือ `0.0 kWh` ทุกจุด อ่านอะไรไม่ได้เลย

### ป้ายค่าไฟบนกราฟ

ทุกจุดมีป้ายบอกค่าไฟติดอยู่เหนือจุด ถ้าเลือกช่วงยาวจนจุดถี่เกินกว่าที่ป้ายจะ
ไม่ทับกัน ระบบจะเว้นระยะให้เอง โดยคิดจากความกว้างจริงของป้ายที่ยาวที่สุด
ไม่ใช่เดาจากจำนวนจุด และจะพยายามวาดป้ายของจุดสุดท้ายเสมอเพราะเป็นค่าล่าสุด
ที่คนดูบ่อยที่สุด

แตะที่กราฟหรือลากนิ้วไปตามเส้น จะมีเส้นแนวตั้งชี้จุดที่เลือกพร้อมกล่อง
รายละเอียดบอกวันที่ ค่าไฟ และเงินบาทของจุดนั้น แตะจุดเดิมซ้ำเป็นการปิดกล่อง

### หน่วยสลับตามขนาดของค่า

`formatEnergy()` ใน `lib/utils/number_format.dart` เลือกหน่วยให้เอง

| ช่วงค่า | หน่วย | ตัวอย่าง |
|---|---|---|
| ต่ำกว่า 1 kWh | `Wh` | `0.005 kWh` -> `5.00 Wh` |
| 1 ถึง 999 kWh | `kWh` | `12.5 kWh` |
| ตั้งแต่ 1000 kWh | `MWh` | `2400 kWh` -> `2.40 MWh` |

จำนวนทศนิยมลดลงเมื่อตัวเลขใหญ่ขึ้น (ต่ำกว่า 1 ใช้ 3 ตำแหน่ง, ถึง 10 ใช้ 2,
ถึง 100 ใช้ 1, เกิน 100 ไม่ใส่ทศนิยม) เพราะทศนิยมของ `142.4 kWh` ไม่มีใครใช้
แต่ทศนิยมของ `0.400 Wh` คือค่าทั้งหมดที่มี

ใช้แล้วที่ยอดรวมหน้าหลัก ยอดรวมหน้าสถิติ การ์ดแยกตามห้อง และป้ายบนกราฟ

### ทำไมทั้งชุดต้องใช้หน่วยเดียวกัน

ถ้าปล่อยให้แต่ละค่าเลือกหน่วยเอง `900 Wh` จะไปอยู่ข้าง `1.2 kWh` แล้วตัวเลข
900 จะดูใหญ่กว่าทั้งที่น้อยกว่า จุดบนกราฟเส้นเดียวกันและการ์ดห้องในรายการ
เดียวกันจึงส่ง `scaleReference` ซึ่งเป็นค่าสูงสุดของชุดเข้าไปด้วย ทุกตัวจะได้
หน่วยและจำนวนทศนิยมชุดเดียวกัน เทียบกันได้ตรง ๆ

ป้ายบนกราฟติดหน่วยไปทุกใบ ไม่ใช่ใส่หน่วยไว้มุมเดียว เพราะกราฟสลับหน่วยตาม
ชุดข้อมูลได้ เห็นแค่ `5.00` ลอย ๆ จะไม่รู้ว่าเป็น Wh หรือ kWh

### แก้ให้เข้ากับ Flutter รุ่นใหม่ (รวมอยู่ใน v3.9.0)

อัปเกรด Flutter แล้วเทสต์ของหน้าฐานข้อมูลค่าไฟพังไป 3 ตัว ทั้งหมดมาจากรากเดียว
กัน คือ Flutter รุ่นใหม่เพิ่ม assertion ว่า `ListTile` ห้ามอยู่ใต้กล่องที่มีสี
พื้นหลัง เพราะ ListTile วาดพื้นหลังกับเอฟเฟกต์กดลงบน `Material` ที่ใกล้ที่สุด
แล้วกล่องที่มีสีจะไปบังเอฟเฟกต์นั้นไว้

`_Panel` ใน `energy_database_screen.dart` เป็นกล่องแบบนั้น และข้างในมี
`CheckboxListTile` กับ `SwitchListTile` อยู่ พอ assertion เด้ง การ build ก็หยุด
เทสต์ตัวอื่นเลยหาปุ่มกับข้อความบนหน้าจอไม่เจอตามไปด้วย แก้โดยครอบเนื้อในของ
`_Panel` ด้วย `Material(type: MaterialType.transparency)` ให้ ListTile มี
Material ของตัวเองอยู่ในกล่อง

เก็บอีกสองจุดพร้อมกัน

- `account_settings_screen.dart` เดิมเรียก `context.tr(...)` ต่อจาก `await`
  ทันที ถ้าผู้ใช้กดออกจากหน้าระหว่างรอบันทึก จะแตะ context ที่ถูกทิ้งไปแล้ว
  ใส่ `if (!mounted) return;` คั่นไว้
- `floor_selector.dart` ยัง import `app_theme.dart` ค้างไว้ทั้งที่ไม่มี
  `AppColors` เหลืออยู่ในไฟล์แล้ว ลบออก

หลังแก้ `_Panel` แล้ว assertion เดียวกันโผล่ที่การ์ดหน้าล็อกอินอีกจุด เพราะมี
`CheckboxListTile` (`จำรหัสผ่าน`) อยู่ในการ์ดที่มีสีพื้นและเงา ครอบด้วย
`Material(type: MaterialType.transparency)` แบบเดียวกัน

พร้อมกันนั้นเจอบั๊กจัดวางของจริงในหน้าล็อกอิน แถวปุ่ม `ลืมรหัสผ่าน?` กับ
`ติดต่อผู้ดูแลระบบ` ใช้ `Row` แบบ `spaceBetween` โดยไม่ได้กันการหด ข้อความไทย
สองปุ่มรวมกันกว้างเกินการ์ดไป 88px จอแคบจะเห็นแถบเหลืองดำทับ แก้โดยครอบปุ่มละ

ค่าที่เลือกเป็น **ตัวคูณ ไม่ใช่ขนาดตายตัว** จึงเอาไปคูณกับขนาดที่ผู้ใช้ตั้งไว้
ในระบบ Android อีกที คนที่ตั้งตัวอักษรใหญ่ไว้ทั้งเครื่องเพราะสายตาไม่ดี จะได้
ไม่โดนแอปบังคับให้กลับไปเล็ก และมีเพดานที่ 2.0 กันตัวอักษรใหญ่จนปุ่มกดไม่ได้

ใส่ไว้ที่ `builder` ของ `MaterialApp` จึงมีผลกับทุกหน้าจอและทุกกล่องโต้ตอบ
ตรรกะการคูณอยู่ที่ `AppSettingsController.resolvedTextScale()`

### การแจ้งเตือนแยกตามชนิด

การแจ้งเตือนของระบบมี 3 ชนิด แต่ละชนิดมี 2 สวิตช์แยกกัน

| ชนิด | ความหมาย |
|---|---|
| แอร์ทำงานนอกเวลาเรียน | ไม่มีคาบเรียน แต่แอร์ทำงานอยู่และมีคนอยู่ในห้อง |
| ปิดแอร์อัตโนมัติสำเร็จ | ระบบสั่งปิดแล้วแอร์หยุดกินไฟจริง |
| ปิดแอร์อัตโนมัติไม่สำเร็จ | สั่งครบจำนวนครั้งแล้วแอร์ยังทำงานอยู่ |

แยกสองช่องเพราะคนละความรำคาญกัน รายการในแอปเปิดไว้ก็ไม่กวนใคร แต่การเด้งบน
มือถือดังตอนกลางดึกได้ ถ้าปิด `แสดงในแอป` สวิตช์ `เด้งบนมือถือ` จะถูกปิดตาม
และกดไม่ได้ เพราะเด้งแล้วกดเข้าไปดูต่อไม่ได้ก็ไม่มีประโยชน์

ชนิดที่แอปรุ่นนั้นยังไม่รู้จัก (`unknown`) จะขึ้นในรายการเสมอและปิดไม่ได้
ถ้าปิดได้ วันที่ Backend เพิ่มชนิดใหม่ ผู้ใช้แอปรุ่นเก่าจะไม่เห็นมันเลย

ค่าตั้งเก็บใน secure storage ของเครื่อง เป็น JSON ก้อนเดียว ไม่ได้ส่งขึ้น
เซิร์ฟเวอร์ เพราะเป็นความชอบของเครื่องนั้น ไม่ใช่ของบัญชี ชนิดที่ยังไม่มีใน
ข้อมูลเก่าจะได้ค่าเริ่มต้นของมันเอง เวลาเพิ่มชนิดใหม่ผู้ใช้เดิมจึงไม่ต้องไป
ตั้งใหม่ทั้งหมด

## สวิตช์รวมของระบบปิดแอร์อัตโนมัติ (v3.11.0)

ระบบปิดแอร์อัตโนมัติมีมาตั้งแต่ v3.8.0 อยู่แล้ว (นับถอยหลัง 5 นาทีเมื่อแอร์
ทำงานแต่ห้องว่าง โชว์เวลาตรงเมนูแอร์ ครบแล้วยิง IR ปิด ซ้ำได้สูงสุด 5 ครั้ง)
สิ่งที่เพิ่มในรุ่นนี้คือ **สวิตช์เปิดปิดทั้งระบบ** ในหน้าตั้งค่าแอป

### ทำไมสวิตช์ต้องอยู่บนเซิร์ฟเวอร์

ตัวที่ยิงคำสั่งปิดคือ Backend ไม่ใช่แอปบนมือถือ สวิตช์ที่เก็บไว้ในเครื่อง
ผู้ใช้จึงหยุดระบบไม่ได้จริง ปิดในมือถือตัวเองแล้วแอร์ก็ยังโดนสั่งปิดอยู่ดี
ค่านี้เลยเก็บในตาราง `system_settings` บนฐานข้อมูล และมีผลกับทั้งอาคารทันที

| เส้นทาง | สิทธิ์ | ทำอะไร |
|---|---|---|
| `GET /api/settings` | ทุกคนที่ล็อกอิน | อ่านสถานะ |
| `PATCH /api/settings/auto-off` | เฉพาะ admin | เปิดปิดระบบ |

คนที่ไม่ใช่แอดมินยังเห็นสถานะได้ แต่กดสลับไม่ได้ ที่ต้องให้เห็นเพราะถ้าซ่อนไว้
เขาจะงงว่าทำไมนับถอยหลังไม่ขึ้นสักที แล้วไปแจ้งว่าเซ็นเซอร์พัง ทั้งที่แค่มีคน
ปิดระบบไว้

ตารางเก็บชื่อคนกดและเวลาไว้ด้วย (`updated_by`, `updated_at`) เวลามีคนถามว่า
ทำไมแอร์ไม่ปิดเอง จะได้ตอบได้ว่าใครปิดและปิดเมื่อไหร่

### ปิดสวิตช์แล้วเกิดอะไรขึ้น

`evaluateAutoOff()` เช็คสวิตช์เป็นอย่างแรกของทุกรอบ ถ้าปิดอยู่จะ **ล้างนาฬิกา
ที่ค้างอยู่ทุกเครื่อง** แล้วจบรอบทันที ที่ต้องล้างเพราะถ้าปล่อยไว้ แอปจะยังโชว์
เวลานับถอยหลังที่ไม่มีวันยิงจริง ซึ่งหลอกตาคนใช้

คำสั่ง `UPDATE` มีเงื่อนไข `auto_off_deadline_at IS NOT NULL` อยู่ รอบที่ไม่มี
อะไรค้างจึงไม่เขียนฐานข้อมูลเลย ตัวคุมจังหวะเรียกทุก 10 วินาที ถ้าเขียนทุกรอบ
จะกวนฐานข้อมูลเปล่า ๆ

ค่าที่อ่านมาถูกพักไว้ 5 วินาที เพราะตัวคุมจังหวะเรียกทั้งทุก 10 วินาทีและทุกครั้ง
ที่บอร์ดส่งสถานะเข้ามา ถ้าอ่านฐานข้อมูลทุกครั้งจะเปลืองเปล่า

ถ้ายังไม่ได้รัน migration (ยังไม่มีตาราง) ระบบจะถอยไปใช้ค่าเริ่มต้นคือ **เปิด**
ของเดิมจะได้ทำงานต่อเหมือนก่อนอัปเดต แทนที่จะล้มทั้งตัวคุมจังหวะ

### สั่งอัปเดตฐานข้อมูล

```powershell
npm run db:migrate:settings
```

`run_all.ps1` และ `deploy\update-server.ps1` เรียกให้เองแล้ว

## เว็บแอป (v3.13.0)

เว็บแอปอยู่ในโฟลเดอร์ `webapp/` แยกจากโค้ด Flutter และ Backend ใช้ API ชุดเดิม
ทั้งหมด ไม่มีเส้นทางเข้าฐานข้อมูลของตัวเอง เปิดใช้งานจริงที่
<https://rmutt-energy.duckdns.org/>

ชื่อโฟลเดอร์เป็น `webapp/` ไม่ใช่ `web/` เพราะ Flutter จอง `web/` ไว้สำหรับ
`flutter build web` อยู่แล้ว (ข้างในมี `index.html` ที่เป็นตัวโหลด Flutter Web
กับ `manifest.json`) ถ้าเอาเว็บแอปไปวางทับ Flutter Web จะ build ไม่ได้

รายละเอียดเชิงลึกอยู่ที่ `webapp/README.md` หัวข้อนี้สรุปเฉพาะสิ่งที่ต้องรู้
เวลาดูภาพรวมของทั้งโปรเจกต์

### ทำไมเป็น HTML + JavaScript ล้วน ไม่มีขั้นตอน build

เซิร์ฟเวอร์มี Caddy ที่เสิร์ฟไฟล์ static อยู่แล้ว การเพิ่ม React หรือ Vite
หมายถึงต้องมี Node บนเครื่องที่ deploy ต้องจำว่าแก้แล้วต้อง `npm run build`
ก่อน และเวลาโปรเจกต์ถูกส่งต่อ ต้องมานั่งไล่ว่าทำไม build พัง สิ่งที่ได้
กลับมาคือความสะดวกตอนเขียนโค้ด ซึ่งไม่คุ้มกับเว็บขนาด 9 หน้า

ผลคือ `deploy-web.ps1` ทำแค่ `scp` ไฟล์ขึ้นไป ไม่ต้อง build ไม่ต้องรีสตาร์ท
อะไรเลย และเปิดโค้ดในโฟลเดอร์ `webapp/` แล้วอ่านได้ตรง ๆ โดยไม่ต้องมีเครื่องมือ

ไม่มีไลบรารีภายนอกเลย กราฟวาดเป็น SVG เอง ไอคอนเขียนเป็น SVG เอง
ฟอนต์จาก Google Fonts เป็นของเสริมล้วน ๆ ถ้าเครือข่ายเข้าไม่ถึงจะถอยไปใช้
ฟอนต์ไทยในเครื่อง และทุกอย่างยังทำงานได้ปกติ

### การดึงข้อมูลและนาฬิกานับถอยหลัง

| แรงดัน, ความถี่, ตัวประกอบกำลัง | เฉลี่ย | 220V กับ 221V รวมกันไม่ใช่ 441V |
| ค่าที่ลงท้ายด้วย Min / Max | ต่ำสุด / สูงสุด | แรงดันต่ำสุดของอาคารคือค่าที่ต่ำที่สุดในบรรดาทุกห้อง ไม่ใช่ผลบวกของค่าต่ำสุดรายห้อง |

ป้ายมุมขวาบนของกราฟบอกไว้ด้วยว่ารอบนั้นยุบแบบไหน (`รวมทุกห้อง` / `เฉลี่ยทุกห้อง`)
และกราฟเรียงจุดตามเวลาเสมอ ไม่เชื่อลำดับที่ฐานข้อมูลส่งมา

### เส้นทางบนเซิร์ฟเวอร์

| ที่อยู่ | คือ |
|---|---|
| `/` | เว็บแอป (`/opt/rmutt/www/index.html`) |
| `/status.html` | หน้าสถานะแบบเดิมที่เคยอยู่ที่ `/` |
| `/api/*` | Backend Express ผ่าน reverse proxy ของ Caddy |

เว็บกับ API อยู่โดเมนเดียวกัน จึงไม่ต้องตั้ง CORS เพิ่มและไม่ต้องขอใบรับรอง
ใหม่ `Caddyfile` เพิ่มแค่หัวเรื่องแคช: ไฟล์ใน `/assets/*` เก็บแคช 1 ชั่วโมง
ส่วน `index.html` ตั้ง `no-cache` เพื่อไม่ให้ผู้ใช้เห็นเว็บรุ่นเก่าหลังอัปเดต
โดยไม่รู้ว่าต้องกด Ctrl+F5

### สั่งขึ้นเซิร์ฟเวอร์

```powershell
# แก้แต่หน้าเว็บ — เร็ว ไม่ต้อง build ไม่ต้องรีสตาร์ท
.\deploy\deploy-web.ps1

# แก้ทั้ง Backend และเว็บ
.\deploy\update-server.ps1
```

ทั้งสองสคริปต์อัปโหลดลง `www.new` ก่อน แล้ว **คัดลอกเข้าไปใน** `www` ตัวเดิม
(ไม่เปลี่ยนชื่อโฟลเดอร์) เพราะ Docker ผูก `./www` เข้ากับ container ของ Caddy
ตาม inode ไม่ใช่ตามชื่อ ถ้าใช้ `mv` สลับโฟลเดอร์ Caddy จะยังชี้ไปที่โฟลเดอร์เดิม
ที่ถูกลบไปแล้ว แล้วตอบ 404 ทุกหน้าโดยไม่มีข้อความบอกว่าเกิดอะไรขึ้น — เจอมาแล้วจริง ๆ
วิธีนี้ยังล้างไฟล์เก่าที่ถูกลบออกจากโปรเจกต์แล้วแต่ยังค้างบนเซิร์ฟเวอร์ด้วย

### พัฒนาบนเครื่องตัวเอง

เว็บต้องเสิร์ฟผ่าน HTTP เปิดไฟล์ `index.html` ด้วยการดับเบิลคลิกจะไม่ทำงาน
เพราะ ES Modules ถูกกติกา CORS ห้ามไว้

```powershell
cd webapp
python -m http.server 5500
```

เปิด <http://127.0.0.1:5500/?api=http://127.0.0.1:3000/api> — พารามิเตอร์
`?api=` ใส่ครั้งเดียวพอ ค่าจะถูกจำไว้ใน localStorage ทำแบบนี้เพื่อให้ไฟล์ใน
โปรเจกต์ไม่ต้องมีที่อยู่เซิร์ฟเวอร์ฝังไว้ และเผลอ deploy ทับของจริงไม่ได้

ถ้า Backend รันคนละ origin ต้องเพิ่ม `http://127.0.0.1:5500` ใน `APP_ORIGIN`
ของ `.env` ฝั่ง backend ไม่งั้นจะติด CORS

### ความปลอดภัย

- โทเคน JWT เก็บใน `localStorage` ไม่ใช่ cookie เพราะ Backend ตรวจสิทธิ์จาก
  หัว `Authorization` อย่างเดียว การใช้ cookie จะทำให้ต้องคิดเรื่อง CSRF เพิ่ม
  โดยไม่ได้ประโยชน์กลับมา
- ทุกคำขอผ่าน `api.js` ที่แนบโทเคนให้เอง เมื่อเจอ 401 จะล้างโทเคนแล้วพากลับ
  ไปหน้าเข้าสู่ระบบทันที จุดเดียวทั้งระบบ
- ข้อมูลจากฐานข้อมูล (ชื่อวิชา ชื่ออาจารย์ ชื่อแอร์) ใส่ลง DOM ด้วย
  `textContent` เสมอ `innerHTML` ใช้เฉพาะกับไอคอน SVG ที่เขียนไว้ในโค้ด
- ปุ่มที่ซ่อนตามสิทธิ์บนหน้าเว็บเป็นแค่ความสะดวก การบังคับจริงอยู่ที่
  `requireAdmin` ของ Backend เสมอ
