เครือข่าย เซิร์ฟเวอร์ และ Tailscale

ภาพรวม#

บทนี้ตอบคำถามว่า "เซิร์ฟเวอร์ของโปรเจกต์อยู่ที่ไหน และคำขอจากแอป เว็บ และบอร์ด ESP32 เดินทางไปถึงมันได้อย่างไร" เริ่มจากความรู้เครือข่ายพื้นฐาน (IP, พอร์ต, DNS, TLS) แล้วไล่ไปจนถึงการตั้งค่าจริงในโฟลเดอร์ deploy/ คือ docker-compose.yml, Caddyfile, Dockerfile ทั้งสองตัว, tailscale-serve.json และ mosquitto/config/mosquitto.conf รวมถึง Broker สำหรับพัฒนาในโฟลเดอร์ mqtt/

เซิร์ฟเวอร์จริงเป็นเครื่อง Ubuntu ที่อยู่ในเครือข่ายภายในของมหาวิทยาลัย ได้ IP ส่วนตัวแบบ 10.x.x.x และ firewall ของมหาวิทยาลัยไม่ยอมให้อินเทอร์เน็ตต่อเข้ามา บนเครื่องรัน Docker 5 กล่อง (container) คือ db (MariaDB), mqtt (Mosquitto), backend (Node.js), caddy (เว็บเซิร์ฟเวอร์/reverse proxy) และ tailscale (ทางเข้าจากอินเทอร์เน็ต)

ระบบจึงมีทางเข้า 4 ทาง ซึ่งเป็นแกนของบทนี้ (สองทางผ่าน Tailscale Funnel จากที่ไหนก็ได้ และสองทางตรงผ่านโดเมน DuckDNS ที่ใช้ได้เฉพาะในอาคาร)

  1. เว็บและ API ในอาคาร ผ่านโดเมน DuckDNS พอร์ต 443 rmutt-energy.duckdns.org → Caddy (เว็บ, API, ไฟล์เฟิร์มแวร์)
  2. เว็บและ API จากที่ไหนก็ได้ ผ่าน Tailscale Funnel พอร์ต 443 rmutt-energy.tailb292b4.ts.net → กล่อง tailscale (ถอด TLS) → Caddy พอร์ต 8080 แอปมือถือใช้ทางนี้เป็นค่าเริ่มต้น
  3. บอร์ด ESP32 จากที่ไหนก็ได้ ผ่าน Tailscale Funnel พอร์ต 8443 rmutt-energy.tailb292b4.ts.net:8443 → กล่อง tailscale (ถอด TLS ด้วยใบรับรอง ts.net) → mqtt:1883 ในเครือข่าย Docker → Mosquitto นี่คือค่าเริ่มต้นปัจจุบันที่ Backend ส่งให้บอร์ดตอน provisioning
  4. บอร์ด ESP32 ในอาคาร ต่อตรง MQTTS พอร์ต 8883 rmutt-energy.duckdns.org:8883 → Mosquitto ยังใช้ได้เสมอ และจะถูกใช้จริงเมื่อตั้ง MQTT_DEVICE_URL=mqtts://<DOMAIN>:8883 ใน .env

ที่ต้องมีทางที่ 3 เพราะโดเมน DuckDNS ชี้ไป IP ภายใน 10.x บอร์ดที่ต่อ Wi-Fi นอกมหาวิทยาลัยจึงหา Broker ไม่เจอ ส่วนชื่อ ts.net ชี้ไปที่ relay สาธารณะของ Tailscale ซึ่งเข้าได้จากทุกเครือข่ายที่มีอินเทอร์เน็ต

ฐานข้อมูล (3306), Backend (3000) และ Caddy 8080 ไม่เปิดออกนอกเครื่องเลย ผู้ดูแลเข้าฐานข้อมูลได้ทางเดียวคืออุโมงค์ SSH ส่วน MQTT แบบไม่เข้ารหัส (1883) ไม่ได้ publish ออกนอกเครื่องเช่นกัน แต่กล่อง tailscale ส่งทราฟฟิกพอร์ต 8443 (ที่ถอด TLS แล้ว) มาที่พอร์ตนี้ภายในเครือข่าย Docker ดังนั้น Broker จึงเข้าถึงได้จากอินเทอร์เน็ตผ่าน Funnel โดยมี TLS และรหัสผ่านรายบอร์ดเป็นด่านป้องกัน (ดูหัวข้อ "ทำไมเปิดทางเข้าแค่สองจุด")

หมายเหตุ

เอกสารบางส่วนในโปรเจกต์ (deploy/DEPLOY.md, deploy/SERVER_REQUIREMENTS.md, docs/learn/14-*.md) ยังเขียนตามแผนเดิมที่ขอให้ฝ่ายไอทีเปิดพอร์ต 80/443 จากอินเทอร์เน็ต และขอใบรับรองแบบ HTTP-01 แต่โค้ดจริงตอนนี้ใช้ DuckDNS + DNS-01 + Tailscale Funnel บทนี้อธิบายตามโค้ดจริง

ความรู้ที่ต้องมีก่อนอ่านบทนี้#

ส่วนนี้ยาวกว่าบทอื่น เพราะเรื่องเซิร์ฟเวอร์ต้องเข้าใจเครือข่ายก่อนถึงจะอธิบายได้ว่า "ทำไม" อ่านตามลำดับ

IP address, LAN, IP ส่วนตัวกับ IP สาธารณะ#

  • IP address คือที่อยู่ของเครื่องในเครือข่าย IPv4 เขียนเป็นเลข 4 ชุด เช่น 10.20.30.40
  • LAN (Local Area Network) คือเครือข่ายวงเดียวกัน เช่น Wi-Fi ในบ้าน หรือเครือข่ายทั้งมหาวิทยาลัย
  • IP ส่วนตัว (private IP) มี 3 ช่วงที่สงวนไว้ใช้ภายในเท่านั้น คือ 10.0.0.0/8 (10.x.x.x), 172.16.0.0/12 (172.16–172.31.x.x) และ 192.168.0.0/16 (192.168.x.x) เราเตอร์บนอินเทอร์เน็ตจะไม่ส่งแพ็กเก็ตไปหา IP ช่วงนี้ เพราะทุกองค์กรใช้ซ้ำกันได้ ใครอยู่นอกวงจึง "มองไม่เห็น" เครื่องที่มีแค่ IP ส่วนตัว
  • IP สาธารณะ (public IP) คือ IP ที่ไม่ซ้ำกันทั้งโลก เข้าถึงได้จากอินเทอร์เน็ต
  • 127.0.0.1 (localhost) คือ "เครื่องตัวเอง" ใช้ได้เฉพาะโปรแกรมในเครื่องนั้น
  • 100.64.0.0/10 (100.64–100.127.x.x) เป็นช่วงที่ Tailscale ใช้แจก IP ให้เครื่องใน tailnet (อธิบายในหัวข้อ Tailscale)

ในโปรเจกต์นี้: เซิร์ฟเวอร์มี IP 10.x (ส่วนตัว), กล่อง Docker แต่ละกล่องมี IP 172.x ในเครือข่ายภายในของ Docker (ก็เป็น IP ส่วนตัวเหมือนกัน)

NAT, router และ firewall#

  • Router (เราเตอร์) ส่งต่อแพ็กเก็ตระหว่างเครือข่าย เช่น ระหว่าง LAN มหาวิทยาลัยกับอินเทอร์เน็ต
  • NAT (Network Address Translation) คือการที่เราเตอร์เปลี่ยน IP ต้นทางของเครื่องภายใน (10.x) เป็น IP สาธารณะของตัวเองตอนออกอินเทอร์เน็ต แล้วจำไว้ว่าการเชื่อมต่อไหนเป็นของใคร พอคำตอบกลับมาก็ส่งคืนถูกเครื่อง ผลคือ เครื่องข้างในต่อออกไปได้ แต่คนข้างนอกต่อเข้ามาหาเครื่องข้างในเองไม่ได้ เพราะเราเตอร์ไม่รู้ว่าจะส่งให้ใคร ยกเว้นตั้ง port forwarding ไว้ (บอกว่า "ใครเข้ามาที่พอร์ต 443 ให้ส่งไปเครื่อง 10.20.30.40")
  • Firewall คือกฎว่าการเชื่อมต่อแบบไหนผ่านได้ ปกติองค์กรตั้งเป็น "ขาออกอนุญาต ขาเข้าปฏิเสธ" มหาวิทยาลัยก็เป็นแบบนี้

นี่คือปัญหาหลักของโปรเจกต์: เซิร์ฟเวอร์ต่อออกอินเทอร์เน็ตได้ (โหลด Docker image, ส่งอีเมล, ขอใบรับรอง) แต่มือถือที่อยู่นอกมหาวิทยาลัยต่อเข้ามาไม่ได้

พอร์ต และพอร์ตที่ใช้ในโปรเจกต์#

IP บอกว่า "เครื่องไหน" พอร์ต (port) บอกว่า "โปรแกรมไหนในเครื่องนั้น" เป็นเลข 0–65535 เขียนแบบ host:port

พอร์ต โปรโตคอล ใครฟัง (listen) เปิดให้ใครเข้า
22 SSH ระบบปฏิบัติการของเซิร์ฟเวอร์ ผู้ดูแล จากเครือข่ายภายในมหาวิทยาลัย
80 HTTP Caddy เครือข่ายภายใน (ใช้ redirect ไป HTTPS)
443 HTTPS Caddy (บล็อกโดเมน DuckDNS) เครือข่ายภายใน
8080 HTTP Caddy (บล็อกสำหรับ Funnel) เฉพาะกล่อง tailscale ในเครือข่าย Docker
3000 HTTP Backend (Express) เฉพาะ Caddy ในเครือข่าย Docker
1883 MQTT ไม่เข้ารหัส Mosquitto Backend และกล่อง tailscale (ส่งต่อจาก Funnel 8443) ในเครือข่าย Docker เท่านั้น
8883 MQTT + TLS (MQTTS) Mosquitto บอร์ด ESP32 ในอาคารที่ต่อตรง (ทางเลือก ตั้งผ่าน MQTT_DEVICE_URL)
443 (Funnel) HTTPS กล่อง tailscale (ถอด TLS แล้วส่งต่อไป caddy:8080) ทุกคนบนอินเทอร์เน็ต ผ่านชื่อ ts.net
8443 (Funnel) MQTT + TLS ถอดที่กล่อง tailscale แล้วส่ง MQTT ดิบไป mqtt:1883 กล่อง tailscale บอร์ด ESP32 จากทุกเครือข่าย ผ่านชื่อ ts.net (ค่าเริ่มต้น)
3306 MariaDB MariaDB 127.0.0.1 ของเซิร์ฟเวอร์เท่านั้น (ผ่านอุโมงค์ SSH)
3307 (อุโมงค์) ssh บนเครื่อง Windows ของผู้ดูแล HeidiSQL บนเครื่องนั้น

สองพอร์ตสุดท้ายที่มีคำว่า Funnel ไม่ได้ publish บนเครื่อง เพราะกล่อง tailscale เป็นฝ่ายต่อออกไปหา relay ของ Tailscale เอง (ดูหัวข้อ Tailscale)

ตอนพัฒนาบนเครื่องตัวเอง Broker ใน mqtt/ เปิด 1883 ให้ ESP32 ใน Wi-Fi เดียวกันต่อตรง

TCP และ client/server#

  • TCP คือโปรโตคอลขนส่งที่รับประกันว่าข้อมูลถึงครบและเรียงลำดับ เริ่มด้วยการ "จับมือ" (handshake) 3 ขั้น HTTP, HTTPS, MQTT, SSH และ MariaDB ในโปรเจกต์นี้วิ่งบน TCP ทั้งหมด
  • Client/Server: ฝั่งที่เริ่มเชื่อมต่อคือ client ฝั่งที่รอรับคือ server สิ่งสำคัญที่ต้องจำคือ ใครเป็นคนเริ่มเชื่อมต่อ เพราะ firewall/NAT ตัดสินจากตรงนี้ ESP32 เป็น client ของ Mosquitto, แอปเป็น client ของ Caddy, และ (จุดที่ทำให้ Tailscale ใช้ได้) กล่อง tailscale เป็น client ที่ต่อออกไปหาเซิร์ฟเวอร์ของ Tailscale

DNS และชื่อโดเมน#

  • DNS แปลงชื่อเป็น IP เหมือนสมุดโทรศัพท์ เช่น ถาม rmutt-energy.duckdns.org ได้คำตอบเป็น IP
  • Record ที่ต้องรู้: A (ชื่อ → IPv4) และ TXT (ชื่อ → ข้อความ ใช้พิสูจน์ความเป็นเจ้าของโดเมน)
  • Resolver คือเซิร์ฟเวอร์ที่เครื่องเราไปถาม (เช่น DNS ของมหาวิทยาลัย, 1.1.1.1 ของ Cloudflare, 8.8.8.8 ของ Google) resolver จะไปถาม authoritative server ของโดเมนนั้นอีกที (ของ duckdns.org คือเซิร์ฟเวอร์ของ DuckDNS)
  • DuckDNS เป็นบริการชื่อโดเมนย่อยฟรีแบบ <ชื่อ>.duckdns.org เราตั้งได้ว่าชื่อนี้ชี้ไป IP อะไร และมี API ให้เขียน TXT record ด้วย token
  • DNS พอร์ตมาตรฐานคือ 53 (UDP/TCP) บางองค์กรบล็อกไม่ให้เครื่องภายในถาม DNS ภายนอกเอง

HTTP กับ HTTPS, TLS, ใบรับรอง และ CA#

  • HTTP ส่งข้อความเป็นตัวอักษรตรง ๆ ใครดักกลางทางก็อ่านรหัสผ่านได้
  • HTTPS = HTTP ที่วิ่งในช่อง TLS ซึ่งทำสองอย่าง: เข้ารหัส และยืนยันตัวตนของเซิร์ฟเวอร์
  • เซิร์ฟเวอร์ยืนยันตัวตนด้วย ใบรับรอง (certificate) ที่บอกว่า "กุญแจสาธารณะนี้เป็นของโดเมนนี้" ลงลายเซ็นโดย CA (Certificate Authority)
  • Client เชื่อใบรับรองเพราะมี ใบรับรองราก (root CA) ของ CA นั้นเก็บไว้ล่วงหน้า (ในระบบปฏิบัติการ/เบราว์เซอร์ หรือในกรณี ESP32 คือฝังในเฟิร์มแวร์) แล้วไล่ตรวจลายเซ็นเป็นสาย (chain) จากใบของเซิร์ฟเวอร์ → ใบกลาง (intermediate) → ใบราก
  • Client ยังตรวจด้วยว่า ชื่อในใบรับรองตรงกับชื่อที่ตั้งใจต่อ และ ใบยังไม่หมดอายุ (ต้องรู้เวลาปัจจุบัน — นี่คือเหตุผลที่ ESP32 ต้องซิงก์เวลา NTP ก่อนต่อ MQTTS)
  • SNI คือชื่อโดเมนที่ client บอกตอนเริ่ม TLS เซิร์ฟเวอร์ใช้เลือกใบรับรอง และ Funnel relay ใช้เลือกว่าจะส่งต่อไปเครื่องไหน

Let's Encrypt และการพิสูจน์โดเมน (HTTP-01 กับ DNS-01)#

Let's Encrypt เป็น CA ฟรีที่ออกใบรับรองอายุ 90 วันผ่านโปรโตคอลอัตโนมัติชื่อ ACME ก่อนออกใบ ต้องพิสูจน์ว่าเราคุมโดเมนจริง (เรียกว่า challenge) วิธีที่เกี่ยวข้องมี 2 แบบ

HTTP-01 DNS-01
วิธีพิสูจน์ วางไฟล์ไว้ที่ http://<โดเมน>/.well-known/acme-challenge/<token> แล้วให้ Let's Encrypt ต่อเข้ามาอ่านที่พอร์ต 80 เขียน TXT record ชื่อ _acme-challenge.<โดเมน> แล้วให้ Let's Encrypt ถาม DNS สาธารณะ
ต้องเปิดพอร์ตขาเข้าไหม ต้องเปิด 80 จากอินเทอร์เน็ต และโดเมนต้องชี้ IP ที่อินเทอร์เน็ตเข้าถึงได้ ไม่ต้อง เซิร์ฟเวอร์แค่ต่อออกไปหา API ของผู้ให้บริการ DNS
ต้องมีอะไรเพิ่ม ไม่มี API token ของผู้ให้บริการ DNS และ Caddy ต้องมีปลั๊กอินของผู้ให้บริการนั้น

(ยังมี TLS-ALPN-01 ที่ตรวจผ่านพอร์ต 443 ซึ่งติดปัญหาเดียวกับ HTTP-01)

Reverse proxy#

Reverse proxy คือเซิร์ฟเวอร์ตัวหน้าที่รับคำขอทั้งหมดแทน แล้วส่งต่อให้โปรแกรมข้างหลัง ในโปรเจกต์คือ Caddy ทำหน้าที่ ถอด TLS (Backend ไม่ต้องรู้เรื่องใบรับรอง), ส่ง /api/* ไป Backend, เสิร์ฟไฟล์เว็บ, ใส่หัวความปลอดภัย พอผ่าน proxy แล้ว Backend จะเห็น IP ต้นทางเป็น IP ของ proxy proxy จึงแนบ IP จริงของผู้ใช้มาในหัว X-Forwarded-For (XFF) และ Backend ต้องรู้ว่า "เชื่อหัวนี้ได้กี่ชั้น" (เรื่อง TRUST_PROXY)

VPN และ overlay network#

  • VPN สร้าง "เครือข่ายเสมือน" ทับบนอินเทอร์เน็ต เครื่องที่อยู่คนละที่คุยกันเหมือนอยู่ LAN เดียว ข้อมูลระหว่างทางถูกเข้ารหัส
  • Overlay network / mesh VPN คือ VPN ที่ทุกเครื่องต่อกันตรง ๆ เป็นตาข่าย ไม่ต้องผ่านเซิร์ฟเวอร์กลางตัวเดียว Tailscale เป็นแบบนี้ สร้างบน WireGuard (โปรโตคอล VPN สมัยใหม่ที่เร็วและโค้ดน้อย)

SSH และ SSH tunnel#

  • SSH (พอร์ต 22) คือการเข้าไปสั่งงานเซิร์ฟเวอร์ผ่านช่องเข้ารหัส ยืนยันตัวด้วยรหัสผ่านหรือ SSH key (คู่กุญแจ: กุญแจลับอยู่ที่เครื่องเรา กุญแจสาธารณะอยู่ใน ~/.ssh/authorized_keys บนเซิร์ฟเวอร์) scp คือคัดลอกไฟล์ผ่าน SSH
  • SSH tunnel (port forwarding) ssh -L 3307:127.0.0.1:3306 user@server แปลว่า "เปิดพอร์ต 3307 บนเครื่องฉัน อะไรที่เข้ามาให้ส่งผ่านช่อง SSH ไปออกที่เซิร์ฟเวอร์ แล้วต่อไป 127.0.0.1:3306 ของเซิร์ฟเวอร์" ทำให้เข้าถึงบริการที่ผูกไว้กับ localhost ของเซิร์ฟเวอร์ได้ โดยไม่ต้องเปิดบริการนั้นออกเครือข่าย

Docker แบบย่อ (ที่ต้องใช้ในบทนี้)#

  • Image = แม่แบบของโปรแกรมพร้อมทุกอย่างที่ต้องใช้ Container = image ที่กำลังรัน
  • Dockerfile = สูตรสร้าง image docker compose = ไฟล์ YAML บอกว่าจะรันกี่กล่อง ต่อกันอย่างไร
  • Port publishing "443:443" = เปิดพอร์ตของเครื่องจริงแล้วส่งเข้ากล่อง ถ้าไม่ publish กล่องอื่นในเครือข่าย Docker ยังเข้าได้ แต่นอกเครื่องเข้าไม่ได้
  • Volume / bind mount ./db/data:/var/lib/mysql = ผูกโฟลเดอร์จริงเข้าไปในกล่อง ข้อมูลไม่หายเมื่อสร้างกล่องใหม่
  • Docker network: กล่องในไฟล์ compose เดียวกันอยู่เครือข่ายเดียวกันและเรียกกันด้วยชื่อ service ได้ (db, mqtt, backend, caddy) เพราะ Docker มี DNS ภายใน

MQTT แบบย่อ#

MQTT เป็นโปรโตคอลส่งข้อความแบบ publish/subscribe ผ่านตัวกลางชื่อ Broker (ที่นี่คือ Mosquitto) บอร์ดและ Backend เป็น client ทั้งคู่ ต่อเข้า Broker แล้วส่ง/รับข้อความตาม topic เช่น rmutt/ac/... และ rmutt/occupancy/... mqtt:// คือพอร์ต 1883 ไม่เข้ารหัส mqtts:// คือมี TLS (พอร์ตมาตรฐาน 8883 แต่ทาง Funnel ในโปรเจกต์นี้ใช้ 8443) (รายละเอียด topic อยู่ในบท MQTT)

สถานการณ์จริงของเซิร์ฟเวอร์#

เซิร์ฟเวอร์อยู่หลัง firewall มหาวิทยาลัย#

  อินเทอร์เน็ต ──X──▶ firewall มหาวิทยาลัย ──▶ 10.x (เซิร์ฟเวอร์)     ขาเข้า: ถูกปิด
  อินเทอร์เน็ต ◀───── firewall มหาวิทยาลัย ◀── 10.x (เซิร์ฟเวอร์)     ขาออก: ได้ (HTTPS 443 ฯลฯ)
  เครื่องในอาคาร ──────────────────────────▶ 10.x (เซิร์ฟเวอร์)     ภายในวงเดียวกัน: ได้

ผลที่ตามมา

  • คนในอาคาร (เบราว์เซอร์ และบอร์ด ESP32 ที่ต่อตรง) ต่อเซิร์ฟเวอร์ได้ เพราะอยู่ในเครือข่ายเดียวกัน
  • คนนอกมหาวิทยาลัย (เจ้าหน้าที่เปิดแอปจากบ้าน และบอร์ด ESP32 ที่ต่อ Wi-Fi ข้างนอก) ต่อไม่ได้ ถ้าไม่มีอะไรช่วย
  • Let's Encrypt ก็ต่อเข้ามาตรวจ HTTP-01 ไม่ได้

DuckDNS ชี้ไปที่ IP ภายใน#

โดเมน rmutt-energy.duckdns.org ถูกตั้งที่ DuckDNS ให้ชี้ไป IP ภายใน 10.x ของเซิร์ฟเวอร์ (ดูคอมเมนต์ใน lib/config/api_config.dart: "rmutt-energy.duckdns.org ชี้ไป IP ภายในมหาวิทยาลัย ใช้ได้เฉพาะในตึก")

  • ใครถาม DNS ก็ได้คำตอบเป็น 10.x เหมือนกันทั้งโลก
  • เครื่องในอาคารเอา 10.x ไปต่อได้จริง
  • เครื่องนอกมหาวิทยาลัยได้ 10.x ไปก็ต่อไม่ถึง (IP ส่วนตัวไม่ถูกส่งผ่านอินเทอร์เน็ต)
  • บอร์ด ESP32 ที่ต่อ Wi-Fi นอกมหาวิทยาลัยเจอปัญหาเดียวกัน (ถ้าบอร์ดต่อ rmutt-energy.duckdns.org:8883 จะใช้ได้เฉพาะในอาคาร) ค่าเริ่มต้นของบอร์ดจึงต่อผ่านชื่อ ts.net พอร์ต 8443 (ดูหัวข้อ "ESP32 ต่อ MQTTS")

ทำไมยังต้องมีชื่อโดเมน ทั้งที่ใช้ได้แค่ในตึก: เพราะใบรับรอง TLS ออกให้ชื่อโดเมน ไม่ใช่ให้ IP ส่วนตัว ถ้าไม่มีชื่อ ก็ไม่มี HTTPS ที่เบราว์เซอร์และ ESP32 เชื่อ และถ้า IP เครื่องเปลี่ยน แก้ที่ DuckDNS ที่เดียว บอร์ดทุกตัวไม่ต้องตั้งใหม่

ระวัง

เราเตอร์/DNS บางแห่งมี "DNS rebinding protection" ที่ทิ้งคำตอบ DNS สาธารณะซึ่งชี้ไป IP ส่วนตัว ถ้าเครื่องในอาคารบางเครื่องเปิดโดเมนไม่ได้ทั้งที่อยู่ในวงเดียวกัน ให้ลอง nslookup rmutt-energy.duckdns.org ดูก่อนว่าได้ IP กลับมาหรือไม่

ใบรับรองผ่าน DuckDNS ด้วย DNS-01#

HTTP-01 ใช้ไม่ได้ เพราะ (1) โดเมนชี้ IP ส่วนตัว Let's Encrypt ซึ่งอยู่บนอินเทอร์เน็ตไม่มีทางต่อถึง และ (2) firewall ปิดขาเข้า Caddy ในโปรเจกต์นี้จึง build ใหม่ให้มีปลั๊กอิน caddy-dns/duckdns (ไฟล์ caddy.Dockerfile) แล้วสั่งใน Caddyfile ให้ใช้ DNS-01

 Caddy (ในเซิร์ฟเวอร์ 10.x)                 อินเทอร์เน็ต
 ─────────────────────────                 ───────────
 1. ขอใบให้ rmutt-energy.duckdns.org  ───▶  Let's Encrypt (ACME API)
                                      ◀───  "เขียน TXT นี้ที่ _acme-challenge.<โดเมน>"
 2. เรียก API DuckDNS ด้วย DUCKDNS_TOKEN ──▶  DuckDNS ตั้ง TXT record
 3. รอ 60 วินาที (propagation_delay)
 4. บอก Let's Encrypt ว่าพร้อม        ───▶  Let's Encrypt ถาม DNS ของ DuckDNS เอง
                                             เจอ TXT ถูกต้อง → ออกใบ
 5. ดาวน์โหลดใบ เก็บที่ /data (= ./caddy/data)

ทุกขั้นเป็นการเชื่อมต่อขาออกจากเซิร์ฟเวอร์ (HTTPS 443) ซึ่ง firewall อนุญาต จึงได้ใบรับรองจริงที่เชื่อถือได้ทั่วโลก แม้เครื่องจะไม่มีใครข้างนอกเข้าถึงได้เลย

การตั้งค่าเพิ่ม 3 บรรทัดใน tls { ... } มีเหตุผลเฉพาะของเครือข่ายมหาวิทยาลัย (คอมเมนต์ใน Caddyfile บรรทัด 67–76)

  • resolvers 1.1.1.1 8.8.8.8 — ก่อนเขียน TXT Caddy ต้องหาว่าชื่อ _acme-challenge.rmutt-energy.duckdns.org อยู่ใน zone ไหน DNS ของมหาวิทยาลัยตอบ SERVFAIL ตอนถามเรื่องนี้ จึงให้ไปถาม DNS สาธารณะแทน
  • propagation_delay 60s — หลังเขียน TXT ให้รอ 60 วินาทีให้ DuckDNS กระจายค่าก่อน
  • propagation_timeout -1 — ปิดการที่ Caddy วนถาม DNS เองว่า TXT ขึ้นหรือยัง (ขั้นนี้ต้องคุย DNS ภายนอกซ้ำหลายรอบ และเครือข่ายมหาวิทยาลัยอาจบล็อกพอร์ต 53) รอครบเวลาแล้วให้ Let's Encrypt ตรวจเลย

Caddy ต่ออายุใบให้อัตโนมัติก่อนหมดอายุ (ใบอายุ 90 วัน) ด้วยวิธีเดียวกัน

ใบรับรองใบเดียว ใช้สองที่: Caddy กับ Mosquitto#

Mosquitto ไม่ขอใบรับรองเองได้ จึงใช้ใบเดียวกับ Caddy สคริปต์ deploy/sync-mqtt-cert.sh (cron ทุกวัน 03:10 ตั้งโดย setup-vps.sh) ก๊อป caddy/data/caddy/certificates/.../<โดเมน>.crt และ .key ไปเป็น mosquitto/certs/fullchain.pem และ privkey.pem ให้เจ้าของเป็น uid 1883 (user ของ mosquitto ในกล่อง) แล้วส่งสัญญาณ docker kill -s HUP rmutt-mqtt ให้ Mosquitto โหลดใบใหม่โดยบอร์ดที่ต่ออยู่ไม่หลุด ถ้าใบไม่เปลี่ยน (cmp -s) ก็ไม่ทำอะไร

ทำไม

ถ้าไม่มี cron นี้ Caddy ต่ออายุใบของตัวเองได้ แต่ Mosquitto ยังถือใบเก่า พอครบ 90 วัน บอร์ด ESP32 ที่ต่อตรงพอร์ต 8883 ทุกตัวจะต่อ MQTTS ไม่ได้พร้อมกันทั้งอาคาร ระบบปิดแอร์อัตโนมัติหยุดทันที

หมายเหตุ

ใบรับรองใบนี้ใช้เฉพาะทางที่บอร์ดต่อตรง 8883 เท่านั้น ทาง Funnel 8443 บอร์ดเห็นใบ ts.net ซึ่งกล่อง tailscale ถอด TLS ให้ Mosquitto ไม่เห็น TLS ชุดนั้นเลย (เห็นแค่ MQTT ดิบที่ listener 1883) บอร์ดที่ต่อทางนี้จึงไม่พึ่ง cron sync-mqtt-cert.sh

ESP32 ต่อ MQTTS ผ่าน Funnel 8443 (หรือ 8883 ตรง) และใบรับรองรากในเฟิร์มแวร์#

ตอนตั้งค่าบอร์ดผ่านบลูทูธ Backend คำนวณค่าที่จะส่งให้บอร์ดจาก MQTT_DEVICE_URL (backend/src/utils/mqtt-provisioning.js แยกเป็น mqttHost, mqttPort, mqttTls = true เมื่อ URL ขึ้นต้น mqtts:// และถ้า URL ไม่ระบุพอร์ตจะใช้ 8883) ค่าเริ่มต้นใน docker-compose.yml ตอนนี้คือ mqtts://rmutt-energy.tailb292b4.ts.net:8443 บอร์ดจึงรู้จักเซิร์ฟเวอร์ในชื่อ ts.net พอร์ต 8443 และจำค่านี้ไว้ในหน่วยความจำของบอร์ด

ถ้าจะให้บอร์ดในมหาวิทยาลัยต่อตรง ให้ตั้ง MQTT_DEVICE_URL=mqtts://<DOMAIN>:8883 ใน .env (compose เขียนเป็น ${MQTT_DEVICE_URL:-...} คือใช้ค่าจาก .env ก่อน ถ้าว่างใช้ค่า Funnel) ค่านี้มีผลกับบอร์ดที่ตั้งค่าหลังจากนั้น บอร์ดที่ตั้งค่าไปแล้วยังจำค่าเดิมอยู่

ฝั่งเฟิร์มแวร์ (firmware/rmutt_esp32_air/rmutt_esp32_air.ino ฟังก์ชัน connectMqtt() และ ensureClockSynced())

  1. ซิงก์เวลา NTP (pool.ntp.org, time.google.com) ให้ได้ก่อน ถ้าเวลาไม่ตรงจะตรวจอายุใบรับรองไม่ผ่าน
  2. secureClient.setCACert(LETSENCRYPT_CA) — ใช้ใบรากที่ฝังไว้ในไฟล์ letsencrypt_ca.h
  3. ต่อ TLS ไปที่ host:port ที่ได้จาก provisioning (ค่าเริ่มต้น rmutt-energy.tailb292b4.ts.net:8443) ตรวจทั้งสายใบรับรองและชื่อโฮสต์
  4. ส่ง MQTT CONNECT ด้วย username/password ของบอร์ดตัวนั้น

ไฟล์ letsencrypt_ca.h (เหมือนกันทั้งบอร์ดแอร์และบอร์ดเซ็นเซอร์) สร้างโดย firmware/update-root-ca.ps1 ซึ่งดาวน์โหลดใบราก ISRG Root X1 (สาย RSA หมดอายุ 2035-06-04) และ ISRG Root X2 (สาย ECDSA หมดอายุ 2040-09-17) มาใส่ในตัวแปร LETSENCRYPT_CA ใส่ทั้งสองใบเพราะ Let's Encrypt อาจออกใบให้จากสายใดก็ได้ ถ้ามีใบเดียวแล้ววันหนึ่งได้ใบจากอีกสาย บอร์ดทุกตัวจะต่อไม่ได้จนกว่าจะแฟลชใหม่

ทำไม

ใบรับรอง ts.net ที่กล่อง tailscale ใช้ถอด TLS ที่พอร์ต 8443 ออกโดย Let's Encrypt เหมือนกัน ใบรากชุดเดิมในเฟิร์มแวร์จึงตรวจผ่านโดยไม่ต้องแก้เฟิร์มแวร์หรือแฟลชบอร์ดใหม่ แค่เปลี่ยนค่า host/port ที่ Backend ส่งให้ตอน provisioning

ใบรากชุดเดียวกันใช้ตอนอัปเดตเฟิร์มแวร์ผ่าน Wi-Fi (OTA) ด้วย: Backend สร้าง URL https://<mqtt_host ของบอร์ด>/firmware/<ไฟล์>.bin (backend/src/utils/firmware.js ฟังก์ชัน firmwareUrl) แล้วบอร์ดดาวน์โหลดด้วย runHttpsOta(url, LETSENCRYPT_CA, ...) เมื่อ host ของบอร์ดเป็นชื่อ ts.net (ค่าเริ่มต้น) คำขอ HTTPS พอร์ต 443 นี้จึงวิ่งผ่าน Funnel 443 → caddy:8080 ซึ่งบล็อก (app) เสิร์ฟ /firmware/* ให้ ส่วนบอร์ดที่ต่อตรงจะดาวน์โหลดจาก Caddy พอร์ต 443 ของโดเมน DuckDNS ฟังก์ชัน otaUrlAllowed ในเฟิร์มแวร์บังคับให้ URL ใช้ host เดียวกับ MQTT host ของบอร์ด จึงไม่ต้องแก้อะไรเมื่อเปลี่ยนค่าเริ่มต้น

ระวัง

ถ้าวันหนึ่งเปลี่ยนไปใช้ใบรับรองของมหาวิทยาลัย (ไม่ใช่ Let's Encrypt) ต้องรัน update-root-ca.ps1 -Urls <url ใบรากของผู้ออก> แล้วแฟลชบอร์ดใหม่ทุกตัว ไม่งั้นบอร์ดต่อ MQTTS ไม่ได้ (เขียนไว้ใน deploy/DEPLOY.md หัวข้อ "ใช้ใบรับรองของมหาวิทยาลัย")

หมายเหตุ

ค่าเริ่มต้น (Funnel) บอร์ดต้องออกอินเทอร์เน็ตไปยังชื่อ ts.net ได้ทั้งพอร์ต 8443 (MQTTS) และ 443 (ดาวน์โหลดเฟิร์มแวร์ OTA) ถ้า Wi-Fi ที่ติดตั้งมีนโยบายบล็อกพอร์ตขาออก ต้องขอเปิดทั้งสองพอร์ต ส่วนบอร์ดที่ต่อตรงต้องถึงเซิร์ฟเวอร์ได้ที่ 8883 และ 443 แต่หัวข้อ Wi-Fi ใน SERVER_REQUIREMENTS.md เขียนแค่ 8883 ถ้าฝ่ายไอทีทำ VLAN IoT แยก ต้องขอ 443 ไปที่เซิร์ฟเวอร์ด้วย

Tailscale ในเชิงลึก#

Tailscale คืออะไร#

Tailscale คือบริการ mesh VPN ที่สร้างบน WireGuard แนวคิดมีไม่กี่ข้อ

  • Tailnet = เครือข่ายส่วนตัวของบัญชีเรา ทุกเครื่องที่ล็อกอินบัญชีเดียวกันเป็นสมาชิก แต่ละเครื่องได้ IP ในช่วง 100.64.0.0/10 ที่ไม่ซ้ำกันใน tailnet
  • การต่อแบบ mesh เครื่องสองเครื่องใน tailnet พยายามต่อกันตรง ๆ (ผ่าน NAT traversal) ถ้าต่อตรงไม่ได้ก็ผ่าน relay ที่เรียกว่า DERP ของ Tailscale ข้อมูลถูกเข้ารหัสด้วย WireGuard ตลอดทาง แม้ผ่าน relay
  • Control plane (เซิร์ฟเวอร์ของ Tailscale) ทำแค่แจกกุญแจและบอกว่าใครอยู่ที่ไหน ไม่ได้แบกข้อมูลของเรา
  • MagicDNS ตั้งชื่อให้ทุกเครื่องอัตโนมัติ ชื่อเต็มคือ <ชื่อเครื่อง>.<ชื่อ tailnet>.ts.net ในโปรเจกต์นี้คือ rmutt-energy.tailb292b4.ts.net (rmutt-energy มาจาก hostname/TS_HOSTNAME ในไฟล์ compose, tailb292b4 คือชื่อ tailnet ที่ Tailscale สุ่มให้)
  • HTTPS ของ ts.net Tailscale ออกใบรับรอง Let's Encrypt ให้ชื่อ *.ts.net ของเครื่องเราได้ ทำให้ไม่ต้องจัดการใบเอง (ใบนี้ใช้ถอด TLS ทั้งพอร์ต 443 ของเว็บและพอร์ต 8443 ของ MQTT และ Let's Encrypt เป็นผู้ออก จึงตรงกับใบรากที่ฝังในเฟิร์มแวร์)

Serve กับ Funnel ต่างกันอย่างไร#

Tailscale Serve Tailscale Funnel
ใครเข้าได้ เฉพาะเครื่องที่อยู่ใน tailnet (ต้องลงแอป Tailscale และล็อกอิน) ใครก็ได้บนอินเทอร์เน็ต ไม่ต้องลงอะไร
ใช้ทำอะไร แชร์บริการให้ทีมภายใน เปิดเว็บ/API (และพอร์ต TCP อย่าง MQTT) สู่สาธารณะ
ชื่อที่ใช้ <เครื่อง>.<tailnet>.ts.net ชื่อเดียวกัน

Funnel คือ "Serve + เปิดให้คนนอก tailnet เข้าได้" ในโปรเจกต์ใช้ Funnel เพราะผู้ใช้คือเจ้าหน้าที่ที่เปิดแอปจากมือถือ ซึ่งไม่ได้อยู่ใน tailnet และเราไม่ต้องการให้ทุกคนลงแอป Tailscale และเพราะบอร์ด ESP32 ติดตั้ง Tailscale ไม่ได้ จึงต้องมีชื่อสาธารณะให้บอร์ดต่อ MQTT เข้ามา

โหมด userspace (TS_USERSPACE)#

ปกติ Tailscale สร้างการ์ดเครือข่ายเสมือน (tun) ในระบบปฏิบัติการ ต้องใช้อุปกรณ์ /dev/net/tun และสิทธิ์ NET_ADMIN ใน Docker ซึ่งเป็นสิทธิ์สูง โหมด userspace ให้ Tailscale จัดการแพ็กเก็ตเองในโปรแกรม ไม่แตะการตั้งค่าเครือข่ายของเครื่อง ผลคือไฟล์ compose ไม่ต้องมี devices, cap_add หรือ network_mode: host กล่องนี้เป็นกล่องธรรมดาที่แย่ที่สุดก็แค่ต่อออกอินเทอร์เน็ตและต่อ caddy:8080 กับ mqtt:1883 ในเครือข่าย Docker ข้อแลกเปลี่ยนคือประสิทธิภาพต่ำกว่าเล็กน้อย ซึ่งไม่มีผลกับเว็บขนาดนี้

ล็อกอินครั้งแรกและ TS_AUTHKEY#

กล่อง tailscale ต้องพิสูจน์ว่าเป็นของบัญชีเรา มี 2 วิธี

  1. ไม่ตั้ง TS_AUTHKEY (ค่าเริ่มต้นใน compose คือว่าง) ดู docker compose logs tailscale จะเจอลิงก์ล็อกอิน เปิดในเบราว์เซอร์แล้วอนุมัติ
  2. ตั้ง TS_AUTHKEY=tskey-auth-... ที่สร้างจากหน้าแอดมินของ Tailscale เครื่องเข้า tailnet เองโดยไม่ต้องกดอนุมัติ เหมาะกับการสร้างใหม่อัตโนมัติ

หลังล็อกอินสำเร็จ ตัวตนของเครื่องถูกเก็บใน TS_STATE_DIR=/var/lib/tailscale ซึ่ง mount ไว้ที่ ./tailscale/state บนเซิร์ฟเวอร์ ครั้งต่อไปที่สร้างกล่องใหม่จึงไม่ต้องล็อกอินอีก และชื่อ ts.net ไม่เปลี่ยน (ถ้าลบโฟลเดอร์นี้ จะได้เครื่องใหม่ และอาจได้ชื่อต่อท้ายเป็น -1 ซึ่งทำให้แอปที่ฝังชื่อเดิมไว้ใช้ไม่ได้)

หมายเหตุ

การเปิด Funnel ต้องทำที่ฝั่งบัญชี Tailscale ด้วย: เปิด MagicDNS และ HTTPS Certificates ในหน้าแอดมิน และให้ node มีสิทธิ์ Funnel (ในนโยบาย ACL ของ tailnet) ขั้นตอนนี้ทำในเว็บของ Tailscale ไม่มีในโค้ดของโปรเจกต์

Funnel กับ TCP: HTTPS handler, TCPForward ดิบ และ TerminateTLS ต่างกันอย่างไร#

Funnel ไม่ได้ส่งต่อได้แค่เว็บ แต่ส่งต่อพอร์ต TCP ได้ด้วย โดยมีเงื่อนไขว่าต้องเป็นการเชื่อมต่อแบบ TLS (เพราะ relay ใช้ SNI เลือกเครื่อง) และเป็นพอร์ต 443, 8443 หรือ 10000 รูปแบบในไฟล์ serve.json ที่เกี่ยวข้องมี 3 แบบ

รูปแบบ ใครถอด TLS ปลายทางเห็นอะไร ในโปรเจกต์นี้
"HTTPS": true + ส่วน Web กล่อง tailscale HTTP ที่อ่าน path ได้ และมีหัว X-Forwarded-For พอร์ต 443 → caddy:8080
"TCPForward" อย่างเดียว (raw TCP) ไม่มีใครถอดที่กล่อง tailscale ไบต์ TLS เดิมจากไคลเอนต์ ปลายทางต้องถอดเองด้วยใบรับรองของตัวเอง ไม่ได้ใช้ (ถ้าส่งไป mqtt:8883 Mosquitto จะแสดงใบ DuckDNS ซึ่งชื่อไม่ตรงกับ ts.net บอร์ดจึงปฏิเสธ)
"TCPForward" + "TerminateTLS" กล่อง tailscale (ใบ ts.net) TCP ดิบที่ถอดแล้ว (ที่นี่คือ MQTT ธรรมดา) พอร์ต 8443 → mqtt:1883

เลือก TerminateTLS ที่กล่อง tailscale แทนการให้ Mosquitto ทำ TLS เองที่ 8883 เพราะ (1) บอร์ดตรวจชื่อโฮสต์ในใบรับรองให้ตรงกับชื่อที่ตั้งใจต่อ บอร์ดต่อชื่อ ts.net แต่ใบของ Mosquitto ออกให้ชื่อ DuckDNS จึงไม่ตรง (2) ใบ ts.net มี Let's Encrypt ออกให้และ tailscale จัดการเอง ไม่ต้องก๊อปใบด้วย cron (3) Mosquitto ไม่ต้องเปลี่ยนอะไรเลย (listener 1883 ที่ Backend ใช้อยู่แล้ว) ผลแลกเปลี่ยนคือช่วงสุดท้ายจากกล่อง tailscale ไป mqtt:1883 เป็น MQTT ไม่เข้ารหัส แต่เป็นการวิ่งในเครือข่าย Docker ของเครื่องเดียวกัน

ทำไมเป็นพอร์ต 8443: Funnel เปิดสู่สาธารณะได้เฉพาะ 443, 8443 และ 10000 พอร์ต 443 ถูกเว็บใช้อยู่แล้ว (หนึ่งพอร์ตผูกกับกฎเดียว) และ 8883 ไม่อยู่ในรายการที่อนุญาต จึงเหลือ 8443 หรือ 10000 ซึ่งเลือก 8443 (commit ไม่ได้ระบุเหตุผลเพิ่มว่าทำไมไม่ใช้ 10000)

ทำไมเปิดทางเข้าแค่สองจุด: caddy:8080 และ mqtt:1883#

Serve ส่งต่อได้ทุกที่อยู่ที่กล่อง tailscale มองเห็น ถ้าชี้ไป backend:3000 หรือ db:3306 ก็เปิดออกอินเทอร์เน็ตได้ทันที เราเลือกเปิดเพียงสองปลายทาง และเหตุผลของแต่ละข้อ

  1. Caddy เป็นประตูเดียวของเว็บและ API ใส่หัวความปลอดภัย (CSP, HSTS), เลือกว่า /api/* ไป Backend ส่วนที่เหลือเป็นไฟล์เว็บ ถ้าข้ามไป Backend ตรง ๆ จะไม่มีกฎพวกนี้
  2. /firmware/* ก็ผ่าน Funnel 443 ได้ด้วย ไฟล์ .bin ถูกเสิร์ฟผ่านบล็อก (app) ที่ใช้ร่วมกัน จึงดาวน์โหลดผ่าน Funnel ได้เช่นกัน (เป็นไฟล์เฟิร์มแวร์ ไม่มีรหัสผ่านในนั้น และ Backend ยังกันการสั่งอัปเดตด้วยสิทธิ์ผู้ใช้) นี่คือสิ่งที่ทำให้ OTA ของบอร์ดที่ใช้ชื่อ ts.net ทำงานได้
  3. พอร์ต 8080 แยกจาก 443 ทำให้แยกได้ว่าคำขอมาจากทางไหน (ดู trusted_proxies ด้านล่าง) และไม่ต้องให้ Caddy ขอใบรับรองซ้ำสำหรับชื่อ ts.net (ใบจัดการโดยกล่อง tailscale แล้ว)
  4. MQTT ผ่านพอร์ต 8443 แยกต่างหาก ไม่ผ่าน Caddy เพราะ Caddy พูดแต่ HTTP ส่ง MQTT ตรงไป Mosquitto ซึ่งยังบังคับ allow_anonymous false กับบัญชี Dynamic Security รายบอร์ด จึงเปิดพอร์ตนี้ให้อินเทอร์เน็ตได้โดยยังมีด่านล็อกอินและ ACL (บอร์ดเห็นเฉพาะ topic ของตัวเอง)

สิ่งที่ไม่ถูกเปิดออกอินเทอร์เน็ตคือ backend:3000, db:3306 และ SSH

ระวัง

พอร์ต 8443 ทำให้ Broker "เข้าถึงได้จากอินเทอร์เน็ต" ความปลอดภัยของ MQTT จึงพึ่ง 2 อย่าง: TLS ระหว่างบอร์ดกับกล่อง tailscale และ username/password รายบอร์ด (รหัสเป็นค่า HMAC จาก Device ID กับ secret ของเซิร์ฟเวอร์ เดาไม่ได้ง่าย) ที่ยังไม่มีคือการจำกัดอัตราการลองรหัสต่อ IP ที่ชั้น MQTT (Mosquitto เห็น IP ต้นทางเป็นกล่อง tailscale ทุกคำขอ) ถ้าไม่ต้องการเปิดแบบนี้ ตั้ง MQTT_DEVICE_URL=mqtts://<DOMAIN>:8883 ใน .env เพื่อให้บอร์ดที่ตั้งค่าใหม่ต่อตรงในอาคาร และเอาส่วน 8443 ออกจาก serve.json (บรรทัด 4–7 และบรรทัด 18 พร้อมแก้เครื่องหมายจุลภาคให้ JSON ยังถูกต้อง)

  • ที่อยู่ ts.net ทำงานทั้งในและนอกมหาวิทยาลัย แอปจึงมีที่อยู่เดียวที่ใช้ได้ทุกที่ ไม่ต้องให้ผู้ใช้เลือก
  • flutter run เฉย ๆ ก็ต่อเซิร์ฟเวอร์จริงได้ ถ้าจะทดสอบกับ Backend ในเครื่องให้ override ตามคอมเมนต์ในไฟล์ (http://10.0.2.2:3000/api สำหรับ Android Emulator, http://127.0.0.1:3000/api สำหรับ Windows)
  • เว็บแอปไม่ต้องฝังที่อยู่ใด ๆ: webapp/assets/js/config.js ตั้ง API_BASE = '/api' (path แบบสัมพัทธ์) เบราว์เซอร์จึงเรียกโดเมนที่เปิดหน้าเว็บอยู่เองไม่ว่าจะเป็น duckdns หรือ ts.net และไม่ติด CORS การรับ ?api= ทำได้เฉพาะเมื่อเปิดจาก localhost (กันลิงก์หลอกให้ส่งรหัสผ่านไปเว็บอื่น)
ระวัง

ถ้าเปิดเว็บผ่านชื่อ ts.net แล้วกด POST (เช่นล็อกอิน) เบราว์เซอร์จะส่งหัว Origin: https://rmutt-energy.tailb292b4.ts.net ซึ่ง Backend ตรวจกับรายการใน APP_ORIGIN (createCorsOptions ใน backend/src/app.js บรรทัด 77–98) ใน compose บรรทัด 88 APP_ORIGIN: https://${DOMAIN},${PUBLIC_URL:-} ดังนั้นต้องตั้ง PUBLIC_URL=https://rmutt-energy.tailb292b4.ts.net ใน .env บนเซิร์ฟเวอร์ (ตัวแปรนี้ไม่อยู่ใน .env.example) แอปมือถือไม่ได้ส่ง Origin จึงไม่โดนตรวจ (เงื่อนไข !origin ผ่านเสมอ)

TRUST_PROXY=2 กับ trusted_proxies ของ Caddy#

ปัญหา: หน้า login มี rate limit ใน backend/src/routes/auth.js (loginLimiter: หน้าต่าง 15 นาที จำกัด 10 ครั้งต่อ IP) ตัวจำกัดนับตาม req.ip ซึ่ง Express คำนวณจากหัว X-Forwarded-For (XFF) ตามค่า trust proxy ถ้าไม่ตั้ง ทุกคำขอจะเห็น IP ของ proxy ตัวสุดท้าย แล้วคนเดียวพิมพ์รหัสผิด 10 ครั้งจะล็อกคนทั้งระบบ 15 นาที

เส้นทางสองทางมีจำนวนชั้น proxy ต่างกัน

  • Express trust proxy = 2 แปลว่า "เชื่อ 2 hop ท้ายสุด" req.ip คือ IP ฝั่งซ้ายสุดที่อยู่ลึกกว่า 2 hop นับจากท้าย ได้ IP จริงของผู้ใช้ทั้งสองทาง (ทางโดเมนหลักมี XFF แค่ 1 ค่า จึงได้ค่านั้น) ตั้งใน deploy/docker-compose.yml บรรทัด 85 อ่านโดย trustProxyFromEnv ใน backend/src/config.js แล้วส่งให้ app.set('trust proxy', ...) ใน backend/src/app.js บรรทัด 33
  • Caddy trusted_proxies static private_ranges (Caddyfile บรรทัด 4–6) บอก Caddy ว่า "คำขอที่มาจากช่วง IP ส่วนตัว เชื่อหัว XFF ที่แนบมาได้" ใช้เฉพาะ server :8080 ซึ่งรับจากกล่อง tailscale (IP 172.x ใน Docker) ถ้าไม่ตั้ง Caddy จะทิ้ง XFF ที่ได้มา แล้วเขียนใหม่เป็น IP ของ tailscale ทำให้ทุกคนเป็น IP เดียวกัน
  • ปลอม XFF ไม่ได้ในทางโดเมนหลัก เพราะ Caddy ไม่เชื่อ XFF จากผู้ใช้ทั่วไป (ไม่อยู่ใน trusted_proxies) จึงทิ้งแล้วใส่ค่าที่ตัวเองเห็น
ระวัง

ค่า TRUST_PROXY ต้องตรงกับจำนวนชั้นจริง ถ้ามากเกิน ผู้โจมตีใส่ XFF ปลอมเพื่อเปลี่ยน IP ตัวเองหนี rate limit ได้ ถ้าน้อยเกิน ทุกคนถูกนับเป็นคนเดียว config.js จึงแปลงค่า true เป็น 1 และปล่อยว่าง = false (ไม่เชื่อเลย เหมาะตอนรันตรงในเครื่อง) หมายเหตุ: คอมเมนต์ใน config.js บรรทัด 10 ยังเขียน "Caddy = 1" ซึ่งเก่ากว่าค่าจริงใน compose

ปิด Funnel ทำอย่างไร#

  1. ปิดทันที: docker compose stop tailscale ทางโดเมนหลัก (เว็บในอาคาร) และบอร์ดที่ต่อตรง 8883 ไม่กระทบ แต่แอปมือถือและบอร์ดที่ตั้งค่าให้ต่อ ts.net:8443 จะต่อเซิร์ฟเวอร์ไม่ได้จนกว่าจะเปิดกลับ (Backend ที่ต่อ Broker ภายในไม่กระทบ)
  2. ปิดถาวร: ลบ service tailscale ออกจาก compose, ลบบล็อก http://:8080 ออกจาก Caddyfile, ตั้ง TRUST_PROXY: 1 กลับ (เพราะเหลือชั้นเดียว), ปล่อย PUBLIC_URL ว่าง และตั้ง MQTT_DEVICE_URL=mqtts://<DOMAIN>:8883 ใน .env (ค่าเริ่มต้นชี้ ts.net:8443 ซึ่งจะใช้ไม่ได้อีก)
  3. ลบเครื่อง rmutt-energy ออกจากหน้าแอดมิน Tailscale เพื่อถอนชื่อ ts.net
  4. ต้อง build แอปมือถือใหม่ด้วย --dart-define=API_BASE_URL=https://<ที่อยู่ใหม่>/api เพราะค่าเริ่มต้นถูกฝังตอน build แอปรุ่นเก่าจะต่อไม่ได้ และบอร์ดที่เคยตั้งค่าให้ต่อ ts.net:8443 ต้องตั้งค่าใหม่ (provisioning) ให้ชี้ไปที่อยู่ใหม่

เปรียบเทียบกับทางเลือกอื่นอย่างตรงไปตรงมา#

ทางเลือก ได้อะไร ติดอะไร เหมาะกับสถานการณ์นี้ไหม
ขอ IP สาธารณะ + เปิดพอร์ต (port forwarding) จากฝ่ายไอที ตรงที่สุด ไม่พึ่งใคร ใช้ HTTP-01 ได้ ต้องขอฝ่ายไอที ใช้เวลา ต้องผ่านนโยบายความปลอดภัย เปิดเซิร์ฟเวอร์ให้โลกเห็น และเป็นสิ่งที่ขอไม่ได้ตอนนี้ ดีที่สุดในระยะยาว แต่ทำไม่ได้ตอนนี้
โดเมนของมหาวิทยาลัย (*.rmutt.ac.th) น่าเชื่อถือ ดูเป็นทางการ ต้องขอฝ่ายไอทีเช่นกัน และมักต้องมี IP ที่เข้าถึงได้ ใช้ได้ถ้าไอทีให้ (Caddyfile เตรียมคอมเมนต์ไว้ให้ลบบล็อก tls ออก)
Cloudflare Tunnel (cloudflared) ทำงานแบบเดียวกัน (ต่อออก) ฟรี ใช้โดเมนของเราเองได้ มี WAF/DDoS ป้องกันให้ ต้องมีโดเมนที่ย้าย DNS ไป Cloudflare (ซื้อโดเมนประมาณปีละไม่กี่ร้อยบาท) ข้อมูลผ่านเครือข่ายของ Cloudflare เป็นทางเลือกที่ดีมาก เลือก Tailscale เพราะไม่ต้องซื้อโดเมน
ngrok ตั้งง่ายมาก แผนฟรีเปลี่ยนที่อยู่/มีข้อจำกัด ชื่อคงที่ต้องจ่าย เหมาะกับทดลองมากกว่าใช้จริง
เช่า VPS สาธารณะ มี IP สาธารณะจริง ควบคุมเต็มที่ ต้องจ่ายรายเดือน ต้องดูแลอีกเครื่อง ข้อมูลไปอยู่นอกมหาวิทยาลัย (ส่วนตัวของนักศึกษา) บอร์ดในตึกต้องต่อออกนอกตึกมาที่ VPS แพงและย้ายข้อมูลออกนอก
ทำแค่ในตึก (ไม่มีทางเข้านอก) ปลอดภัยที่สุด ง่ายที่สุด เจ้าหน้าที่ดูจากบ้านไม่ได้ ไม่ตอบโจทย์ "ดูได้ทุกที่"

Funnel ถูกเลือกเพราะ: (1) ฟรี (2) ไม่ต้องแก้ firewall หรือขอไอที เพราะต่อออกอย่างเดียว (3) ได้ชื่อ HTTPS พร้อมใบรับรองจริงโดยไม่ต้องซื้อโดเมน (4) ติดตั้งเป็นกล่อง Docker เพิ่มกล่องเดียว และปิดได้ด้วยคำสั่งเดียว (5) ส่งต่อพอร์ต TCP ได้ด้วย (8443) จึงใช้กล่องเดียวกันเปิดทางให้ MQTT ของบอร์ดได้

  • พึ่งบริษัทภายนอก ถ้า Tailscale ล่มหรือเปลี่ยนเงื่อนไขแผนฟรี ทางเข้า ts.net หายทั้งสองพอร์ต คือแอปและเว็บนอกตึก และบอร์ดที่ตั้งค่าให้ต่อ ts.net:8443 (คำสั่งจาก Backend ถึงบอร์ดเหล่านั้นหยุดจนกว่าจะกลับมา) ส่วนเว็บในตึกทางโดเมนหลักและบอร์ดที่ต่อตรง 8883 ยังทำงาน
  • ข้อมูลผ่านเครือข่ายของ Tailscale แม้ relay ไม่ถอด TLS แต่ metadata (ใครต่อเมื่อไร รวมถึงการต่อ MQTT ของบอร์ด) ผ่านมือบริษัท
  • Funnel เปิดได้เฉพาะพอร์ต 443, 8443 และ 10000 และต้องเป็นการเชื่อมต่อ TLS MQTT ใช้พอร์ต 8443 ได้ด้วย TCPForward + TerminateTLS แต่ MariaDB หรือ SSH ไม่เหมาะและเราไม่ได้เปิด
  • ช่วงสุดท้ายเป็น MQTT ไม่เข้ารหัส จากกล่อง tailscale ไป mqtt:1883 วิ่งในเครือข่าย Docker ของเครื่องเดียวกัน ใครควบคุมเครื่องหรือ Docker ได้ก็เห็นข้อความดิบได้ (แต่คนนั้นอ่านฐานข้อมูลได้อยู่แล้ว)
  • Broker เข้าถึงได้จากอินเทอร์เน็ต ป้องกันด้วย TLS และบัญชี Dynamic Security รายบอร์ด ยังไม่มี rate limit ต่อ IP ที่ชั้น MQTT (ดูบท 15)
  • บอร์ดต้องออกพอร์ต 8443 ได้ และมีเวลา NTP ถูกต้อง เพื่อตรวจใบ ts.net (ถ้า Wi-Fi ที่ติดตั้งบล็อกพอร์ตขาออกนี้ ให้ใช้ทางต่อตรง 8883 ถ้าอยู่ในอาคาร)
  • ชื่อ ts.net ฝังในแอปตอน build และอยู่ในค่า provisioning ของบอร์ด ถ้าชื่อเปลี่ยน ต้อง build แอปใหม่และตั้งค่าบอร์ดใหม่ทุกตัว
  • ความเร็ว มี relay เพิ่มหนึ่งทอด ช้ากว่าต่อตรง เล็กน้อย แต่พอสำหรับแอปที่ดึงข้อมูลทุก 10 วินาทีและข้อความ MQTT ขนาดเล็กของบอร์ด

DuckDNS และ Let's Encrypt แบบ DNS-01 (สรุปรวม)#

หัวข้อ "สถานการณ์จริงของเซิร์ฟเวอร์" ด้านบนอธิบายขั้นตอนแล้ว ตรงนี้สรุปเหตุผลที่ต้องจำ

  • ทำไม HTTP-01 ทำไม่ได้: Let's Encrypt ต้องต่อเข้ามาที่พอร์ต 80 ของ IP ที่โดเมนชี้ แต่ DuckDNS ชี้ 10.x (ส่วนตัว) จึงไม่มีทางต่อถึง และ firewall ปิดขาเข้าอยู่แล้ว
  • DNS-01 ทำได้ เพราะเป็นขาออกล้วน: Caddy → Let's Encrypt (ขอใบ), Caddy → DuckDNS (เขียน TXT), Let's Encrypt → DNS ของ DuckDNS (ตรวจ TXT ซึ่งเป็นบริการสาธารณะอยู่แล้ว)
  • ปลั๊กอิน: Caddy มาตรฐานไม่มีตัวคุยกับ DuckDNS จึงต้อง build ใหม่ด้วย xcaddy build --with github.com/caddy-dns/duckdns (caddy.Dockerfile) แล้วตั้ง tag rmutt-caddy:duckdns
  • DUCKDNS_TOKEN อยู่ใน .env ส่งเข้ากล่อง caddy เป็น environment แล้ว Caddyfile อ้างด้วย {env.DUCKDNS_TOKEN} (ถ้าไม่ตั้ง compose ใช้ค่าว่าง ${DUCKDNS_TOKEN:-} และ Caddy ขอใบไม่สำเร็จ)
  • resolvers 1.1.1.1 8.8.8.8: DNS ของมหาวิทยาลัยตอบ SERVFAIL เมื่อ Caddy ถามหา zone ของ _acme-challenge จึงใช้ DNS สาธารณะ
  • propagation_delay 60s + propagation_timeout -1: รอ 60 วินาทีให้ค่า TXT กระจายแล้วให้ Let's Encrypt ตรวจเลย ไม่ให้ Caddy วนถาม DNS เอง (เพราะเครือข่ายมหาวิทยาลัยอาจบล็อกพอร์ต 53 ขาออก)
  • ผลกระทบข้างเคียง: ใบรับรอง DNS-01 ออกให้ชื่อ rmutt-energy.duckdns.org จริง เบราว์เซอร์และ ESP32 เชื่อได้ทั้งที่ชื่อชี้ IP ส่วนตัว

อธิบายทีละไฟล์#

deploy/docker-compose.yml#

ไฟล์ศูนย์กลางของ deploy ประกาศ 5 service, เครือข่ายเริ่มต้น (Docker สร้างให้โดยชื่อ rmutt_default จาก name: rmutt), และ anchor x-logging ที่ใช้ร่วมกัน ใครเรียกใช้: docker compose up -d บนเซิร์ฟเวอร์ (ผ่าน update-server.ps1/update-remote.sh) ค่า ${...} อ่านจากไฟล์ .env ในโฟลเดอร์เดียวกัน

service image / build พอร์ตที่ publish เก็บข้อมูลที่ หน้าที่
db mariadb:11 127.0.0.1:3306 (เฉพาะเครื่องตัวเอง) ./db/data ฐานข้อมูล
mqtt eclipse-mosquitto:2.0 8883 ./mosquitto/data, certs, config Broker
backend build ./backend ไม่มี (ภายในเท่านั้น 3000) อ่าน ./firmware API และตัวรับ MQTT
caddy build caddy.Dockerfile 80, 443 (8080 ไม่ publish) ./caddy/data, ./caddy/config เว็บ + proxy + ใบรับรอง
tailscale tailscale/tailscale:stable ไม่มี ./tailscale/state Funnel (443 → caddy:8080, 8443 → mqtt:1883)

Published vs internal: พอร์ตที่เขียนใน ports: เปิดบนเครื่องจริง พอร์ตที่ไม่เขียนยังเข้าถึงได้จากกล่องอื่นในเครือข่ายเดียวกันด้วยชื่อ service (db:3306, mqtt:1883, backend:3000, caddy:8080) 1883, 3000 และ 8080 จึงไม่โผล่นอกเครื่อง (1883 มีกล่อง tailscale ส่งต่อมาจาก Funnel 8443 ภายในเครือข่าย Docker เท่านั้น)

DNS ภายใน Docker: Backend ต่อ DB_HOST: db และ MQTT_URL: mqtt://mqtt:1883, Caddy ส่งต่อ backend:3000, tailscale ส่งต่อ caddy:8080 และ mqtt:1883 ไม่มี IP ฝังในไฟล์ใดเลย กล่องเปลี่ยน IP เมื่อสร้างใหม่ได้โดยไม่เสียหาย

Healthcheck: Docker รันคำสั่งตรวจเป็นระยะและติดป้าย healthy/unhealthy - db ใช้ healthcheck.sh --connect --innodb_initialized ที่มากับ image - mqtt ใช้ mosquitto_sub ต่อ 127.0.0.1:1883 ด้วยบัญชี Backend อ่าน $SYS/broker/version หนึ่งข้อความ (-C 1) รอไม่เกิน 5 วินาที (-W 5) เขียน $$ เพราะ compose ใช้ $ แทนตัวแปร ต้องใช้ $$ เพื่อให้ shell ในกล่องเห็น $ จริง - backend ใช้ node -e เรียก fetch('http://127.0.0.1:3000/api/health') (image node:22-alpine ไม่มี curl จึงใช้ Node เอง)

depends_on: ควบคุมลำดับเริ่ม backend รอ db ถึงขั้น service_healthy (ไม่งั้นต่อ DB ไม่ติดตอนบูต) แต่รอ mqtt แค่ service_started ส่วน caddy รอ backend เริ่ม และ tailscale รอ caddy กับ mqtt (ให้ปลายทางทั้งสองขึ้นก่อนที่ Funnel จะเริ่มส่งต่อ) ข้อสังเกต: depends_on ไม่ใช่การรับประกันว่าพร้อมรับคำขอ

restart: unless-stopped: กล่องเด้งกลับเองเมื่อพังหรือเครื่องรีบูต แต่ถ้าเราสั่ง docker compose stop เองมันจะไม่ลุกขึ้นมาเอง (นี่คือเหตุผลที่ "ปิด Funnel" ด้วย stop ได้ผล)

Logging: anchor x-logging จำกัด log กล่องละ 10 MB × 5 ไฟล์ = 50 MB สูงสุดต่อกล่อง ค่าเริ่มต้นของ Docker ไม่จำกัด เครื่องที่รันยาวจะดิสก์เต็ม

Selective env vars: Backend ได้รับเฉพาะตัวแปรที่ใช้ ไม่ใช้ env_file: .env ทั้งไฟล์ เพราะ .env มีรหัส root ของ MariaDB, DUCKDNS_TOKEN, TS_AUTHKEY และรหัสแอดมินตัวแรก ถ้าส่งทั้งไฟล์ ใครที่รัน docker inspect rmutt-backend หรือเจาะ Backend ได้จะเห็นความลับที่ Backend ไม่เคยใช้ ผลเสียของวิธีนี้คือต้องมาเพิ่มตัวแปรในรายการเองเมื่อ Backend ต้องใช้ตัวใหม่

deploy/Caddyfile#

ตั้งค่า Caddy มี 4 ส่วน: บล็อกตั้งค่าทั่วไป (บรรทัด 1–7), snippet (app) ที่ใช้ร่วม (บรรทัด 10–56), บล็อกโดเมนหลัก {$DOMAIN} (บรรทัด 58–79), และบล็อก http://:8080 สำหรับ Funnel (บรรทัด 83–85) ทำไมใช้ snippet: เว็บและ API เหมือนกันทั้งสองทางเข้า เขียนครั้งเดียวแล้ว import app สองที่ ไม่มีโอกาสที่สองทางจะต่างกัน

deploy/caddy.Dockerfile และ deploy/backend.Dockerfile#

สูตรสร้าง image Caddy (multi-stage build เอาเฉพาะไบนารี) และ image Backend (ติดตั้ง dependency แบบ production, ปรับสิทธิ์อ่านซอร์สให้ user node, รันด้วย user node) ดูในหัวข้อเจาะโค้ด caddy.Dockerfile อ้างจาก compose ผ่าน build.dockerfile ส่วน backend.Dockerfile compose ไม่ได้อ้างตรง ๆ (ใช้ build: ./backend ซึ่งมองหา backend/Dockerfile) แต่สคริปต์ upload.ps1 และ update-remote.sh จะรัน cp -f backend.Dockerfile backend/Dockerfile บนเซิร์ฟเวอร์ให้ก่อน build ทุกครั้ง (ในซอร์สไม่มี backend/Dockerfile เก็บไว้) ถ้าลืมก๊อป docker compose build จะหา Dockerfile ไม่เจอ

กฎ Funnel สองพอร์ต (443 → caddy:8080 และ 8443 → mqtt:1883) อธิบายครบแล้วในหัวข้อ Tailscale mount เข้ากล่อง tailscale แบบอ่านอย่างเดียว (:ro) ไฟล์นี้ถูกอัปโหลดทับเป็นไฟล์ใหม่ทุกครั้งที่ deploy ซึ่ง container เดิมยังเห็นไฟล์เก่า update-remote.sh จึงสั่งสร้างกล่อง tailscale ใหม่ให้ (ดูบท 14)

  • server.config.example.json คัดลอกเป็น server.config.json (ไม่ถูก commit) เก็บ host, user, port (SSH), domain ที่สคริปต์ PowerShell ทุกตัว (update-server.ps1, deploy-web.ps1, upload.ps1, db-tunnel.ps1) อ่านผ่าน deploy/ServerConfig.ps1 เพื่อไม่ต้องฝังที่อยู่เซิร์ฟเวอร์ในสคริปต์

หลักการเขียนโค้ดที่ใช้ในส่วนนี้#

  • Least exposure (เปิดให้น้อยที่สุด) docker-compose.yml: publish แค่ 80, 443, 8883, และ 3306 ที่ผูก 127.0.0.1 ส่วนที่เหลือคุยกันในเครือข่าย Docker ทางเข้า Funnel ก็เปิดแค่สองปลายทางคือ caddy:8080 (พอร์ต 443) กับ mqtt:1883 (พอร์ต 8443 ซึ่งยังต้องล็อกอินด้วยบัญชีรายบอร์ด) ถ้ามีช่องโหว่ใน Backend ผู้โจมตียังเข้าฐานข้อมูลตรง ๆ จากอินเทอร์เน็ตไม่ได้
  • Least privilege (สิทธิ์น้อยที่สุด) backend.Dockerfile ใช้ USER node; MariaDB แยก user ของแอปที่มีสิทธิ์เฉพาะฐานข้อมูล ไม่ใช้ root; กล่องที่ mount config ใช้ :ro; tailscale ใช้ userspace ไม่ขอ NET_ADMIN; บอร์ดแต่ละตัวมีบัญชี MQTT ของตัวเอง
  • Secrets แยกออกจากโค้ด รหัสผ่านทุกตัวอยู่ใน .env (ไม่ commit; init-env.sh สุ่มให้) compose อ้างด้วย ${...}; ส่งเข้าแต่ละกล่องเฉพาะที่ใช้ ลดความเสียหายถ้ากล่องใดถูกเจาะ
  • Reverse proxy เป็นประตูเดียว (Caddy) เก็บ TLS, หัวความปลอดภัย, การแยก path ไว้ที่เดียว Backend ไม่ต้องรู้เรื่อง TLS และไม่ต้องเปิดตรงสู่ภายนอก
  • ถอด TLS ที่ขอบ (TLS termination) deploy/tailscale-serve.json: กล่อง tailscale ถอด TLS ทั้งพอร์ต 443 (ส่ง HTTP ไป Caddy) และพอร์ต 8443 (ส่ง MQTT ดิบไป Mosquitto 1883) ชั้นในจึงไม่ต้องดูแลใบรับรองของชื่อ ts.net เอง ข้อแลกเปลี่ยนคือช่วงสุดท้ายไม่เข้ารหัส ต้องจำกัดให้อยู่ในเครือข่าย Docker ภายในเครื่อง
  • DRY ด้วย snippet / anchor (app) ใน Caddyfile และ &default-logging ใน compose เขียนครั้งเดียวใช้หลายที่ ลดโอกาสที่สองทางเข้าจะต่างกันโดยไม่ตั้งใจ
  • Defense in depth (ป้องกันหลายชั้น) CSP + HSTS + nosniff + CORS allow-list + rate limit + JWT ไม่พึ่งชั้นเดียว
  • Declarative infrastructure ระบบทั้งหมดอธิบายเป็นไฟล์ (compose, Caddyfile, serve.json) สร้างใหม่ได้ด้วย docker compose up -d สถานะที่ต้องเก็บมีแค่ volume (db/data, caddy/data, mosquitto/data, tailscale/state) ซึ่งเป็นสิ่งที่ต้องสำรอง
  • Healthcheck + depends_on condition ให้ลำดับเริ่มระบบรอจนบริการพร้อมจริง ไม่ใช่แค่เริ่มทำงาน
  • ไม่ผูกที่อยู่กับโค้ด ใช้ชื่อ service ภายใน Docker, {$DOMAIN} ใน Caddyfile, /api สัมพัทธ์ในเว็บ และ --dart-define ในแอป ย้ายโดเมนแล้วแก้ที่เดียว
  • Fail-safe default ถ้า TRUST_PROXY ว่าง = ไม่เชื่อ XFF เลย (config.js) ค่าเริ่มต้นเลือกด้านปลอดภัย

คำถามที่อาจารย์อาจถาม#

อาจารย์อาจถาม

ทำไมต้องใช้ Tailscale ทำไมไม่ขอเปิดพอร์ตจากฝ่ายไอทีไปเลย เซิร์ฟเวอร์อยู่หลัง firewall ของมหาวิทยาลัยที่ไม่ให้ต่อขาเข้า และเราต้องการให้เจ้าหน้าที่เปิดแอปจากนอกมหาวิทยาลัยได้ รวมทั้งให้บอร์ด ESP32 ที่ต่อ Wi-Fi ข้างนอกต่อ MQTT เข้ามาได้ การขอเปิดพอร์ตเป็นทางที่ตรงที่สุดและดีในระยะยาว แต่ต้องผ่านขั้นตอนและนโยบายของไอที ซึ่งเราควบคุมไม่ได้ Tailscale Funnel ให้กล่อง Docker ต่อ "ออก" ไปหา Tailscale เอง ซึ่ง firewall อนุญาตอยู่แล้ว ผู้ใช้จึงเข้ามาทางท่อนั้นได้โดยไม่ต้องเปิดพอร์ตขาเข้า ได้ HTTPS ที่ถูกต้อง ฟรี และปิดได้ทันทีด้วย docker compose stop tailscale ถ้าภายหลังไอทีเปิดพอร์ตให้ ก็ถอด Funnel ออกแล้วใช้โดเมนของมหาวิทยาลัยได้

อาจารย์อาจถาม

Funnel กับ Serve ต่างกันอย่างไร และ Funnel ปลอดภัยไหม Serve เปิดให้เฉพาะเครื่องใน tailnet ส่วน Funnel เปิดให้ทั้งอินเทอร์เน็ต เราเปิดสองทาง: เว็บและ API (พอร์ต 443 → caddy:8080) และ MQTT ของบอร์ด (พอร์ต 8443 → mqtt:1883) ฐานข้อมูลและ SSH ไม่ถูกเปิด ทางเว็บป้องกันที่ชั้นแอป: HTTPS, JWT, rate limit การล็อกอิน (10 ครั้ง/15 นาที), CSP, และ CORS ทาง MQTT ป้องกันด้วย TLS ที่พอร์ต 8443 และบัญชี Dynamic Security รายบอร์ด (allow_anonymous false บอร์ดเห็นเฉพาะ topic ของตัวเอง) ความเสี่ยงที่ยอมรับคือใครก็ลองเรียก API หรือลองต่อ MQTT ได้ จึงต้องพึ่งการยืนยันตัวตนและรหัสรายบอร์ดที่เดายาก ส่วน MQTT ยังไม่มี rate limit ต่อ IP ถ้าไม่อยากรับความเสี่ยงนี้ ตั้ง MQTT_DEVICE_URL=mqtts://<DOMAIN>:8883 ให้บอร์ดต่อตรงในอาคารแทน

อาจารย์อาจถาม

เซิร์ฟเวอร์ไม่มี IP สาธารณะ Funnel เข้ามาถึงได้อย่างไร กล่อง tailscale ในเซิร์ฟเวอร์สร้างการเชื่อมต่อขาออกไปหา Tailscale แล้วค้างไว้ DNS ของชื่อ ts.net ชี้ไป relay ของ Tailscale เมื่อผู้ใช้เข้ามา relay ส่งต่อผ่านการเชื่อมต่อที่ค้างไว้นั้น เรียกว่าเป็นการต่อ "ย้อนท่อ" firewall เห็นเป็นทราฟฟิกขาออกจึงไม่ปิดกั้น

อาจารย์อาจถาม

ทำไม TRUST_PROXY เป็น 2 ค่า 1 หรือ true ได้ไหม ได้ แต่จะผิด ทางโดเมนหลักผ่าน Caddy ชั้นเดียว ทาง Funnel ผ่านสองชั้น (tailscale แล้ว Caddy) ถ้าตั้ง 1 คำขอผ่าน Funnel จะได้ IP ของกล่อง tailscale เป็น req.ip ทุกคนถูกนับเป็นคนเดียว rate limit ล็อกอินจะทำให้ใครพิมพ์ผิด 10 ครั้งแล้วล็อกทั้งระบบ ถ้าตั้งมากกว่าจริง ผู้โจมตีปลอมหัว XFF เปลี่ยน IP หนี rate limit ได้ true จะถูก config.js แปลงเป็น 1 เพราะ express-rate-limit ไม่ยอมรับ true

อาจารย์อาจถาม

ทำไมต้องใช้ DuckDNS + DNS-01 ทำไมไม่ใช้ HTTP-01 ซึ่งง่ายกว่า HTTP-01 ให้ Let's Encrypt ต่อเข้าพอร์ต 80 ของเซิร์ฟเวอร์ แต่โดเมนของเราชี้ไป IP ภายใน 10.x และ firewall ปิดขาเข้า จึงต่อไม่ถึง DNS-01 พิสูจน์ด้วย TXT record ที่เขียนผ่าน API ของ DuckDNS เป็นการเชื่อมต่อขาออกทั้งหมด เราจึงได้ใบรับรองที่ถูกต้องโดยไม่เปิดพอร์ต ต้อง build Caddy ใหม่ให้มีปลั๊กอิน DuckDNS

อาจารย์อาจถาม

ทำไมโดเมนชี้ไป IP ภายใน แล้วยังต้องมีโดเมน ใบรับรอง TLS ออกให้ชื่อโดเมน ไม่ออกให้ IP ส่วนตัว บอร์ดและเบราว์เซอร์ตรวจว่าชื่อตรงกับใบ และถ้า IP เซิร์ฟเวอร์เปลี่ยน แก้ที่ DuckDNS ที่เดียว บอร์ดไม่ต้องตั้งใหม่ ชื่อนี้ใช้ได้เฉพาะในตึก ส่วนนอกตึกใช้ ts.net (แอป และบอร์ดตามค่าเริ่มต้นปัจจุบัน)

อาจารย์อาจถาม

ทำไม ESP32 ต่อ MQTT ผ่าน Funnel และทำไมเป็นพอร์ต 8443 ถ้าบอร์ดต่อ rmutt-energy.duckdns.org:8883 จะติดปัญหาว่าโดเมน DuckDNS ชี้ไป IP ภายใน 10.x บอร์ดที่ต่อ Wi-Fi นอกมหาวิทยาลัยจึงหา Broker ไม่เจอ ชื่อ ts.net ของ Funnel ชี้ไปที่ relay สาธารณะ เข้าได้จากทุกเครือข่าย และกล่อง tailscale เป็นฝ่ายต่อออกไปหา relay เอง จึงไม่ต้องขอเปิดพอร์ตขาเข้า Funnel รองรับพอร์ต TCP ได้ด้วย แต่เปิดสู่สาธารณะได้เฉพาะ 443, 8443 และ 10000 พอร์ต 443 เว็บใช้อยู่แล้ว และ 8883 ไม่อยู่ในรายการ จึงเลือก 8443 สำหรับ MQTT บอร์ดต่อ rmutt-energy.tailb292b4.ts.net:8443 ได้จากทุกที่ ส่วนบอร์ดในอาคารยังต่อตรง 8883 ได้ถ้าตั้ง MQTT_DEVICE_URL

อาจารย์อาจถาม

ทำไมถอด TLS ที่กล่อง tailscale (TerminateTLS) ไม่ใช้ใบรับรองของ Mosquitto ที่ 8883 บอร์ดตรวจว่าชื่อในใบรับรองตรงกับชื่อที่ต่อ ใบของ Mosquitto ออกให้ rmutt-energy.duckdns.org แต่บอร์ดต่อชื่อ ts.net ถ้าส่งต่อ TLS ดิบ (TCPForward อย่างเดียว) ไป 8883 บอร์ดจะเห็นใบผิดชื่อและปฏิเสธ จึงให้กล่อง tailscale ถอด TLS ด้วยใบ ts.net ของตัวเอง (ออกโดย Let's Encrypt จึงตรงกับใบรากที่ฝังในเฟิร์มแวร์ ไม่ต้องแฟลชใหม่) แล้วส่ง MQTT ดิบไป mqtt:1883 ซึ่ง Backend ใช้อยู่แล้ว ไม่ต้องแก้ Mosquitto และไม่ต้องก๊อปใบด้วย cron ข้อแลกเปลี่ยนคือช่วงสุดท้ายไม่เข้ารหัส แต่วิ่งในเครือข่าย Docker ของเครื่องเดียว และบอร์ดยังต้องล็อกอินด้วยบัญชีรายตัว

อาจารย์อาจถาม

ใบรับรองหมดอายุจะเกิดอะไรขึ้น Caddy ต่ออายุเองด้วย DNS-01 ส่วน Mosquitto ใช้ใบเดียวกันแต่ต้องมีคนก๊อปให้ จึงมี cron sync-mqtt-cert.sh ทุกวัน 03:10 ที่ก๊อปเมื่อใบเปลี่ยนแล้วส่ง SIGHUP ให้ Mosquitto โหลดใหม่โดยไม่ตัดการเชื่อมต่อบอร์ด ถ้าไม่ทำ บอร์ดที่ต่อตรง 8883 ทุกตัวจะต่อ MQTTS ไม่ได้พร้อมกันเมื่อใบเก่าหมด (บอร์ดที่ต่อผ่าน Funnel 8443 ใช้ใบ ts.net ที่กล่อง tailscale จัดการเอง จึงไม่เกี่ยวกับ cron นี้) นอกจากนี้บอร์ดฝังใบรากของ Let's Encrypt (ISRG Root X1 และ X2) ซึ่งหมดอายุ 2035 และ 2040 จึงไม่ต้องแฟลชใหม่ตามรอบ 90 วัน

อาจารย์อาจถาม

ทำไมฐานข้อมูลเปิด 127.0.0.1:3306 ไม่ปิดไปเลย ผู้ดูแลต้องดูและแก้ข้อมูลด้วย HeidiSQL การเปิดเฉพาะ loopback ของเซิร์ฟเวอร์แล้วเข้าผ่านอุโมงค์ SSH ทำให้ต้องผ่านการยืนยันตัวตน SSH ก่อน และไม่มีใครในเครือข่าย 10.x ต่อ 3306 ตรง ๆ ได้ ปิดไปเลยก็ทำให้ดูแลยาก

อาจารย์อาจถาม

ทำไมไม่ส่ง .env ทั้งไฟล์ให้ Backend .env มีรหัส root ของฐานข้อมูล, token DuckDNS, authkey Tailscale และรหัสแอดมินตัวแรกซึ่ง Backend ไม่ได้ใช้ ถ้าส่งทั้งไฟล์ ใครที่เจาะ Backend ได้หรือรัน docker inspect จะเห็นความลับเหล่านั้น เราจึงใส่ทีละตัวใน environment: ของ service

สรุปและเช็กลิสต์ความเข้าใจ#

ถ้าตอบข้อเหล่านี้ได้ แปลว่าเข้าใจบทนี้แล้ว

  • อธิบายได้ว่าทำไมเซิร์ฟเวอร์ต่อจากนอกมหาวิทยาลัยไม่ได้ (IP 10.x + NAT + firewall ขาเข้าปิด) และทำไมขาออกยังทำงาน
  • บอกทางเข้า 4 ทาง (duckdns → 443 ในอาคาร, ts.net Funnel 443 → caddy:8080, ts.net Funnel 8443 → mqtt:1883 สำหรับ ESP32, duckdns:8883 ต่อตรงในอาคาร) และใครใช้แต่ละทาง
  • อธิบายได้ว่า Funnel ถึงเซิร์ฟเวอร์โดยไม่เปิดพอร์ตขาเข้าได้อย่างไร (การเชื่อมต่อขาออกที่ค้างไว้)
  • ต่างระหว่าง Tailscale Serve กับ Funnel, tailnet, MagicDNS, *.ts.net และ TS_USERSPACE
  • อ่าน tailscale-serve.json ได้ทีละบรรทัด และบอกว่าบรรทัดไหนทำให้เปิดสู่สาธารณะ (บรรทัด 16–19)
  • อธิบายความต่างของ HTTPS + Web, TCPForward ดิบ และ TCPForward + TerminateTLS และเหตุที่ MQTT ใช้แบบสุดท้ายที่พอร์ต 8443
  • บอกได้ว่าทำไมเปิดแค่ caddy:8080 กับ mqtt:1883 และทำไมแอปใช้ที่อยู่ ts.net เป็นค่าเริ่มต้น
  • อธิบายความสัมพันธ์ TRUST_PROXY=2 ↔ trusted_proxies ↔ rate limit ล็อกอิน และเหตุที่ตั้งผิดแล้วเสียหาย
  • เปรียบเทียบ Funnel กับ port forwarding, Cloudflare Tunnel, ngrok, VPS, โดเมนมหาวิทยาลัยได้ พร้อมข้อจำกัดของ Funnel (เปิดได้เฉพาะพอร์ต 443/8443/10000, ช่วงสุดท้ายถึง Mosquitto เป็น MQTT ดิบในเครือข่าย Docker, Broker เข้าถึงได้จากอินเทอร์เน็ต)
  • อธิบาย DNS-01 ทีละขั้น และ resolvers, propagation_delay, propagation_timeout -1
  • อธิบายวิธีที่ใบรับรองของ Caddy ถึง Mosquitto และใบรากใน ESP32 (รวมถึงเหตุที่ใบ ts.net ใช้ใบรากเดิมได้)
  • ไล่ service ใน compose: image, พอร์ตที่ publish/ภายใน, volume, healthcheck, depends_on, logging
  • อธิบายความต่างของ Broker ใน deploy/ กับ mqtt/
  • อธิบาย multi-stage build ของ caddy.Dockerfile และเหตุที่ backend.Dockerfile แยก npm ci ออกจาก COPY . . กับเหตุที่ต้อง chmod -R a+rX ก่อน USER node
  • วาดเส้นทางคำขอทั้ง 5 แบบ (รวม ESP32 ผ่าน Funnel 8443 และต่อตรง 8883)จากความจำได้
