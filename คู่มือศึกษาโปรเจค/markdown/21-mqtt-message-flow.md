# เส้นทางข้อความ MQTT: จากบอร์ดถึง Backend และกลับไปบอร์ด

บท 3 เล่าเส้นทางของข้อมูลแบบภาพรวม บท 8 อธิบายโปรโตคอล MQTT เอง และบท 7 อธิบายตรรกะใน Backend บทนี้เก็บทุกอย่างมาเรียงเป็น **เรื่องเดียวระดับข้อความ**: บอร์ดส่งข้อความอะไร ไปที่ topic ไหน ทุกกี่วินาที Backend รับแล้วทำอะไรกับฐานข้อมูล แล้วส่งอะไรกลับไปต่อ ทุกข้อในบทนี้ตรวจจากโค้ดจริง ได้แก่ `backend/src/services/mqtt.js`, `energy-recorder.js`, `auto-off.js`, `utils/mqtt-accounts.js` และเฟิร์มแวร์ `firmware/rmutt_esp32_air`, `rmutt_esp32_air_wired`, `rmutt_esp32_occupancy`

> [!NOTE]
> ตัวเลขเวลาทั้งหมดอ่านจากค่าคงที่ในโค้ด (เช่น `STATUS_INTERVAL_MS = 10000`) ถ้าแก้ค่าในโค้ด ตัวเลขในบทนี้ต้องแก้ตาม

## ภาพรวม: ใครส่งอะไรให้ใคร

```text
 [บอร์ดแอร์ ESP32]                         [บอร์ดตรวจคน OCC32]
   │ ส่ง: status, state,                     │ ส่ง: status,
   │      provision, history                 │      provision
   │ รับ: command, provision-ack,            │ รับ: command,
   │      schedule-status, history-ack       │      provision-ack
   ▼                                         ▼
 ┌─────────────────────────────────────────────────┐
 │            Mosquitto (Broker)                   │
 │  rmutt/ac/<ESP32-…>/…                           │
 │  rmutt/occupancy/<OCC32-…>/…                    │
 └─────────────────────────────────────────────────┘
        ▲ รับ status/state/history/provision
        │ ส่ง command/ack/schedule-status
        ▼
 [Backend Node.js] ───► MariaDB
        ▲
        │ REST API (HTTP)
 [แอป Flutter / เว็บ]
```

จุดที่ต้องจำสามข้อ

1. **บอร์ดไม่คุยกับ Backend ตรง ๆ** ทุกอย่างผ่าน Broker โดยบอร์ดกับ Backend ต่างก็เป็น client ของ Broker
2. **แอปไม่ฟัง MQTT เลย** แอปคุยกับ Backend ด้วย REST แล้ว Backend ค่อยส่งต่อเป็นข้อความ MQTT ส่วนค่าที่แอปแสดงมาจากฐานข้อมูล ซึ่ง Backend อัปเดตจากข้อความที่บอร์ดส่งมา แอปจึงเห็นค่าใหม่เมื่อดึงรอบถัดไป (บอร์ดแอร์และห้อง ดึงทุก 10 วินาที แดชบอร์ดทุก 30 วินาที)
3. **เซ็นเซอร์ตรวจคนกับบอร์ดแอร์ไม่คุยกันเอง** คนที่เห็นทั้งสองฝั่งคือ Backend จึงให้ Backend ตัดสินใจปิดแอร์

## กติกาพื้นฐานของทุกข้อความ

| เรื่อง | ค่าที่ใช้ | หมายเหตุ |
|---|---|---|
| รูปแบบข้อมูล | JSON ทุกข้อความ | ข้อความที่แปลง JSON ไม่ได้ Backend ทิ้งเงียบ ๆ |
| Topic ของบอร์ดแอร์ | `rmutt/ac/<deviceId>/<ชนิด>` | `deviceId` รูปแบบ `ESP32-` ตามด้วย hex 12 ตัว ตั้งต้นจากค่าใน `MQTT_TOPIC_PREFIX` |
| Topic ของบอร์ดตรวจคน | `rmutt/occupancy/<deviceId>/<ชนิด>` | `deviceId` รูปแบบ `OCC32-` ตามด้วย hex 12 ตัว ตั้งจาก `MQTT_OCCUPANCY_TOPIC_PREFIX` |
| Backend ตรวจ topic | regular expression ตายตัว | topic ที่รหัสอุปกรณ์หรือชนิดไม่ตรงถูกทิ้ง |
| Client ID | บอร์ด `rmutt-<deviceId>`, Backend `rmutt-api-<pid>` | Backend ตั้ง `clean: true` และต่อใหม่เองทุก 3 วินาทีเมื่อหลุด |
| QoS ฝั่งบอร์ด | publish เป็น QoS 0, subscribe เป็น QoS 1, Last Will เป็น QoS 1 | ไลบรารี PubSubClient ส่งข้อความได้เฉพาะ QoS 0 |
| QoS ฝั่ง Backend | subscribe และ publish เป็น QoS 1 ทั้งหมด | คำสั่งถึงบอร์ดอย่างน้อยหนึ่งครั้งถ้าบอร์ดออนไลน์ |
| การเข้ารหัส | TLS (`mqtts` ปกติพอร์ต 8883) ได้ ถ้าตั้งค่าตอน provisioning | บอร์ดต้องซิงก์เวลา NTP ก่อน ไม่งั้นตรวจใบรับรองไม่ผ่าน และใช้ใบรับรอง Let's Encrypt ที่ฝังในเฟิร์มแวร์ |
| บัญชีต่อบอร์ด | username = deviceId (โหมด `dynsec`) | Backend สร้างบัญชีและ ACL ในตัว Broker ผ่าน Dynamic Security |

### ใครมีสิทธิ์ส่ง/รับ topic ไหน (ACL ต่อบอร์ด)

Backend สร้างบัญชีให้บอร์ดแต่ละตัวพร้อมสิทธิ์เฉพาะ topic ของตัวเอง (`utils/mqtt-accounts.js`) บอร์ดตัวหนึ่งจึงอ่านหรือปลอมข้อความของบอร์ดอื่นไม่ได้

| ประเภทบอร์ด | ส่งได้ (publish) | รับได้ (subscribe) |
|---|---|---|
| บอร์ดแอร์ | `state`, `status`, `provision`, `provision-ack`, `history` | `command`, `provision-ack`, `schedule-status`, `history-ack` |
| บอร์ดตรวจคน | `status`, `provision`, `provision-ack` | `command`, `provision-ack` |

บอร์ดตรวจคนไม่มี topic `state`, `history` และ `schedule-status`

## Topic ทั้งหมดของบอร์ดแอร์

ฐาน `rmutt/ac/<deviceId>/` แล้วตามด้วยชื่อในคอลัมน์แรก

| Topic | ทิศทาง | Retain | ใครส่งเมื่อไร | ใครรับและทำอะไร |
|---|---|---|---|---|
| `status` | บอร์ด → Backend | ใช่ | บอร์ดส่งทุก 10 วินาที และทันทีเมื่อเหตุการณ์สำคัญเปลี่ยน | Backend อัปเดตค่าไฟ สถานะแอร์ รุ่นเฟิร์มแวร์ บันทึกถังรายชั่วโมง ส่ง schedule-status กลับ และปลุกระบบปิดแอร์อัตโนมัติ |
| `status` (Last Will) | Broker → Backend | ใช่ | Broker ส่งแทนบอร์ดเมื่อบอร์ดหลุดแบบไม่ได้ตัดการเชื่อมต่อ | Backend ตั้ง `is_online = 0` |
| `state` | บอร์ด → Backend | ใช่ | ส่งตอนต่อ Broker ได้ และหลังบอร์ดทำตามคำสั่งเสร็จ | Backend เก็บลง `state_json` |
| `command` | Backend → บอร์ด | ไม่ | Backend ส่งเมื่อผู้ใช้สั่ง หรือระบบปิดแอร์ยิง | บอร์ดตรวจค่า ส่ง IR แล้วตอบด้วย `state` |
| `schedule-status` | Backend → บอร์ด | ใช่ | Backend ส่งทุกครั้งที่ได้ `status` ที่บอร์ดบอกว่าออนไลน์ (ราว ๆ ทุก 10 วินาที) | บอร์ดใช้ตัดสินว่าตอนนี้อยู่ในคาบเรียนหรือไม่ เพื่อเปิดไฟเตือนนอกคาบ |
| `provision` | บอร์ด → Backend | ใช่ | ส่งซ้ำทุก 10 วินาทีจนกว่าจะได้ provision-ack | Backend ตรวจ token แล้วเปิดใช้งานอุปกรณ์ |
| `provision-ack` | Backend → บอร์ด | ใช่ | ตอบหลังตรวจ token ผ่าน | บอร์ดลบ token ทิ้ง แล้วล้างข้อความ retain ของ topic นี้ |
| `history` | บอร์ด → Backend | ไม่ | ส่งเมื่อมีข้อมูลที่เก็บไว้ตอนเน็ตหลุด ครั้งละ 10 รายการ | Backend บันทึกลงถังรายชั่วโมงแล้วตอบ history-ack |
| `history-ack` | Backend → บอร์ด | ไม่ | ตอบหลังบันทึกสำเร็จ | บอร์ดลบรายการที่ยืนยันแล้วออกจาก flash |

บอร์ดตรวจคนใช้ฐาน `rmutt/occupancy/<deviceId>/` และมีแค่ `status`, `command`, `provision`, `provision-ack` ความหมายเหมือนกัน

## ตารางเวลา: อะไรเกิดทุกกี่วินาที

### ฝั่งบอร์ดแอร์

| เหตุการณ์ | รอบเวลา | ที่มาในโค้ด |
|---|---|---|
| อ่าน PZEM (แรงดัน กระแส กำลัง ฯลฯ) | ทุก 2 วินาที | `PZEM_READ_INTERVAL_MS` |
| ส่ง `status` | ทุก 10 วินาที | `STATUS_INTERVAL_MS` |
| ส่ง `status` ทันที | เมื่อ PZEM กลับมาอ่านได้/อ่านไม่ได้ เมื่อแอร์เริ่มหรือหยุดกินไฟ เมื่อสถานะนอกคาบเปลี่ยน เมื่อส่งข้อมูลย้อนหลังครบ หรือเมื่อ OTA ล้มเหลว | `statusPublishRequested` |
| ตัดสินว่าแอร์ "ทำงาน" | กำลังไฟ ≥ 30 W ติดกัน 3 ครั้ง = ทำงาน, ≤ 10 W ติดกัน 3 ครั้ง = หยุด | `AC_RUNNING_*` |
| ถือว่า PZEM เสีย | อ่านไม่ได้ติดกัน 3 ครั้ง | `PZEM_FAILURE_LIMIT` |
| ต่อ MQTT ใหม่เมื่อหลุด | ลองทุก 3 วินาที | `loop()` |
| ส่ง `provision` ซ้ำ | ทุก 10 วินาทีจนกว่าจะได้ provision-ack | `lastProvisionAt` |
| เวลาที่ใช้ผลจาก `schedule-status` | ไม่เกิน 2 นาทีนับจากข้อความล่าสุด เลยจากนั้นใช้ตารางเปิด-ปิดประจำวันในบอร์ดแทน | `CLASS_SCHEDULE_TTL_MS` |
| สรุปค่าไฟเก็บไว้ตอนเน็ตหลุด | ช่วงละ 5 นาที (เก็บเมื่อต่อ MQTT ไม่ได้หรือยังมีค้างส่ง) | `HISTORY_INTERVAL_SECONDS = 300` |
| เริ่มส่งข้อมูลย้อนหลัง | หน่วงแบบสุ่ม 5–45 วินาทีหลังต่อ MQTT ได้ (กันบอร์ดทั้งตึกส่งพร้อมกัน) | `HISTORY_START_DELAY_*` |
| ส่งข้อมูลย้อนหลัง | ครั้งละ 10 รายการ ห่างกันอย่างน้อย 1 วินาที | `HISTORY_BATCH_SIZE`, `HISTORY_SEND_GAP_MS` |
| รอ `history-ack` | 20 วินาที ถ้าไม่ได้ ส่งชุดเดิมใหม่หลังรออีก 5 วินาที | `HISTORY_ACK_TIMEOUT_MS`, `HISTORY_RETRY_DELAY_MS` |
| บัญชี MQTT ถูกลบ | ถ้า Broker ปฏิเสธรหัสติดกันนานเกิน 2 นาทีและอย่างน้อย 10 ครั้ง บอร์ดล้างค่าทั้งหมดแล้วเข้าโหมดตั้งค่า | `MQTT_AUTH_REJECT_*` |

## เส้นทางที่ 1: บอร์ดต่อ Broker ได้

เกิดทุกครั้งที่บอร์ดบูต หรือต่อใหม่หลังเน็ตหลุด (`connectMqtt()` ใน `.ino`)

1. ถ้าเปิด TLS บอร์ดซิงก์เวลา NTP ก่อน (รอได้ 15 วินาที) แล้วตั้งใบรับรอง
2. ต่อ Broker ด้วย client ID `rmutt-<deviceId>` ใส่ username/password ที่ได้ตอนติดตั้ง และฝาก **Last Will** ไว้ที่ `…/status` แบบ QoS 1 retain ว่า `{"online":false,"deviceId":"ESP32-…"}`
3. subscribe topic `command`, `provision-ack`, `schedule-status`, `history-ack` (QoS 1)
4. ตั้งเวลาเริ่มส่งข้อมูลย้อนหลังแบบสุ่ม 5–45 วินาที
5. ส่ง `status` ทันที, ส่ง `state` ทันที และส่ง `provision` ถ้ายังมี token ค้าง

> [!WHY]
> **Last Will คืออะไร และทำไมสำคัญ**
> ถ้าไฟดับหรือสาย LAN หลุด บอร์ดบอกใครไม่ทัน Last Will คือข้อความที่บอร์ดฝากไว้กับ Broker ล่วงหน้า เมื่อ Broker พบว่าบอร์ดหายไปโดยไม่ได้ตัดการเชื่อมต่อตามปกติ Broker จะส่งข้อความนั้นแทนบอร์ด Backend จึงรู้ทันทีว่าเครื่องออฟไลน์ โดยไม่ต้องรอ timeout เอง ถ้าบอร์ดตัดการเชื่อมต่อแบบปกติ (เช่นตอนรีบูตเพื่อ OTA) Broker จะไม่ส่ง Last Will

## เส้นทางที่ 2: บอร์ดแอร์ส่ง `status` (หัวใจของระบบ)

### สิ่งที่บอร์ดส่ง

ทุก 10 วินาทีที่ `…/status` แบบ retain

```json
{
  "online": true,
  "deviceId": "ESP32-A1B2C3D4E5F6",
  "firmwareVersion": "2.5.2",
  "roomNumber": "16302",
  "airNumber": 1,
  "ip": "192.168.1.45",
  "rssi": -58,
  "pzemAvailable": true,
  "acRunning": true,
  "outsideSchedule": false,
  "scheduleConfigured": true,
  "classScheduleConfigured": true,
  "historyPending": 0,
  "voltage": 221.4,
  "current": 4.512,
  "powerWatts": 980.2,
  "energyKwh": 123.456,
  "frequencyHz": 50.0,
  "powerFactor": 0.98
}
```

- ถ้า PZEM อ่านไม่ได้ ค่าไฟทั้ง 6 ค่าจะเป็น `null`
- ถ้ามีข้อผิดพลาดจาก OTA จะมี `otaError` เพิ่ม
- บอร์ดรุ่นสายแอร์ (Daikin SLM8) เพิ่มฟิลด์ `controlMode`, `airBrand`, `busOk`, `compressorRunning`, `unitRoomTemperature`, `roomTemperature` ซึ่ง Backend อ่านเฉพาะ `controlMode`: ถ้าเป็น `wired` จะปรับคอลัมน์ `protocol` ของเครื่องนั้นให้เป็นโปรโตคอลสายแอร์ ส่วนฟิลด์อื่นไม่ได้ถูกเก็บ

### สิ่งที่ Backend ทำต่อ (ตามลำดับ)

ฟังก์ชัน `handleIncomingMessage` → `handleAirStatus` ใน `services/mqtt.js` ทำ **ทีละข้อความต่อบอร์ด** ผ่าน `runSerialForDevice` เพื่อไม่ให้ status สดกับข้อมูลย้อนหลังแย่งแก้ค่าเดียวกัน

1. **ตรวจ topic** ว่าตรงรูปแบบและ JSON อ่านได้ ถ้าไม่ใช่ ทิ้ง
2. **ตรวจว่าใช่คำตอบ "ล้างค่าแล้ว"** (`unprovisioned: true`) หรือไม่ ถ้าใช่ ปลดการรอแล้วจบ
3. **ปรับ `protocol`** ถ้าเป็นบอร์ดสายแอร์และค่าไม่ตรง (เขียนเฉพาะเมื่อไม่ตรง ไม่เขียนทุก 10 วินาที)
4. **จัดรูปค่า** (`normalizePowerStatus`): ถ้า `pzemAvailable` ไม่เป็น `true` ค่าไฟทุกค่าถูกบังคับเป็น `null` และ `acRunning`, `outsideSchedule` เป็น `false`
5. **อ่านแถวเดิมของเครื่อง** ก่อนทับ เพื่อใช้หาผลต่างเลขมิเตอร์
6. **บันทึกถังรายชั่วโมง** (`recordEnergySample`) เฉพาะเมื่อ `historyPending = 0` คำนวณผลต่างของ `energyKwh` กับครั้งก่อน นับเวลาที่แอร์ทำงานและเวลาออนไลน์ แล้วบวกเข้าแถวของชั่วโมงนั้น (เวลาไทย) ใน `energy_hourly`
7. **เขียนค่าล่าสุดทับ** ใน `air_conditioners` (`is_online`, `voltage`, `current_amp`, `power_watts`, `energy_kwh`, `frequency_hz`, `power_factor`, `pzem_available`, `ac_running`, `outside_schedule`, `last_seen_at`)
8. **บันทึกรุ่นเฟิร์มแวร์และผล OTA** (`firmware_version`, `ota_error`)
9. **บันทึก `history_pending`** (เฉพาะตอนออนไลน์)
10. **ส่ง `schedule-status` กลับ** ให้บอร์ดนี้ (ถ้าออนไลน์และอุปกรณ์เปิดใช้งานแล้ว) ดูเส้นทางที่ 5
11. **แจ้งผู้ฟังเหตุการณ์** ซึ่งก็คือระบบปิดแอร์อัตโนมัติ ให้ประเมินห้องนี้ใหม่ทันที

> [!WARN]
> ขั้น 5 → 6 → 7 ต้องเรียงแบบนี้ ถ้าเขียนค่าทับก่อน จะไม่เหลือเลขมิเตอร์เดิมไว้ลบ และถ้าผลต่างติดลบ (มิเตอร์ PZEM ถูกรีเซ็ต) หรือเกิน 50 kWh Backend นับเป็น 0 กันตัวเลขเพี้ยน และถ้าบอร์ดเงียบนานเกิน 5 นาที เวลาที่หายไปจะไม่ถูกนับเป็นเวลาทำงาน

### เมื่อบอร์ดหลุด (Last Will)

ข้อความ `{"online":false,"deviceId":"…"}` เข้าทางเดียวกับ status ปกติ ผลคือ Backend ตั้ง `is_online = 0`, ค่าไฟทุกค่าเป็น `null` และ `ac_running = 0` ไม่ส่ง `schedule-status` (เพราะไม่ออนไลน์) และไม่ทับรุ่นเฟิร์มแวร์เดิม (ข้อความนี้ไม่มีฟิลด์นั้น) ค่าที่แอปเห็นจะเปลี่ยนเป็นออฟไลน์เมื่อดึงรอบถัดไป

## เส้นทางที่ 3: ผู้ใช้สั่งแอร์ (`command` → IR → `state`)

```text
[แอป] POST /api/air-conditioners/:deviceId/command  (ต้องล็อกอิน)
   │
[Backend routes/air-conditioners.js]
   │  1. หาเครื่องในฐานข้อมูล ไม่พบ → 404
   │  2. provision_status ต้องเป็น active ไม่งั้น → 409
   │  3. validateAirState() ตรวจค่าตามชนิดแอร์ (อุณหภูมิ โหมด ลม ฯลฯ)
   │  4. publishAirCommand() → ส่งเข้า Broker  (ถ้า Broker ไม่ต่อ → 503)
   │  5. ตอบแอปทันที 202 พร้อม commandId  (ยังไม่รอบอร์ด)
   ▼
[Broker] rmutt/ac/<deviceId>/command   QoS 1, ไม่ retain
   ▼
[บอร์ดแอร์] mqttCallback เก็บข้อความ → loop() เรียก processMqttCommand()
   │  ตรวจซ้ำที่บอร์ด: อุณหภูมิ 16–30 °C (แอร์ Saijo Denki 18–29 °C),
   │  โหมด/ความแรงลม/ทิศทางลมที่แอร์ Saijo Denki รองรับ
   │  → saveAirState() (เก็บลง flash) → ส่ง IR / สั่งผ่านสายแอร์
   │  → publishState(commandId)
   ▼
[Broker] rmutt/ac/<deviceId>/state   retain
   ▼
[Backend] UPDATE air_conditioners SET state_json = …, is_online = 1, last_seen_at = NOW
   ▼
[แอป] ดึงข้อมูลรอบถัดไป (≤ 10 วินาที) เห็น state ใหม่
```

ข้อความ `command` ที่ Backend ส่ง

```json
{
  "version": 1,
  "commandId": "0b7c…-uuid",
  "sentAt": "2026-10-15T09:30:00.000Z",
  "state": {
    "power": true, "temperature": 25, "mode": "cool",
    "fanSpeed": "auto", "verticalSwing": "auto", "horizontalSwing": false,
    "eco": false, "turbo": false, "sleep": false, "quiet": false,
    "displayLight": true, "clean": false,
    "timerOnMinutes": null, "timerOffMinutes": null
  }
}
```

บอร์ดตอบด้วย `state` ที่มี `commandId` เดิมกลับมา รูปแบบ `{"commandId":"…","state":{…}}` และ Backend เก็บเฉพาะส่วน `state`

> [!WHY]
> **ทำไมตอบแอปทันทีแทนที่จะรอให้แอร์เปลี่ยนจริง**
> IR เป็นการยิงทางเดียว บอร์ดไม่มีทางรู้ว่าแอร์รับคำสั่งหรือไม่ ค่า `state` ที่ตอบกลับคือ "สิ่งที่บอร์ดสั่งไป" ไม่ใช่สิ่งที่แอร์ทำจริง ส่วนหลักฐานว่าแอร์ทำตามจริงคือกำลังไฟจาก PZEM ใน `status` (เช่นสั่งปิดแล้วกำลังไฟตกลงต่ำกว่า 10 W) การตอบ 202 ทันทีจึงตรงกับธรรมชาติของระบบและไม่ทำให้แอปค้าง

## เส้นทางที่ 4: ข้อมูลช่วงเน็ตหลุด (`history` ↔ `history-ack`)

ถ้าไม่มีส่วนนี้ ค่าไฟช่วงที่บอร์ดต่อ Broker ไม่ได้จะหายไปจากรายงาน

**ฝั่งบอร์ด**

1. ระหว่างที่ต่อ MQTT ไม่ได้ (หรือยังมีรายการค้างส่ง) บอร์ดสรุปค่าไฟทุก 5 นาที เขียนลง flash พาร์ติชัน `rmuttlog` เป็น ring buffer รายการละ 32 ไบต์ เก็บได้ 2,048 รายการ (ราว 7 วัน) เต็มแล้วทับของเก่า
2. พอต่อได้ รอแบบสุ่ม 5–45 วินาที แล้วส่งชุดละไม่เกิน 10 รายการที่ `…/history` ห่างกันอย่างน้อย 1 วินาที
3. **ส่งชุดต่อไปได้ก็ต่อเมื่อได้ `history-ack`** ถ้าไม่ได้ใน 20 วินาที ส่งชุดเดิมซ้ำ
4. ได้ `history-ack` แล้วลบรายการที่ยืนยันออกจาก flash

**แต่ละรายการ** เป็น array ตัวเลข 15 ช่อง เรียงตามนี้ `[เวลาปลายช่วง, เลขมิเตอร์ kWh, แรงดันเฉลี่ย×10, ต่ำสุด×10, สูงสุด×10, กระแสเฉลี่ย×1000, สูงสุด×1000, กำลังเฉลี่ย×10, ต่ำสุด×10, สูงสุด×10, PF×100, (ความถี่−40)×10, วินาทีที่แอร์ทำงาน, จำนวนตัวอย่าง, flags]` ส่งเป็นจำนวนเต็มคูณสเกลเพื่อให้ข้อความสั้นและเก็บได้ในไบต์น้อย

```json
{
  "v": 1,
  "deviceId": "ESP32-A1B2C3D4E5F6",
  "records": [
    [1760520300, 123.4, 2214, 2205, 2230, 4512, 5100,
     9802, 120, 11000, 98, 100, 240, 150, 1]
  ]
}
```

**ฝั่ง Backend** (`handleAirHistory` → `recordHistoryBatch`)

1. รับสูงสุด 50 รายการต่อชุด ถอดรหัสทีละรายการ รายการผิดรูปแบบนับเป็น `invalid`
2. เปิด transaction แล้วล็อกแถวของเครื่อง (`FOR UPDATE`)
3. ข้ามรายการที่เก่ากว่า 31 วัน อยู่ในอนาคตเกิน 5 นาที หรือเวลาไม่เกิน "จุดต่อ" ที่บันทึกไปแล้ว (จึงส่งซ้ำกี่ครั้งก็ไม่นับซ้ำ)
4. ที่เหลือคำนวณผลต่างจากจุดต่อ บวกเข้าถังรายชั่วโมง และขยับจุดต่อไปข้างหน้า
5. ตอบ `history-ack` ที่ `rmutt/ac/<deviceId>/history-ack`

```json
{
  "version": 1,
  "upTo": 1760520300,
  "stored": 10,
  "skipped": 0
}
```

ถ้าบันทึกไม่สำเร็จ Backend **ไม่ตอบ** บอร์ดจึงส่งชุดเดิมใหม่เอง ระหว่างที่ `historyPending > 0` Backend ไม่บันทึก status สดลงถัง ไม่งั้นพลังงานช่วงเน็ตหลุดจะถูกนับซ้ำ

> [!NOTE]
> "จุดต่อ" คือคอลัมน์ `energy_chain_*` ในตาราง `air_conditioners` (เวลา เลขมิเตอร์ และสถานะแอร์ของตัวอย่างล่าสุดที่บันทึกแล้ว) ข้อมูลสดและข้อมูลย้อนหลังใช้จุดต่อเดียวกัน จึงไม่มีช่วงไหนซ้ำหรือหาย รายละเอียดอยู่ในบท 20

## เส้นทางที่ 5: `schedule-status` — บอกบอร์ดว่าตอนนี้ "อยู่ในคาบ" หรือไม่

Backend รู้ตารางเรียน วันเปิดภาคเรียน และการจองห้อง บอร์ดไม่รู้ Backend จึงประเมินให้ทุกครั้งที่ได้ status ที่ออนไลน์ แล้วส่งที่ `…/schedule-status` แบบ retain

```json
{
  "version": 1,
  "classScheduleConfigured": true,
  "withinClassSchedule": true,
  "evaluatedAt": "2026-10-15T09:30:10.000Z",
  "timezone": "Asia/Bangkok"
}
```

- Backend อ่านตาราง `class_schedules` ของห้อง ตรวจว่าอยู่ในช่วงภาคเรียนหรือไม่ (`academic_terms`) และนับ `room_bookings` ที่กำลังเกิดขึ้นเป็น "อยู่ในคาบ" ด้วย
- บอร์ดเก็บค่าไว้และใช้ได้ 2 นาที ถ้าไม่ได้ข้อความใหม่เกินนั้น (เช่น Backend ล่ม) จะใช้ตารางเปิด-ปิดประจำวันที่ตั้งไว้ในบอร์ดแทน
- บอร์ดใช้ค่านี้ตั้งธง `outsideSchedule` (แอร์ทำงาน และไม่อยู่ในคาบ) แล้วรายงานกลับใน status ถัดไป พร้อมเปลี่ยนไฟ LED เตือน

## เส้นทางที่ 6: บอร์ดตรวจคน → ปิดแอร์อัตโนมัติ

### บอร์ดตรวจคนส่ง `status`

```json
{
  "online": true,
  "deviceId": "OCC32-A1B2C3D4E5F6",
  "firmwareVersion": "1.3.9",
  "roomNumber": "16302",
  "radarAvailable": true,
  "occupied": false,
  "staticThreshold": 25
}
```

ส่งทุก 10 วินาที และทันทีที่ `occupied` หรือ `radarAvailable` เปลี่ยน Backend อัปเดต `occupancy_sensors` (`is_online`, `radar_available`, `is_occupied`, `last_seen_at`, รุ่นเฟิร์มแวร์) แล้วค้นหาห้องของเซ็นเซอร์นั้น ส่งให้ระบบปิดแอร์ประเมินเฉพาะแอร์ในห้องนั้น

### ระบบปิดแอร์ตัดสินใจ

`services/auto-off.js` ถูกปลุกจากสามทาง คือ status ของแอร์ status ของเซ็นเซอร์ และจับเวลาเองทุก 10 วินาที (เผื่ออุปกรณ์เงียบไปเฉย ๆ) โดยมีล็อกใน MariaDB กันไม่ให้ Backend สองตัวยิงซ้ำกัน ถ้าแอดมินปิดสวิตช์รวมไว้ ระบบหยุดและล้างนาฬิกาที่ค้าง

| เงื่อนไขที่ตรวจ | ถ้าไม่ผ่าน |
|---|---|
| เซ็นเซอร์ในห้อง ออนไลน์ และเรดาร์พร้อม | ไม่ปิด (ไม่รู้ว่ามีคนไหม จึงไม่เสี่ยง) ถ้ากำลังนับถอยหลังอยู่ ยกเลิก |
| PZEM อ่านได้ | ไม่ปิด (ตรวจไม่ได้ว่าแอร์หยุดจริงไหม) |
| ห้องว่าง | มีคนเข้ามา → ยกเลิกทันที |
| แอร์กินไฟอยู่ | ถ้ากำลังนับและเคยสั่งปิดแล้ว = สำเร็จ ถ้ายังไม่เคยสั่ง = ยกเลิก |

ถ้าผ่านทั้งหมดและยังไม่นับ → เริ่มนับถอยหลัง 5 นาที (15 นาทีถ้าอยู่ในคาบเรียนหรือมีการจอง) เก็บเวลาไว้ใน `auto_off_deadline_at` ครบเวลาแล้วยังว่าง → ส่ง `command` ปิดแอร์ (ใช้ค่าสถานะล่าสุด แล้วตั้ง `power: false`) ยิงซ้ำทุก 20 วินาทีได้สูงสุด 5 ครั้ง ผลลัพธ์

- กำลังไฟตกจนถือว่าแอร์หยุด → บันทึกแจ้งเตือน `auto_off_succeeded` แล้วล้างนาฬิกา
- ครบ 5 ครั้งแล้วยังกินไฟ → แจ้งเตือน `auto_off_failed` ให้คนมาจัดการ
- ไม่มีคาบเรียน แต่แอร์ทำงานและมีคนอยู่ → แจ้งเตือน `outside_schedule_occupied` (ปิดอัตโนมัติเมื่อเงื่อนไขหมดไป)

คำสั่งปิดที่ยิงออกไปหน้าตาเหมือนคำสั่งที่ผู้ใช้สั่งทุกประการ บอร์ดจึงไม่รู้ด้วยซ้ำว่าใครสั่ง

## เส้นทางที่ 7: ติดตั้งบอร์ดใหม่ (`provision` ↔ `provision-ack`)

```text
แอดมิน (แอป) กรอกห้อง/แอร์ → POST /api/air-conditioners/reservations (ขอจองอุปกรณ์)
   │ Backend สร้างแถว provision_status = reserved
   │ สร้าง token แบบสุ่ม เก็บเฉพาะ "แฮช" + เวลาหมดอายุ 15 นาที
   │ (โหมด dynsec) สร้างบัญชี MQTT + ACL ให้บอร์ดนี้
   ▼
แอป → บอร์ด ทาง Bluetooth: Wi-Fi + MQTT (host, topic, user/pass) + token
   ▼
บอร์ดต่อ Wi-Fi และ Broker แล้วส่ง  …/provision  (retain) ทุก 10 วินาที
   { "token": "…", "deviceId": "ESP32-…", "roomNumber": "16302", "airNumber": 1 }
   ▼
Backend activateProvisioning():
   ตรวจว่าแถวเป็น reserved/active, token ยังไม่หมดอายุ, แฮชของ token ตรงกัน
   → provision_status = 'active', is_online = 1
   → ส่ง  …/provision-ack (retain)  { "version":1, "activated":true, "deviceId":"…", "token":"…" }
   → ลบแฮช token และเวลาหมดอายุออกจากฐานข้อมูล
   → ล้าง retained ของ  …/provision  (ส่งข้อความว่าง)
   ▼
บอร์ดได้ provision-ack ที่ token ตรงกับของตัวเอง → ลบ token ใน flash
   → ล้าง retained ของ  …/provision-ack (ส่งข้อความว่าง)
```

ถ้า token ไม่ตรงหรือหมดอายุ Backend ไม่ทำอะไรเลย (ไม่ตอบ ไม่บันทึก) ผู้ใช้จึงเห็นเครื่องค้างที่สถานะ reserved แล้วต้องจองใหม่ บอร์ดตรวจคนทำแบบเดียวกันทุกประการที่ `rmutt/occupancy/…`

> [!WHY]
> **ทำไมใช้ retain กับ provision และ provision-ack แล้วต้องล้างทิ้ง**
> retain ทำให้ข้อความรออยู่ที่ Broker แม้อีกฝ่ายยังไม่ต่อ ถ้า Backend รีสตาร์ตอยู่พอดี พอกลับมาก็ยังเห็น `provision` ของบอร์ด และถ้าบอร์ดหลุดก่อนได้ ack พอต่อกลับมาก็ยังได้ `provision-ack` แต่ข้อความพวกนี้มีความลับ (token) จึงต้องล้างทิ้งเมื่อใช้เสร็จ ไม่ให้ค้างบน Broker

## เส้นทางที่ 8: คำสั่งพิเศษทาง `command`

นอกจาก `state` แล้ว topic `command` รับ `action` อีกสามแบบ (ทั้งบอร์ดแอร์และบอร์ดตรวจคน) ส่งเข้า QoS 1 ไม่ retain

| `action` | ใครสั่ง | บอร์ดทำอะไร |
|---|---|---|
| `enter_setup` | แอดมินกด "ตั้งค่าใหม่" (`POST …/setup-mode`) | เปิดโหมดตั้งค่า Bluetooth โดยยังออนไลน์อยู่ ใช้ได้ภายในหน้าต่าง 5 นาที |
| `ota` พร้อม `url` | แอดมินกดอัปเดตเฟิร์มแวร์ | ตรวจว่า URL เป็นของ Backend ที่อนุญาต (ไม่งั้นรายงาน `otaError: url_rejected`) ตัดการเชื่อมต่อ MQTT ดาวน์โหลดผ่าน HTTPS เขียนลงเครื่อง แล้วรีบูต ถ้าล้มเหลวทำงานต่อด้วยรุ่นเดิมและรายงานสาเหตุใน `otaError` |
| `unprovision` พร้อม `deviceId` | Backend ตอนแอดมินลบอุปกรณ์ | ตรวจว่า `deviceId` เป็นของตัวเองอีกชั้น แล้วล้างค่าทั้งหมด (Wi-Fi, MQTT, ห้อง, สถานะแอร์, ข้อมูลย้อนหลัง) และรีบูตเข้าโหมดตั้งค่า |

### ลำดับตอนลบอุปกรณ์

ลำดับสำคัญเพราะถ้าลบบัญชี MQTT ก่อน Broker จะตัดบอร์ดทันทีและคำสั่งไปไม่ถึง

1. ลบแถวในฐานข้อมูล
2. ส่ง `{"action":"unprovision","deviceId":"…"}` ไปที่ `command` แล้วรอสูงสุด 4 วินาที
3. บอร์ดตอบที่ `status` ว่า `{"deviceId":"…","online":false,"unprovisioned":true}` แล้วล้าง retained ของ `status` และ `state` ของตัวเอง ตัดการเชื่อมต่อแบบปกติ (ไม่ให้ Last Will ถูกส่ง) แล้วล้างค่าและรีบูต
4. Backend ล้างข้อความ retain ของอุปกรณ์ทั้งหมดบน Broker (`command`, `state`, `status`, `provision`, `provision-ack`, `schedule-status`)
5. ลบบัญชี MQTT ของบอร์ด

ถ้าบอร์ดออฟไลน์ คำสั่งไม่ถึง แต่การลบในฐานข้อมูลยังสำเร็จเสมอ (ไม่ส่งแบบ retain เพราะถ้าเพิ่มบอร์ดตัวเดิมกลับมา คำสั่งค้างจะล้างบอร์ดอีกรอบ) เมื่อบอร์ดตัวนั้นกลับมาออนไลน์ Broker จะปฏิเสธรหัสทุกครั้ง และบอร์ดล้างค่าตัวเองหลังถูกปฏิเสธติดกันเกิน 2 นาที (อย่างน้อย 10 ครั้ง)

## สรุป: ข้อความไหนเปลี่ยนอะไรในฐานข้อมูล

| ข้อความ | ตาราง/คอลัมน์ที่เปลี่ยน |
|---|---|
| `status` ของแอร์ | `air_conditioners`: `is_online`, ค่าไฟ 6 ค่า, `pzem_available`, `ac_running`, `outside_schedule`, `last_seen_at`, `firmware_version`, `ota_error`, `history_pending`, `protocol` และ `energy_chain_*`; `energy_hourly`: บวกเข้าถังชั่วโมง |
| `state` | `air_conditioners.state_json`, `is_online`, `last_seen_at` |
| `history` | `energy_hourly` (ผ่าน transaction) และ `energy_chain_*` |
| `status` ของเซ็นเซอร์ | `occupancy_sensors`: `is_online`, `radar_available`, `is_occupied`, `last_seen_at`, `firmware_version`, `ota_error` |
| `provision` | `provision_status = 'active'`, ล้าง `provisioning_token_hash` และ `provisioning_expires_at` |
| การตัดสินใจปิดแอร์ | `air_conditioners.auto_off_*`, `state_json`; `system_alerts` |

## ลองดูข้อความจริงด้วยตัวเอง

ถ้าเครื่องที่ต่อ Broker ได้มีโปรแกรม Mosquitto client ติดตั้งอยู่ ใช้ดูข้อความที่ไหลผ่านได้ (ต้องมีบัญชีที่มีสิทธิ์อ่าน topic เหล่านี้ เช่นบัญชีของ Backend)

```bash
# ดูทุกข้อความของบอร์ดแอร์ทั้งหมด (-v แสดงชื่อ topic ด้วย)
mosquitto_sub -h <broker> -p 1883 -u <user> -P <password> -t 'rmutt/ac/#' -v

# ดูเฉพาะ status ของเซ็นเซอร์ตรวจคน
mosquitto_sub -h <broker> -p 1883 -u <user> -P <password> -t 'rmutt/occupancy/+/status' -v
```

ข้อความ `status` และ `state` เป็น retain เปิดดูแล้วจะเห็นค่าล่าสุดทันทีแม้บอร์ดยังไม่ส่งรอบใหม่ ส่วน `command` ไม่ retain จะเห็นเฉพาะตอนมีคนสั่ง

## คำถามที่อาจารย์อาจถาม

> [!ASK]
> **ถาม:** ทำไมแอปไม่ subscribe MQTT เองเพื่อให้เห็นค่าเรียลไทม์?
> **ตอบ:** ตั้งใจให้ Backend เป็นประตูเดียว เพราะต้องตรวจสิทธิ์ผู้ใช้ ตรวจค่าที่สั่ง และบันทึกประวัติ ถ้าแอปต่อ Broker ตรงต้องแจกรหัส Broker ให้ทุกเครื่องและกระจายกติกาไปทุกแอป ข้อเสียคือแอปเห็นค่าช้ากว่าจริงได้สูงสุดราว 10 วินาที (ช่วงดึงข้อมูล) ซึ่งยอมรับได้เพราะค่าไฟและสถานะแอร์ไม่ได้เปลี่ยนเร็วขนาดนั้น

> [!ASK]
> **ถาม:** ถ้า Backend ล่มระหว่างที่บอร์ดส่ง status จะเกิดอะไรขึ้น?
> **ตอบ:** บอร์ดส่ง QoS 0 และ Backend ต่อ Broker แบบ `clean: true` ข้อความ status ช่วงนั้นหายไป แต่ไม่กระทบความถูกต้องของค่าไฟสะสม เพราะค่าไฟคิดจากผลต่างของเลขมิเตอร์ PZEM ครั้งแรกที่กลับมาจะบวกพลังงานของช่วงที่หายไปเข้าชั่วโมงปัจจุบัน (ถ้าเงียบเกิน 5 นาที เวลาทำงานช่วงนั้นไม่นับ แต่พลังงานนับตามผลต่างเลขมิเตอร์) ส่วน `status` และ `state` ที่เป็น retain ทำให้เห็นค่าล่าสุดทันทีเมื่อกลับมาต่อ

> [!ASK]
> **ถาม:** ถ้าบอร์ดส่งข้อมูลย้อนหลังซ้ำ จะนับค่าไฟซ้ำไหม?
> **ตอบ:** ไม่นับ Backend จำ "จุดต่อ" (เวลาของตัวอย่างล่าสุดที่บันทึก) รายการที่เวลาไม่เกินจุดต่อถูกข้าม และจะไม่ตอบ `history-ack` ถ้าบันทึกไม่สำเร็จ บอร์ดจึงส่งซ้ำได้อย่างปลอดภัย ระหว่างที่ยังส่งไม่ครบ Backend ยังไม่บันทึก status สดลงถังด้วย

> [!ASK]
> **ถาม:** ทำไมระบบปิดแอร์อยู่ที่ Backend ไม่ใช่ในบอร์ด?
> **ตอบ:** เซ็นเซอร์ตรวจคนกับบอร์ดแอร์เป็นคนละตัวและไม่ได้คุยกันเอง Backend เป็นที่เดียวที่เห็นทั้งสองฝั่ง รวมทั้งตารางเรียน ภาคเรียน และการจองห้อง ข้อเสียคือถ้า Backend ล่ม ระบบปิดอัตโนมัติหยุด แต่ตารางเปิด-ปิดประจำวันในบอร์ดยังทำงานต่อได้

> [!ASK]
> **ถาม:** ใครสั่งปิดแอร์ ผู้ใช้หรือระบบ บอร์ดแยกออกไหม?
> **ตอบ:** แยกไม่ออกและไม่จำเป็นต้องแยก ทั้งสองทางส่ง `command` รูปแบบเดียวกัน บอร์ดทำตามค่าที่ตรวจผ่าน ส่วนการแยกว่าใครสั่งอยู่ที่ Backend (ระบบปิดแอร์เขียน `auto_off_*` และสร้างแจ้งเตือน)
