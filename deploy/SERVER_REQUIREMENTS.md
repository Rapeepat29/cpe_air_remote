# ขอใช้เซิร์ฟเวอร์ — ระบบ RMUTT Save Energy (อาคาร 16)

เอกสารนี้สรุปทรัพยากรที่ต้องการจากฝ่ายเทคโนโลยีสารสนเทศ ว่าแต่ละส่วนนำไปใช้ทำอะไร
และเหตุผลที่ต้องใช้ขนาดเท่านี้ ตัวเลขมาจากการวัดระบบจริงที่รันอยู่และการคำนวณ
จากจำนวนอุปกรณ์ในอาคาร 16

## 1. ระบบนี้ทำอะไร

ระบบติดตามการใช้ไฟฟ้าและควบคุมเครื่องปรับอากาศของอาคาร 16 ประกอบด้วย

- **บอร์ด ESP32 ที่เครื่องปรับอากาศ** (ประมาณ 1–3 บอร์ดต่อห้อง) วัดไฟด้วย PZEM-004T
  และสั่งแอร์ด้วยอินฟราเรด (แอร์ Daikin ที่ใช้รีโมตติดผนังใช้บอร์ดรุ่นต่อสายแอร์แทน)
- **บอร์ด ESP32 + เรดาร์ LD2410 ตรวจจับคน** ห้องละ 1 บอร์ด
- **เซิร์ฟเวอร์** รับข้อมูลจากบอร์ดทุกตัวผ่าน MQTT เก็บลงฐานข้อมูล ตัดสินใจปิดแอร์อัตโนมัติ
  เมื่อห้องว่าง และให้บริการเว็บแอปกับแอปมือถือของเจ้าหน้าที่

เซิร์ฟเวอร์ต้องทำงานตลอด 24 ชั่วโมง เพราะการปิดแอร์อัตโนมัติและการสั่งแอร์จากแอป
ทำผ่านเซิร์ฟเวอร์ทั้งหมด ถ้าเซิร์ฟเวอร์หยุด แอร์ยังใช้รีโมตปกติได้ แต่ระบบประหยัดไฟจะหยุดทำงาน

ขนาดที่ใช้คำนวณ: ห้อง 22 ห้อง, บอร์ดแอร์สูงสุดประมาณ 50 ตัว, บอร์ดเซ็นเซอร์ 22 ตัว,
ผู้ใช้งานพร้อมกันไม่เกิน 50 คน

## 2. สเปกเครื่องที่ขอ

| รายการ | ขั้นต่ำ | แนะนำ |
|---|---|---|
| CPU | 2 vCPU (x86-64) | 2–4 vCPU |
| หน่วยความจำ (RAM) | 2 GB + swap 2 GB | **4 GB** |
| ดิสก์ | 40 GB SSD | **60 GB SSD** |
| ระบบปฏิบัติการ | Ubuntu Server 22.04 LTS | **Ubuntu Server 24.04 LTS** (64-bit) |
| รูปแบบ | VM หรือเครื่องจริงก็ได้ | VM ที่มีการสำรอง snapshot |
| สิทธิ์ | บัญชีที่ใช้ `sudo` ได้ และติดตั้ง Docker ได้ | |

### 2.1 ซอฟต์แวร์ที่รันบนเครื่อง (ทั้งหมดอยู่ใน Docker)

| บริการ | ใช้ทำอะไร | หน่วยความจำที่วัดได้ |
|---|---|---|
| Caddy | เว็บเซิร์ฟเวอร์ HTTPS, ขอ/ต่ออายุใบรับรองอัตโนมัติ, เสิร์ฟเว็บแอปและไฟล์อัปเดตเฟิร์มแวร์ | ~40 MB |
| Backend (Node.js 22) | API ของแอป/เว็บ, รับข้อมูลจากบอร์ด, ตัดสินใจปิดแอร์อัตโนมัติทุก 10 วินาที, สร้างไฟล์ Excel | ~100 MB |
| MariaDB 11 | ฐานข้อมูลผู้ใช้ ห้อง ตารางเรียน อุปกรณ์ และประวัติไฟฟ้ารายชั่วโมง | ~110 MB ตอนว่าง (buffer pool 128 MB) |
| Mosquitto 2 | MQTT Broker รับ-ส่งข้อความกับบอร์ด ESP32 ผ่าน TLS | ~8 MB |

### 2.2 ทำไม RAM 4 GB

- บริการทั้งสี่ใช้รวมประมาณ **300 MB** ตอนทำงานปกติ ระบบปฏิบัติการกับ Docker ใช้อีก **0.5–0.7 GB**
- ตอนอัปเดตระบบ เครื่องต้อง build Backend ใหม่ (`npm ci` + Docker build) ใช้หน่วยความจำเพิ่มชั่วคราว **0.5–1 GB**
- MariaDB จะใช้หน่วยความจำมากขึ้นตามข้อมูลที่สะสม เพื่อให้รายงานรายปีเร็ว
  (ข้อมูล 1 ปีประมาณ 230 MB ถ้าอยู่ในหน่วยความจำได้ทั้งหมด การดึงรายงานจะไม่ต้องอ่านดิสก์)
- ที่ 2 GB ระบบทำงานได้แต่ต้องพึ่ง swap ตอน build และไม่มีที่เหลือให้เครื่องมือ monitor
  หรือ antivirus ของมหาวิทยาลัย **4 GB จึงเป็นขนาดที่ใช้งานได้สบายตลอดอายุโครงการ**

### 2.3 ทำไม CPU 2 vCPU

งานปกติเบามาก: ข้อความจากบอร์ดประมาณ **7 ข้อความ/วินาที** และคำขอจากแอป/เว็บ
ประมาณ **15 คำขอ/วินาที** ตอนมีผู้ใช้เปิดพร้อมกัน 50 คน แต่มีช่วงที่ใช้ CPU พร้อมกันหลายงาน

- เมื่อ Wi-Fi อาคารกลับมาหลังล่ม บอร์ดประมาณ 70 ตัวจะต่อ TLS ใหม่พร้อมกัน
- การส่งออกรายงาน Excel (สูงสุด 20,000 แถวต่อไฟล์) และสรุปรายเดือนจากฐานข้อมูล
- การ build Backend ตอนอัปเดตระบบ

2 vCPU ทำให้งานเหล่านี้ไม่ไปแย่ง CPU กับการรับข้อมูลจากบอร์ด จนการปิดแอร์อัตโนมัติช้าลง

### 2.4 ทำไมดิสก์ 60 GB

| ส่วน | ขนาด |
|---|---|
| ระบบปฏิบัติการและอัปเดต | ~10 GB |
| Docker images + build cache | ~3 GB |
| ฐานข้อมูล (วัดได้ ~363 ไบต์/แถว, 72 บอร์ด × 8,760 ชั่วโมง/ปี) | **~230 MB ต่อปี** |
| สำรองฐานข้อมูลรายวัน เก็บ 14 วัน (บีบอัด) | < 1 GB ในปีแรก |
| log (จำกัดไว้ 50 MB ต่อบริการ) | ~0.3 GB |
| ไฟล์อัปเดตเฟิร์มแวร์ ESP32 (~2 MB ต่อรุ่น) | < 0.1 GB |

รวมปีแรกประมาณ **15 GB** ข้อมูลโตปีละไม่ถึง 1 GB (รวม backup) 40 GB จึงพอ
แต่ **60 GB เผื่อให้เก็บประวัติไฟฟ้าย้อนหลังได้หลายปี** (ใช้ทำรายงานเปรียบเทียบประหยัดไฟ)
และเผื่อพื้นที่ให้อัปเกรดระบบปฏิบัติการได้โดยไม่ต้องขยายดิสก์ ควรใช้ SSD
เพราะฐานข้อมูลเขียนทุกครั้งที่บอร์ดส่งค่า (หลายครั้งต่อวินาที)

### 2.5 ปริมาณการใช้เครือข่าย

- MQTT จากบอร์ด: ประมาณ 4 KB/วินาที ≈ **10 GB/เดือน** (รวม TLS)
- เว็บและแอป: หน้าเว็บโหลดครั้งแรก ~200 KB ผู้ใช้ที่เปิดค้างใช้ ~5 KB ทุก 10 วินาที
- ความเร็วเครือข่าย 10 Mbps ก็เพียงพอ

## 3. เครือข่ายและ Firewall

### 3.1 ชื่อโดเมน

ขอ subdomain ของมหาวิทยาลัยหนึ่งชื่อ (เช่น `energy.eng.rmutt.ac.th`) ชี้มาที่เครื่องนี้
ใช้ทั้งเว็บแอป, API ของแอปมือถือ และ MQTT ของ ESP32

### 3.2 พอร์ตขาเข้า

| พอร์ต | จากที่ไหน | ใช้ทำอะไร |
|---|---|---|
| **443/TCP** (HTTPS) | อินเทอร์เน็ต | เว็บแอปและแอปมือถือ เจ้าหน้าที่ใช้นอกมหาวิทยาลัยผ่านเน็ตมือถือได้ |
| **80/TCP** (HTTP) | อินเทอร์เน็ต | ให้ Let's Encrypt ตรวจโดเมนก่อนออกใบรับรอง และ redirect ไป 443 (ไม่มีข้อมูลผ่านพอร์ตนี้) |
| **8883/TCP** (MQTTS) | เครือข่าย Wi-Fi ที่บอร์ด ESP32 ใช้ (จำกัดเฉพาะวงของมหาวิทยาลัยได้) | บอร์ดรับคำสั่งและส่งค่าไฟ เข้ารหัส TLS ทุกครั้ง |
| 22/TCP (SSH) | เฉพาะเครือข่ายภายในหรือ VPN ของผู้ดูแล | ดูแลระบบและอัปเดต |

ไม่ต้องเปิดพอร์ตอื่น ฐานข้อมูล (3306) และ MQTT แบบไม่เข้ารหัส (1883)
อยู่ภายในเครื่องเท่านั้น

> ถ้าเปิดพอร์ต 80 จากอินเทอร์เน็ตไม่ได้ ให้ออกใบรับรอง TLS ของมหาวิทยาลัยสำหรับโดเมนนี้แทน
> (ต้องแจ้งผู้พัฒนาเพื่อเปลี่ยนใบรับรองรากในเฟิร์มแวร์ ESP32 ด้วย)

### 3.3 พอร์ตขาออกจากเซิร์ฟเวอร์

| ปลายทาง | ใช้ทำอะไร |
|---|---|
| 443 ไป Docker Hub, npm registry, Ubuntu mirror | ติดตั้งและอัปเดตซอฟต์แวร์ |
| 443 ไป Let's Encrypt (`acme-v02.api.letsencrypt.org`) | ขอและต่ออายุใบรับรองอัตโนมัติทุก ~60 วัน |
| 465 หรือ 587 ไป SMTP (Gmail หรือ SMTP relay ของมหาวิทยาลัย) | ส่งรหัส OTP ตอนผู้ใช้ลืมรหัสผ่าน |
| 123/UDP NTP | เวลาของเครื่องต้องตรง ไม่งั้น TLS และตารางเรียนผิด |

## 4. Wi-Fi สำหรับบอร์ด ESP32 (สำคัญ)

บอร์ด ESP32 มีข้อจำกัดที่ Wi-Fi ของมหาวิทยาลัยต้องรองรับ

- **2.4 GHz เท่านั้น** (ESP32 ไม่รองรับ 5 GHz)
- **WPA2-Personal (รหัสผ่านเดียว)** ESP32 ในโครงการนี้ **ไม่รองรับ** WPA2-Enterprise
  (ล็อกอินด้วยบัญชีผู้ใช้/802.1X) และไม่รองรับหน้า login แบบ captive portal
  จึงขอ SSID สำหรับอุปกรณ์ IoT ที่ใช้รหัสผ่านเดียว หรือ VLAN IoT ที่ครอบคลุมอาคาร 16
- ต้องออกไปที่เซิร์ฟเวอร์ **พอร์ต 8883** ได้ และเข้าถึง NTP (`pool.ntp.org`,
  `time.google.com`) ได้ เพื่อให้เวลาตรงก่อนตรวจใบรับรอง TLS
- ใช้ DHCP ได้ ไม่ต้องใช้ IP คงที่ และเปิด client isolation ได้
  (บอร์ดคุยกับเซิร์ฟเวอร์อย่างเดียว ไม่คุยกันเอง)

## 5. ความปลอดภัยที่ระบบมีอยู่แล้ว

- ทุกการเชื่อมต่อจากภายนอกเข้ารหัส TLS (HTTPS 443, MQTTS 8883) ใบรับรองต่ออายุอัตโนมัติ
- บอร์ด ESP32 **แต่ละตัวมีบัญชี MQTT ของตัวเอง** และเห็นเฉพาะข้อมูลของตัวเอง
  ถ้าบอร์ดตัวใดถูกถอดไปอ่านรหัส ก็สั่งอุปกรณ์ตัวอื่นไม่ได้ และถอนสิทธิ์ได้ทันทีจากหน้าเว็บ
- ผู้ใช้ล็อกอินด้วยรหัสผ่านที่เก็บแบบ bcrypt, มี rate limit กันเดารหัส,
  แยกสิทธิ์ admin/staff, รีเซ็ตรหัสผ่านด้วย OTP ทางอีเมล
- Backend ใช้บัญชีฐานข้อมูลที่มีสิทธิ์เฉพาะฐานข้อมูลของระบบ ไม่ใช้ root
- เว็บตั้ง Content-Security-Policy, HSTS และหัวความปลอดภัยมาตรฐาน
- สำรองฐานข้อมูลอัตโนมัติทุกวัน เก็บย้อนหลัง 14 วัน

## 6. สิ่งที่ขอเพิ่ม (ถ้ามี)

- **พื้นที่สำรองข้อมูลนอกเครื่อง** (เช่น NAS หรือ backup server ของมหาวิทยาลัย)
  ที่เข้าผ่าน SSH/rsync ได้ ประมาณ 5 GB ระบบจะส่งไฟล์สำรองรายวันไปเก็บให้อัตโนมัติ
- **snapshot ของ VM** ก่อนอัปเดตระบบปฏิบัติการ
- **SMTP relay ของมหาวิทยาลัย** สำหรับส่ง OTP (อีเมลถึงผู้ใช้ได้ดีกว่า Gmail ส่วนตัว)
- ให้ระบบ monitor ของมหาวิทยาลัยตรวจ `https://<โดเมน>/api/health` ทุก 5 นาที

## 7. สรุปสิ่งที่ขอ (สำหรับกรอกแบบฟอร์ม)

- VM Ubuntu Server 24.04 LTS 64-bit, **2–4 vCPU, RAM 4 GB, SSD 60 GB**, บัญชี sudo
- subdomain 1 ชื่อ ชี้มาที่เครื่องนี้
- เปิดขาเข้า 443 และ 80 จากอินเทอร์เน็ต, 8883 จาก Wi-Fi ที่บอร์ดใช้, 22 จากเครือข่ายผู้ดูแล
- เปิดขาออก 443, SMTP 465/587, NTP 123
- SSID/VLAN IoT แบบ 2.4 GHz + WPA2-Personal ครอบคลุมอาคาร 16
- (ไม่บังคับ) พื้นที่สำรองนอกเครื่อง ~5 GB, snapshot VM, SMTP relay
